# P003: Error Handling

## Definition
P003 validates comprehensive error response documentation and consistent error handling patterns. It ensures that every endpoint documents its failure modes, enabling automated negative testing and client-side error handling verification.

## DDT Axiom Mapping
**Completeness Axiom** — Error scenarios must be documented to enable negative testing. An API that only documents its happy path is incomplete from a testing perspective; the specification must enumerate failure modes to form a complete contract.

## Severity
Warning

## AutoFixable
Yes — common error responses (400, 401, 403, 404, 500) can be scaffolded with standard error schemas when missing.

## Checks Performed
1. 4xx client error responses documented for relevant operations
2. 5xx server error responses documented (at minimum 500 Internal Server Error)
3. Error response schemas include error codes
4. Error response schemas include human-readable messages
5. Error details schema is defined (structured error body, not just a string)
6. Common error responses are defined in components/responses for reuse
7. Error format is consistent across all endpoints (same schema structure)

## Mode Behavior
- **Minimal:** Only checks that existing error responses are well-formed (checks 3-5 on declared errors)
- **Test-ready:** Checks 1, 3-5 enforced (4xx responses required, error schemas validated — functional tests need to know error shapes; skips 5xx requirement, components reuse, and format consistency)
- **Strict:** Requires all error categories to be present (all 7 checks enforced)
