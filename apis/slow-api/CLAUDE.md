# Slow API -- Deliberately Slow Reference Implementation

## Overview
A FastAPI application derived from `perfect-api` that deliberately fails DriveBy P007 (Performance Testing) while passing all other principles (P001-P006, P008-P009). Every async route handler includes a 500ms artificial delay (`await asyncio.sleep(0.5)`) before any business logic.

Single requests complete successfully (functional tests pass), but under concurrent load (10+ users), P95 latency far exceeds the 200ms threshold that P007 enforces.

## How It Differs from perfect-api
- `import asyncio` added to imports
- `await asyncio.sleep(0.5)` inserted as the first line of every async route handler:
  - `create_task`, `get_products`, `get_product`, `create_product`, `update_product`, `delete_product`, `list_products_legacy`, `health_check`, `echo_test`
- Module name changed to `slow_api` (file and `__main__` reference)
- Everything else is identical: models, documentation, security, OpenAPI customization, startup data

## Thesis Insight
This API represents the most interesting case in the DDT evaluation matrix: a defect that is **invisible to static validation** (P001-P005 all pass) **and invisible to single-request functional testing** (P006 passes). The performance degradation only manifests under concurrent load, which is exactly what P007 is designed to catch.

This proves the DDT methodology's layered validation approach -- each principle layer catches a distinct class of defects:
- **Static layer** (P001-P005, P008-P009): catches specification and documentation defects
- **Functional layer** (P006): catches behavioral correctness defects
- **Performance layer** (P007): catches scalability and latency defects

No single layer is sufficient. The slow-api demonstrates that an API can be perfectly documented, functionally correct, and still unsuitable for production due to performance characteristics that only appear under load.
