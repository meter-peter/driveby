\chapter{A Conceptual Framework: Specification-Driven Testing}
\label{ch:methodology}

This chapter presents Specification-Driven Testing (SDT) as a conceptual framework for automated API quality assurance. We define the three axioms that constitute its theoretical foundation, present nine validation principles that operationalize the framework jointly under all three axioms, and specify four validation modes that govern how principles are applied in practice. The chapter defines \textit{what} SDT validates and \textit{why}; Chapter~\ref{ch:architecture} describes \textit{how} the DriveBy framework implements these definitions.

We claim SDT as a \emph{conceptual framework}---a strong theoretical core for a future formal methodology---rather than as a complete software-testing methodology in its own right. A complete formal methodology would additionally cover three elements that are deliberately out of scope here: a formal procedure for deriving tests from the specification (beyond the principle-driven check derivation we present), execution and failure semantics for runtime validation (beyond the binary pass/fail/severity model used by the validation gate), and lifecycle governance over how the principles themselves evolve as the underlying API specification standard changes. These are scoped as future work in Chapter~\ref{ch:conclusion}.

% ============================================================================
\section{The SDT Paradigm}
\label{sec:ddt-paradigm}
% ============================================================================

SDT formalises the third of the paradigms identified in Chapter~\ref{ch:related-work} (Section~\ref{subsec:spec-driven-gap}): where test-first requires engineers to author test cases and contract-first requires consumers to publish expectations, SDT derives all validation from the API specification itself---simultaneously the documentation, the contract, and the test oracle.

This is not a tooling distinction. It is a methodological one. SDT treats the specification as a \textit{complete} description of the API contract---not a partial sketch to be supplemented by external tests. \textit{What is being validated}: SDT operates on \emph{two} artefacts that must not be conflated. The static principles (P001--P005, P008, P009) validate the \emph{specification document itself}---they answer ``is this OpenAPI document complete, well-structured, and informative enough to support downstream automation?'' The runtime principles (P006, P007) validate the \emph{implementation against the specification}---they answer ``does the running API behave as the document declares?'' One scoping note: the \emph{content} of validation---which checks run, which probes are derived---comes from the specification alone, but the \emph{thresholds} parameterising the performance principle (P007: concurrent users, latency percentiles, success rates) are declared in the XSDLC custom resource (Chapter~\ref{ch:kubernetes}), a versioned deployment-policy artefact---SDT claims specification-sole derivation for test content, not for operational policy. Throughout this thesis, ``complete'' refers to the specification document unless explicitly qualified otherwise. The three axioms, defined in Section~\ref{sec:three-axioms}, apply uniformly to both readings.

These three properties---completeness, determinism, and observability---are axioms: foundational assumptions from which the entire framework follows. We organise SDT as a two-layer structure: the \textit{axiomatic layer} defines three axioms that any SDT-compliant validation must satisfy; the \textit{principle layer} defines nine concrete validation principles. Every principle is bound to satisfy all three axioms simultaneously---it must check a specific facet of contract completeness, produce a deterministic verdict (Section~\ref{subsec:fp-formalism}), and emit a structured, machine-readable result. The axioms are therefore framework-wide invariants rather than a partition of the principles; each principle nonetheless has a \emph{governing} axiom that primarily motivates it, alongside the axioms it impacts---a two-sided assignment made explicit in Table~\ref{tab:principle-catalogue}. The separation lets the axioms remain stable as principles evolve and gives a principled admission test for new checks: any proposed check must satisfy all three axioms.

% ============================================================================
\section{The Three Axioms}
\label{sec:three-axioms}
% ============================================================================

The three axioms of SDT define the minimal conditions under which specification-driven validation is sound. Each axiom addresses a distinct concern: the sufficiency of the specification as input, the reproducibility of the validation process, and the utility of the validation output.

A natural question is whether a fourth axiom---\textit{precision} or \textit{accuracy}, capturing whether the specification's claims correctly reflect the underlying API---should be added. We chose to fold the concern into Completeness: a specification cannot be fully ``complete'' in the SDT sense if its content is inaccurate, since inaccurate content fails the dual reading of completeness as both a validation precondition and as transferable knowledge. We acknowledge that an explicit Accuracy axiom would sharpen the framework's vocabulary for specifications that are syntactically complete but semantically incorrect, and record it as a candidate refinement for future work (Chapter~\ref{ch:conclusion}).

% ----------------------------------------------------------------------------
\subsection{Axiom of Completeness}
\label{subsec:axiom-completeness}
% ----------------------------------------------------------------------------

\textit{The API specification must fully describe the API contract; SDT validation must produce a finding for any aspect of the contract that the specification fails to cover.}

Completeness requires that the specification contains sufficient information to derive validation rules without external input---not every implementation detail, but everything a consumer needs to understand, integrate with, and depend on the API: endpoints, parameters, request and response schemas, error responses, security mechanisms, and usage examples. Per the folding decision above (Section~\ref{sec:three-axioms}), completeness also subsumes \emph{accuracy}: a specification that misrepresents the API is not complete in the SDT sense, however exhaustive its coverage. The static principles measure the descriptive facets on the document itself; the runtime principle P006 (Section~\ref{subsec:p006}) measures accuracy directly against the running implementation.

Completeness is the enabling axiom. Without it, specification-driven validation degenerates into partial checking---the validator can only assess what the specification happens to include, with no way to determine what is missing. Each of the nine principles (Table~\ref{tab:principle-catalogue}) measures one facet of completeness, together giving a multi-dimensional answer to whether the specification fully describes the contract.

Completeness admits a dual reading. In the validation sense, it ensures the specification contains sufficient information to derive validation rules; in the \textit{knowledge transfer} sense, sufficient information for a new engineer---or an autonomous agent---to understand, integrate with, and depend on the API without consulting tribal sources. The two readings coincide: the information needed to validate a contract is precisely the information a consumer needs to use it, so a specification satisfying P001--P004 is by construction an onboarding-complete artefact~\cite{nonaka-knowledge}, codified organisational knowledge that reduces cognitive load through self-service interfaces~\cite{team-topologies} and persists independently of its authors.

A subtle but important consequence: \textit{specification validity is itself a first-class output of SDT, not a pre-condition for applying it.} The very principles whose Axiom is Completeness (P001--P004 for the static facets, P006 for the runtime check) are what \emph{measure} completeness: the framework does not assume the specification is complete but produces a structured, per-facet report on the degree to which it is, with concrete remediation suggestions. The Axiom describes what SDT \emph{evaluates}, not what it requires as input.

% ----------------------------------------------------------------------------
\subsection{Axiom of Determinism}
\label{subsec:axiom-determinism}
% ----------------------------------------------------------------------------

\textit{SDT validation must produce identical results given the same specification, the same API, and the same validation mode.}

Determinism requires that the validation process is reproducible: the same inputs must yield the same outputs regardless of execution environment, time, or operator identity, eliminating subjectivity. This is critical for automation---a quality gate that produces different results on repeated execution cannot serve as a reliable gate. Determinism is satisfied at the level of the whole framework by the parallel-application semantics of Section~\ref{subsec:fp-formalism}: each principle is atomic and side-effect-free, the aggregation function is canonical, and the report is the same under any execution order or parallelism choice. It is therefore a structural property of how the principles compose, not a property of any one principle.

\textit{Context-dependent APIs and the determinism axiom.} Do context-aware APIs---those that legitimately return different responses for the same request based on tenant, locale, time-of-day, or feature-flag state---break the Determinism axiom? They do not: the axiom constrains \emph{validation results}, not API responses. A P006 functional test derived from a specification asserts the properties the specification declares (status code, schema shape, declared header presence), not the literal response body, so a multi-tenant API returning tenant-specific data satisfies P006 deterministically as long as every response conforms to the declared schema. Asserting \emph{literal content} would be stronger, but for context-dependent APIs it would shift the determinism burden onto the specification's examples, which would then have to be declared per tenant, locale, or flag state; SDT therefore scopes P006 assertions to contract conformance (Section~\ref{subsec:p006}). What \emph{does} break the axiom is non-determinism in the validation logic itself (random sampling, time-sensitive thresholds, retries with hidden side effects), which SDT explicitly forbids: such tests are not eliminated but parameterised to assert only specification-declared properties. Specifications that declare context-dependent behaviour (e.g.\ via \texttt{x-context} extensions or per-tenant servers) are first-class SDT inputs; Completeness covers these declarations too: such behaviour is part of the contract, so a specification omitting it is incomplete in the SDT sense.

Determinism is especially critical when the consumer of validation results is an autonomous agent: an agent that receives different results on repeated runs cannot distinguish genuine regressions from noise, and therefore cannot be trusted for autonomous corrective action~\cite{swe-agent}.

% ----------------------------------------------------------------------------
\subsection{Axiom of Observability}
\label{subsec:axiom-observability}
% ----------------------------------------------------------------------------

\textit{SDT validation must produce structured, machine-readable, and actionable reports for every principle it evaluates.}

Observability requires that validation output is structured, quantifiable, and suitable for automated consumption: results a CI pipeline can gate on, a dashboard can display, and an engineer can act on without interpreting free-text narratives. Where a code review yields unstructured prose, SDT produces structured reports with per-principle pass/fail status, severity classifications, specific check results, and suggested remediations. Observability is a property of every principle's output: each $f_{p_i}$ emits a structured, typed, machine-readable \texttt{PrincipleResult}, and aggregation preserves that structure into the final report. Functional-test outcomes (P006) are treated identically---their remediation-relevant information (failing endpoint, payload, status code) appears in the same form as static findings, so downstream automation acts on runtime and static results through one uniform interface.

``Automated consumption'' is deliberately broad: it encompasses CI/CD pipelines gating on exit codes, dashboards visualising quality trends, and autonomous engineering agents that parse validation reports and generate remediation code~\cite{swe-agent, devin-cognition}. Because results are structured and deterministic, they also support longitudinal tracking of quality trends across versions and APIs.

Observability admits a second reading that the validation \emph{conclusion}---not merely the \emph{output}---should be grounded in observable evidence. Some principles read this evidence from the specification document (e.g.\ whether a security scheme is declared, whether an error response is documented), others from the deployed system at runtime (e.g.\ whether the declared scheme is actually enforced, whether responses conform to the declared schema). The framework places no special weight on one source over the other: both are first-class inputs to validation, and both contribute structured findings under the Observability axiom.

\section{The Nine Principles}
\label{sec:nine-principles}
% ============================================================================

Each SDT principle defines a specific dimension of API quality, traces its rationale to one or more axioms, classifies its severity, and enumerates the concrete checks it performs.

\textit{Severity semantics.} \textbf{Critical}: failure indicates the specification cannot support meaningful downstream automation (test generation, contract enforcement, security gating); the validation gate blocks promotion (exit code~1). \textbf{Warning}: failure indicates a quality gap that degrades the specification's usefulness without preventing automation; the gate surfaces it without blocking (exit code~0). The precise severity-to-gate mapping is defined in Section~\ref{sec:severity-and-gate}.

% ----------------------------------------------------------------------------
\subsection{Validation as Parallel Application and Aggregation}
\label{subsec:fp-formalism}
% ----------------------------------------------------------------------------

Before describing the principles individually, we fix the formal model that governs how they combine: parallel application over the same input, not function composition.

Let $s$ denote an API specification (an OpenAPI~3.x or Swagger~2.0 document, normalised through the abstraction layer of Section~\ref{sec:spec-abstraction}), and let $f_{p_i}$ denote the principle-specific validation function mapping the specification to a structured \texttt{PrincipleResult}. A \textit{validation policy} $f_p$ is determined by a subset of principles $\{p_1, \dots, p_n\}$ selected by the validation mode (Section~\ref{sec:validation-modes}). The policy is realised as
\[
  f_p(s) \;=\; \mathrm{agg}\bigl(f_{p_1}(s),\, f_{p_2}(s),\, \dots,\, f_{p_n}(s)\bigr),
\]
where $\mathrm{agg}$ is the deterministic aggregation function that assembles the per-principle results into the structured validation report (Section~\ref{sec:report-generation}). Each principle function receives the \emph{same} specification $s$ as input; no principle consumes the output of another.

This is \textit{not} function composition: there is no chain $f_{p_n} \circ f_{p_{n-1}} \circ \dots \circ f_{p_1}$. Three consequences follow directly from this choice.

\textit{Determinism is preserved by construction.} Each $f_{p_i}$ is atomic and side-effect-free: it reads only $s$ and writes only its own \texttt{PrincipleResult}, with no shared mutable state, ordering effect, or cross-principle data flow. The aggregation function consumes the set of per-principle outputs $\{f_{p_i}(s)\}_{i=1}^{n}$ under a fixed canonical ordering by principle identifier, so any permutation of the per-principle calls produces the same report---satisfying the Axiom of Determinism by construction rather than by convention.

\textit{Validation modes are modular subsets, not modified pipelines.} Each validation mode (\texttt{minimal}, \texttt{strict}, \texttt{test-ready}, \texttt{test-only}) corresponds to a subset of the principle index set, not to a reordering or transformation of a fixed pipeline (Section~\ref{sec:validation-modes}). Adding a new principle registers an additional $f_{p_{n+1}}$ without disturbing the principles that preceded it; restricting a mode drops an index from its subset. Composition, by contrast, would force modes to encode evaluation order and partial-failure truncation semantics.

\textit{Principles can be evaluated concurrently without coordination.} Because no $f_{p_i}$ reads any other principle's output, the formalism permits parallel, sequential, or distributed evaluation; the current implementation runs them sequentially for operational simplicity (Section~\ref{sec:engine}) without affecting $f_p(s)$.

The aggregation function $\mathrm{agg}$ introduces no decisions of its own beyond canonical ordering and summary counting; the report structure it produces is described in Section~\ref{sec:report-generation}. This formal commitment is what makes validation a deterministic ``sensor'' in the control-theoretic framing of Chapter~\ref{ch:workflow} (Section~\ref{sec:control-loop}) and the SDT report a stable feedback signal for autonomous agents (Chapter~\ref{ch:ai-development}).

\textit{Mode coverage.} Each principle entry below carries a \textbf{Mode behaviour} note naming the static modes (Section~\ref{sec:validation-modes}) in which it runs: \emph{Mode-uniform} when the check set is identical in every mode in which the principle runs, \emph{Mode-specific} (with the exact per-mode subset) when it differs, plus an explicit statement when a mode skips the principle. The mode--check matrix is thus explicit at the principle level, not only in Table~\ref{tab:validation-modes}.

\subsection{P001: OpenAPI Specification Compliance}
\label{subsec:p001}
% ----------------------------------------------------------------------------

\textbf{Severity:} Critical. \textbf{Status:} Implemented. \textbf{Mode behaviour:} Mode-uniform---P001 applies its identical seven-check set in every static mode (minimal, test-ready, strict).

P001 validates that the API specification conforms to the OpenAPI standard~\cite{openapi} and is structurally sound. A specification that fails P001 cannot be reliably consumed by code generators, documentation renderers, or downstream validators---nor meaningfully assessed by any other principle; P001 is therefore a prerequisite for all other principles and the one principle present in every mode.

P001 performs seven checks: (1)~the specification version is present and valid; (2)~required info fields (title, version) exist; (3)~at least one path is defined; (4)~components are structurally valid; (5)~the overall specification structure passes validation via the \texttt{APISpec.ValidateStructure()} adapter method, which delegates to the underlying parser's schema validator; (6)~no duplicate \texttt{operationId} values exist across operations; and (7)~all HTTP methods used are standard (GET, POST, PUT, DELETE, PATCH, HEAD, OPTIONS, TRACE). For OpenAPI~3.x specifications, the structural check~(5) additionally verifies null type semantics: OpenAPI~3.1.0 permits \texttt{type: ``null''} directly, whereas OpenAPI~3.0.x requires the nullable keyword---a specification that uses the wrong null representation for its declared version fails the structural check.

\subsection{P002: API Documentation Quality}
\label{subsec:p002}
% ----------------------------------------------------------------------------

\textbf{Severity:} Critical. \textbf{Status:} Implemented. \textbf{Mode behaviour:} Mode-specific---\textit{strict} mode performs all ten checks below; \textit{test-ready} mode performs the test-critical subset (operation summaries, descriptions, and \texttt{operationId}s; parameter descriptions; request/response examples; schema and enum descriptions), skipping the contact and license checks; not evaluated in minimal mode.

\textit{Severity escalation note.} P002 was originally classified as \textbf{Warning} on the rationale that incomplete documentation degrades a specification's usefulness without strictly preventing automation. Operational evidence from the controlled and large-scale evaluations (Chapter~\ref{ch:evaluation}) reversed this judgement: specifications missing operation summaries, parameter descriptions, schema descriptions, or response examples systematically prevent downstream agents and code generators from producing usable artefacts, and missing examples cascade into the runtime principles---without them, the functional and performance pipelines (P006, P007) can only synthesize input data, reintroducing exactly the non-determinism the framework forbids. The principle was escalated to \textbf{Critical} in the source code (commit \texttt{c96d9c7}, ``Make P002/P003/P004 critical''); the severity stated here reflects those source-of-truth constants, and the same escalation applies to P003 and P004 below for parallel reasons. The escalation has a load-bearing empirical consequence: 84\% of public APIs in the APIs.guru sample now block at the static layer rather than degrade gracefully (Chapter~\ref{ch:evaluation})---the quantitative form of the systemic specification-quality gap that motivates the framework. Strict mode is therefore a true quality gate rather than an advisory layer; teams needing a non-blocking baseline use minimal or test-ready mode (Section~\ref{sec:validation-modes}).

P002 assesses whether the specification serves as effective documentation: a specification can be structurally valid (passing P001) yet practically useless, with endpoints lacking descriptions and schemas lacking examples.

P002 performs ten checks across three scopes. At the \textit{API level}: (1)~the API has a general description; (2)~contact information is provided; (3)~license information is specified. At the \textit{operation level}: (4)~all operations have summaries; (5)~all operations have detailed descriptions; (6)~all operations have unique \texttt{operationId} values; (7)~all parameters have descriptions; (8)~all request and response bodies include examples. At the \textit{schema level}: (9)~all component schemas have descriptions; (10)~all enum values are documented within their schema descriptions.

P002 addresses a gap identified in Chapter~\ref{ch:related-work}: existing linters verify specification \textit{form}, whereas P002 systematically verifies documentation \textit{substance}---that every element a consumer interacts with is documented.

\subsection{P003: Error Handling Standards}
\label{subsec:p003}
% ----------------------------------------------------------------------------

\textbf{Severity:} Critical. \textbf{Status:} Implemented. \textbf{Mode behaviour:} Mode-specific---\textit{strict} mode performs all seven checks below; \textit{test-ready} mode performs exactly two: check~(1), 4xx error responses documented, and check~(5), error schemas contain structured fields (\texttt{message}, \texttt{code}, or \texttt{details}), skipping the 5xx, reusable-component, and format-consistency checks. P003 is not evaluated in minimal mode.

P003 validates that the specification documents error responses comprehensively and consistently. Undocumented error responses are a primary source of integration failures: consumers must reverse-engineer unmentioned 403 or 422 responses from raw HTTP traffic.

In strict mode, P003 performs seven comprehensive checks: (1)~all operations document at least one 4xx error response; (2)~all operations document at least one 5xx error response; (3)~error responses include descriptive error codes (via non-empty descriptions); (4)~error responses include error messages; (5)~error response schemas contain structured fields (\texttt{message}, \texttt{code}, or \texttt{details} properties); (6)~common error responses (400, 401, 403, 404, 500) are defined as reusable components in \texttt{components.responses}; and (7)~error response formats are consistent across operations (all errors share the same schema property structure).

The consistency check~(7) is particularly valuable: APIs that return \texttt{\{``message'': ...\}} for 400 errors but \texttt{\{``error'': ..., ``code'': ...\}} for 500 errors impose unnecessary complexity on consumers, so the implementation flags any specification where more than one distinct error-schema property structure appears.

\textit{Uniformity vs completeness.} Check~(7) raises a sharper conceptual question: is the consistency it enforces a property of \emph{completeness} (the specification's coverage of error formats is incomplete because it omits a uniform-format declaration), or a distinct property of \emph{uniformity} that should arguably be a fourth axiom? The framework currently folds it into completeness on the grounds that a multi-format specification is missing the meta-information ``which format applies to which class of error''---i.e.\ the heterogeneity is a completeness gap at the meta-level. We acknowledge that an explicit \emph{Axiom of Uniformity}, governing format consistency across operations, schemas, and error responses, would sharpen the framework's vocabulary; the question of whether to introduce it is recorded as a candidate refinement in Chapter~\ref{ch:conclusion} alongside the precision/accuracy axiom.

\subsection{P004: Schema Definitions}
\label{subsec:p004}
% ----------------------------------------------------------------------------

\textbf{Severity:} Critical. \textbf{Status:} Implemented. \textbf{Mode behaviour:} Mode-specific---\textit{test-ready} mode checks schema existence plus type specifications (every schema and property must declare a type) without enforcing constraints, so that test-data generators can produce typed values; \textit{strict} mode performs all ten checks below. P004 is not evaluated in minimal mode.

P004 validates that request and response schemas are precise, constrained, and complete---not merely present but informative. A schema declaring a field as type \texttt{string} without length, pattern, or format constraints provides the consumer with no useful validation guidance.

In strict mode, P004 performs ten comprehensive checks: (1)~all path parameters have schemas; (2)~all query parameters have schemas; (3)~all header parameters have schemas; (4)~all request bodies have content schemas; (5)~all schemas specify data types; (6)~all schemas have appropriate constraints; (7)~all required fields listed in \texttt{required} arrays exist in \texttt{properties}; (8)~all enum values are non-null; (9)~all numeric fields have range constraints (\texttt{minimum}, \texttt{maximum}); and (10)~all string fields have length constraints (\texttt{minLength}, \texttt{maxLength}) or pattern restrictions.

All checks are applied recursively through the schema tree, including nested object properties and array items---a top-level object may be well-defined while a nested field is typed as a bare \texttt{object} with no properties. This aligns with the JSON Schema specification's~\cite{json-schema-2020} principle that schemas should be as restrictive as the domain permits.

\subsection{P005: Security Standards}
\label{subsec:p005}
% ----------------------------------------------------------------------------

\textbf{Severity:} Critical. \textbf{Status:} Implemented. \textbf{Mode behaviour:} P005 is evaluated only in \textit{strict} mode, where it performs all seven checks below. Its exclusion from minimal and test-ready is a deliberate design decision: test-readiness asks whether meaningful test data can be derived from the specification, and authentication is exercised at the runtime layer rather than as a precondition for test generation.

P005 validates that the specification defines security mechanisms comprehensively and consistently. Security misconfigurations in API specifications---missing authentication requirements, undefined schemes, inconsistent enforcement---are among the top risks identified by the OWASP API Security project~\cite{owasp-api-security}, and their omission leaves consumers guessing and automated tools unable to verify compliance~\cite{api-security-testing}.

P005 performs seven checks: (1)~at least one security scheme is defined in \texttt{components.securitySchemes}; (2)~global security requirements are set at the top level; (3)~all operations are covered by either global or operation-level security (operations inherit global security when no operation-level security is declared); (4)~OAuth2 and OpenID Connect schemes are referenced with scopes in at least one security requirement; (5)~API key schemes include descriptions; (6)~API key schemes specify the \texttt{name} and \texttt{in} fields (header, query, or cookie location); and (7)~all security scheme names referenced in security requirements are defined in components.

Check~(7) addresses a subtle but dangerous inconsistency: a security requirement referencing a scheme name absent from \texttt{components.\allowbreak securitySchemes} appears to enforce security whose enforcement is undefined; P005 scans both global and per-operation requirements for such phantom references.

\textit{Intentionally public APIs.} P005 applies even to a deliberately public API, but the obligation it imposes is \emph{declaration}, not protection. OpenAPI distinguishes an operation that explicitly declares it requires no authentication (an empty security requirement, \texttt{security: []}) from one whose specification is simply silent: the former documents a design decision that consumers and validators can rely on; the latter leaves authentication undefined. P005 findings on a public API are therefore resolved by declaring the public posture explicitly, not by adding authentication the API does not need.

\subsection{P006: Functional Testing}
\label{subsec:p006}
% ----------------------------------------------------------------------------

\textbf{Severity:} Critical. \textbf{Status:} Defined theoretically; implementation as a \texttt{PrincipleChecker} wrapper is pending. \textbf{Mode behaviour:} Runtime principle---exercised by \textit{test-only} mode through the functional-testing pipeline (and the \texttt{functional-test} gate check type), not by any static mode.

P006 validates that the API's runtime behaviour matches the specification; unlike the static principles, it requires a live API instance. It derives test cases from the specification---HTTP requests with appropriate parameters, headers, and bodies---and verifies that responses conform to the declared schemas, status codes, and content types.

The DriveBy framework already implements the underlying functional testing logic (Chapter~\ref{ch:architecture}); the pending work is integrating it into the unified principle evaluation pipeline so that it contributes to the structured validation report.

P006 operationalizes the Axiom of Determinism: given the same specification and the same API, functional tests must produce the same pass/fail results. This requires that test inputs are derived deterministically from the specification rather than generated randomly (distinguishing SDT's functional testing from property-based approaches like Schemathesis~\cite{schemathesis}). Deterministic derivation relies in practice on declared example data: parameter and request-body examples let the test generator produce the same typed, valid inputs on every run---precisely the precondition that P009 (Section~\ref{subsec:p009}) verifies before runtime testing begins. Two operational consequences follow. First, example values flow into test requests and validation reports, so authors must not embed real or sensitive data in examples; the framework assumes this synthetic-data discipline rather than enforcing it. Second, authentication credentials are deliberately \emph{not} derived from example data: they are supplied as operational configuration (Chapter~\ref{ch:workflow}), keeping secrets out of both the specification and the structured report.

\textit{Assertion scope.} P006 asserts \emph{contract conformance}---status codes, response schema shape, declared types and headers---by design. Semantic correctness of response \emph{content} (whether a returned value is the \emph{right} value, not merely well-formed) would require an oracle the specification cannot supply; it is out of P006's scope and recorded as a limitation in Chapter~\ref{ch:conclusion}, with example-derived content assertions scoped as a natural future extension.

% ----------------------------------------------------------------------------
\subsection{P007: Performance Testing}
\label{subsec:p007}
% ----------------------------------------------------------------------------

\textbf{Severity:} Critical. \textbf{Status:} Defined theoretically; implementation as a \texttt{PrincipleChecker} wrapper is pending; the load-test runner that realises it is operational. \textbf{Mode behaviour:} Runtime principle---exercised by \textit{test-only} mode through the load-testing pipeline (and the \texttt{load-test} gate check type), not by any static mode.

P007 validates that the API meets performance expectations by measuring response times, throughput, and error rates under load; like P006, it requires a live API instance. It operationalizes the Axiom of Observability: it produces latency distributions, throughput measurements, and error rate statistics that can be compared against configurable thresholds and tracked longitudinally across API versions.

Performance measurements are environmentally sensitive: the same API under the same load profile yields different raw latencies across runs, so per-sample threshold checks could flip between pass and fail, violating the Determinism axiom in spirit. P007 therefore evaluates its thresholds only over statistically robust aggregates of a sustained run---latency percentiles such as P95 and success-rate ratios---never individual samples. Provisioning a representative environment remains the operator's responsibility: the framework makes measurement and verdict derivation deterministic, but cannot make under-provisioned or noisy infrastructure behave deterministically.

The pending work mirrors P006: integrating the existing performance testing logic into the unified principle evaluation pipeline.

\subsection{P008: API Versioning Strategy}
\label{subsec:p008}
% ----------------------------------------------------------------------------

\textbf{Severity:} Warning. \textbf{Status:} Implemented. \textbf{Mode behaviour:} P008 is evaluated only in \textit{strict} mode, performing all seven checks below; minimal and test-ready skip it (versioning discipline does not affect whether meaningful tests can be generated).

P008 validates that the API follows a disciplined versioning strategy. APIs evolve; without explicit versioning, deprecation notices, and migration guidance, consumers face silent breaking changes. P008 ensures the specification communicates its version lifecycle clearly, following the Semantic Versioning convention~\cite{semver}.

P008 performs seven checks: (1)~the API version is specified in the info section; (2)~the version follows Semantic Versioning format (MAJOR.MINOR.PATCH), validated via the regular expression \texttt{\textasciicircum\textbackslash d+\textbackslash.\textbackslash d+\textbackslash.\textbackslash d+\$}; (3)~the versioning strategy is documented in the API description (detected by keyword match for ``version''); (4)~deprecated operations include deprecation details in their descriptions (operations marked \texttt{deprecated: true} must contain the word ``deprecat'' in their description); (5)~breaking changes are documented or a changelog is referenced; (6)~version compatibility (backward compatibility) is addressed; and (7)~migration or upgrade guides are referenced.

Checks (3)--(7) are distinctive: where most tools verify only that a version string exists and follows semver, P008 requires that the specification communicates its \textit{versioning practices}---transitions, changes, and migration guidance---by scanning \texttt{info.description} for relevant keywords, transforming the version field from a static label into a living contract about the API's evolution.

% ----------------------------------------------------------------------------
\subsection{P009: Test Readiness}
\label{subsec:p009}
% ----------------------------------------------------------------------------

\textbf{Severity:} Warning. \textbf{Status:} Implemented. \textbf{Mode behaviour:} Mode-uniform---P009 runs in \textit{test-ready} mode (its four checks are the core of that mode's verdict) and performs the identical check set whenever it is evaluated.

P009 validates that a specification provides sufficient detail for meaningful functional and load testing: without adequate examples, typed schemas, and response definitions, automated test generators fall back to generic placeholder values that real API validation logic rejects, producing false failures.

P009 performs four checks:
\begin{enumerate}
  \item \textit{Path parameters have examples or typed schemas.} Without an example or a typed schema, parameter substitution falls back to untyped strings (\texttt{"test-value"}) that fail server-side validation for integer, UUID, or enum parameters.
  \item \textit{Request bodies have examples or typed schema properties.} The functional tester's request body builder prioritises explicit examples, then falls back to schema-based generation. The fallback is itself a determinism risk: values must be synthesized purely from the schema (fixed representative values per declared type), never sampled randomly---one reason P009 flags missing examples, steering specifications toward trivially deterministic test derivation. If neither is available, generated payloads are rejected by any API with input validation.
  \item \textit{2xx responses have schemas defined.} Without response schemas, functional tests degrade to status-code-only checks with no response body validation.
  \item \textit{2xx responses have examples defined.} Advisory \emph{within} P009: a miss is surfaced as a finding but does not by itself fail the principle---a status distinct from P009's principle-level Warning severity, which governs the gate mapping (Section~\ref{sec:severity-and-gate}). Response examples improve test reporting but are not required for the contract-conformance testing P006 performs; they would become necessary only for content-level assertions, which are outside P006's scope (Section~\ref{subsec:p006}).
\end{enumerate}

P009 thus secures the preconditions for deterministic test execution: generated test data is typed and meaningful rather than dependent on arbitrary fallback heuristics.

\textit{Why a principle and not a mode.} Is P009 redundant---with the test-ready \emph{mode}, or with P001 plus partial P002--P004? No, for three reasons. First, modes and principles are different categories: a mode is a \emph{selection} of principles, a principle a measurable property with its own verdict. Test-ready mode is the set $\{$P001, P002, P003, P004 (reduced check sets), P009$\}$; without P009 as a principle, the mode's defining question---can meaningful test data be derived from this specification?---would have no dedicated, reportable verdict. Second, P009's checks are \emph{disjunctive preconditions} that no other principle expresses: P002 asks the documentation question ``do all request and response bodies have examples?'', P009 the strictly weaker test-derivability question ``does every parameter and body have an example \emph{or} a typed schema?''---the minimal condition for typed, valid test data instead of untyped fallbacks. A specification with no examples but fully typed schemas \emph{fails} P002 yet \emph{passes} P009---precisely the case in which functional testing is still meaningful---and the reduced P002--P004 check sets, being conjunctive, cannot express this disjunction. Third, keeping P009 a principle preserves composability: any future mode or gate can include the test-derivability verdict without re-deriving it from fragments of other principles.

The severity classification---critical versus warning---governs how validation results translate to quality gate decisions through a deterministic exit code mechanism: if any principle with \texttt{severity: critical} has \texttt{Passed: false}, the overall report status is \texttt{``failed''} and the process exits with code~1; if only warning-severity principles fail, the status remains \texttt{``passed''} with exit code~0. This binary mapping is the mechanism by which SDT integrates with CI/CD quality gates.

The severity assignment reflects a core SDT design principle: \textit{static validation gates runtime testing}---functional (P006) and performance (P007) alike, since load profiles, like functional probes, are derived from the documented operations and payloads. The completeness-of-contract principles (P001--P005) are all critical because an incomplete specification cannot produce meaningful test results from either runtime principle: without examples and descriptions (P002) generated request data is rejected as false failures, without documented error schemas (P003) negative assertions cannot verify error shapes, without typed schemas (P004) generators fall back on placeholders that fail server-side validation, and misconfigured authentication (P005) blocks all endpoint access. Only versioning (P008) and test readiness advisory checks (P009) remain at warning severity---quality dimensions that degrade gracefully rather than preventing test execution entirely.

\textbf{Minimal mode} evaluates only P001 (OpenAPI Specification Compliance): a fast baseline gate for pull request pipelines where rapid feedback is prioritised. A specification that passes is structurally valid and safe for code generation, but its documentation quality, error handling, and security definitions are unchecked.

\textbf{Strict mode} evaluates P001 through P005 and P008---all implemented static principles---providing comprehensive specification quality assessment without a live API instance. One might expect strict mode to include every principle except P009; the boundary is deliberate: strict mode is the portion of a pre-merge gate that runs on the specification alone, and a full gate adds the dynamic test-only stage once a deployed environment is available. Strict mode suits release pipelines, the static half of pre-merge gates, and periodic audits.

\textbf{Test-only mode} skips all static validation: the principle registry returns no checkers, and the runtime testing pipeline---functional endpoint testing and load testing---runs directly against a live API instance (operational via the \texttt{function-only} and \texttt{load-only} CLI commands, pending the P006/P007 wrappers noted in Table~\ref{tab:validation-modes}). It serves scenarios where the specification has already been validated statically, decoupling static and runtime validation into separate pipeline stages.

\textbf{Test-ready mode} evaluates P001, P009, and the reduced check sets of P002--P004 (Table~\ref{tab:validation-modes} footnotes). It is a fast pre-flight check answering: \textit{is this specification good enough to produce meaningful test results?} Without it, functional tests send placeholder values that are rejected by API validation, and load tests run for minutes before revealing that the specification was incomplete; test-ready mode runs in seconds and gates whether testing is worth executing.

The four modes map onto the standard cost-increasing sequence of organisational quality gates: \textit{minimal} as a fast gate on every commit, \textit{test-ready} as a pre-flight gate before functional testing pipelines, and \textit{strict} as the static half of a pre-merge gate. \textit{Test-only} maps onto a pre-merge, post-merge, or release gate depending on environment availability: functional tests need a running instance of the changed API (pre-merge where ephemeral preview environments are cheap, post-merge or release where only shared staging exists), while load tests, the most expensive stage, typically gate release promotion.

\section{Summary}
\label{sec:methodology-summary}
% ============================================================================

This chapter defined SDT as a two-layer conceptual framework: three axioms---Completeness, Determinism, and Observability---and nine validation principles derived from them, applied under four validation modes that enable incremental adoption. What is presented here is the theoretical core for a future formal methodology, whose remaining elements are scoped as future work in Chapter~\ref{ch:conclusion}. Chapter~\ref{ch:architecture} describes how the DriveBy framework implements these definitions.
