\chapter{GitOps Pipeline and CI/CD}
\label{ch:workflow}

Chapter~\ref{ch:kubernetes} described the Kubernetes infrastructure---Crossplane XRDs, Argo Events, Argo Workflows---that implements the quality gate system. This chapter describes how that infrastructure operates within the broader GitOps pipeline: the promotion-driven quality gate flow, the two-repo architecture and its ``Bring Your Own CI'' (BYOCI) design principle, multi-environment promotion, human-in-the-loop decision patterns, the quality gate as a closed-loop control system, and the automated release of DriveBy itself.

This chapter realises the outermost layer of the three-layer model (Section~\ref{sec:three-layer-model})---the point where validation results become operational signals that advance or block software delivery.

The chapter addresses Research Question~3 (RQ3): \textit{How effectively does specification-driven quality assurance integrate into cloud-native GitOps pipelines, and can a single declarative custom resource replace the manual provisioning of quality gate infrastructure?} The answer is demonstrated through a proof-of-concept deployment on the \texttt{private.novelcore.org} cluster, where DriveBy validates five evaluation APIs across three environments.

% ============================================================================
\section{Promotion-Driven Quality Gate}
\label{sec:promotion-driven-gate}
% ============================================================================

The quality gate operates on a key insight: \textit{validate the source environment, not the target}. The developer's own CI builds a new container image (the BYOCI boundary described in Section~\ref{subsec:byoci}), then commits the updated dry manifests and image tag to the \texttt{main} branch of the dedicated gitops repository. The ArgoCD Source Hydrator~\cite{argocd-hydrator} renders each environment's Kustomize overlay and writes hydrated output to the corresponding \texttt{-next} branch. The GitOps Promoter creates a promotion PR from the \texttt{-next} branch to the active branch, and ArgoCD~\cite{argocd} synchronises the environment once the PR is merged.

This promotion PR triggers the quality gate. The GitHub webhook fires, the EventSource receives the event, the Sensor filters for PR actions, and the Workflow executes validation against the \textit{source} (development) environment---the environment where the new code is already running. The validation results determine whether the promotion PR is approved (merged) or blocked (left open with a failure status).

This inversion is deliberate. Validating the source environment ensures that quality is assessed against the actual deployment rather than a hypothetical future state. If the API in development passes strict SDT validation, the same code deployed to staging will behave identically (assuming equivalent infrastructure). The alternative---validating the target environment after promotion---would detect problems only after the potentially breaking change has already been deployed, violating the shift-left principle~\cite{shift-left}.

Figure~\ref{fig:gitops-pipeline} shows the end-to-end pipeline from deploy trigger to validation feedback.

\section{Event-Driven Validation Pipeline}
\label{sec:event-pipeline-detail}
% ============================================================================

The event-driven pipeline transforms an external webhook into a structured validation workflow. Its components---EventSource, EventBus, Sensor, and the generated Ingress and webhook configuration---are described in Chapter~\ref{ch:kubernetes}; this section covers only their pipeline-level behaviour and latency.

% ----------------------------------------------------------------------------
\subsection{Webhook Delivery and Event Processing}
\label{subsec:webhook-delivery}
\label{subsec:event-processing}
% ----------------------------------------------------------------------------

Webhook routing is convention-over-configuration: the composition derives the GitHub webhook URL (\texttt{https://\{app\}-\{gate\}-webhook.\allowbreak\{domain\}/\allowbreak\{app\}-\{gate\}-\allowbreak pr-trigger}), the Ingress that exposes it, and the EventSource endpoint from the same two identity fields, so they agree without manual coordination (Section~\ref{subsec:k8s-design-goals}, Chapter~\ref{ch:kubernetes}). The Sensor filters for \texttt{pull\_request} events with action \texttt{opened}, \texttt{reopened}, or \texttt{synchronize}, extracts ten parameters via JSONPath (Table~\ref{tab:sensor-params} of Chapter~\ref{ch:kubernetes}), and submits the generated WorkflowTemplate with those parameters as arguments.

% ----------------------------------------------------------------------------
\subsection{Latency Analysis}
\label{subsec:latency}
% ----------------------------------------------------------------------------

The end-to-end latency from webhook delivery to workflow completion depends on three factors: event processing overhead (typically under 2~seconds for EventSource $\rightarrow$ EventBus $\rightarrow$ Sensor $\rightarrow$ workflow submission), source readiness wait (0--120~seconds, depending on whether the deployment is already healthy), and validation execution time (10--60~seconds, depending on specification size, validation mode, and check type---static, functional, or load). In practice, the validation step itself completes in 10--30~seconds: the five-API evaluation (Section~\ref{sec:multi-api-eval}) measured 10--12~seconds for gates with static validation only and 18--28~seconds for gates that include functional or load testing. End-to-end---from PR creation to commit status posted---the proof-of-concept runs show 40--70~seconds as the typical range with a median of 69~seconds (Section~\ref{sec:cicd-metrics}), the difference being event-processing overhead and the source-readiness wait; gates whose source environment is unreachable take approximately 5~minutes (the health check retries for 60 attempts at 5-second intervals before timing out).

\section{Two-Repo Architecture}
\label{sec:two-repo}
% ============================================================================

The quality gate system operates within a \textit{two-repository} model: the software repository is entirely developer-owned and untouched by XSDLC, while a dedicated GitOps repository---auto-created by the XSDLC composition---holds Kubernetes manifests on per-environment branches.

% ----------------------------------------------------------------------------
\subsection{Why a Dedicated GitOps Repository}
\label{subsec:why-two-repo}
% ----------------------------------------------------------------------------

Traditional GitOps deployments face a tension between two concerns: the developer wants to keep manifests close to the source code for co-evolution, while the platform needs a clean Git-based state store that ArgoCD can watch without being polluted by source code history, CI artefacts, or unrelated commits. Single-repo models conflate these concerns: every source commit appears in the ArgoCD diff view, and manifest-only environment branches create divergent histories in a repository whose \texttt{main} branch carries application source.

The XSDLC v3.0.0 model resolves this tension by separating the two concerns into two repositories. The software repository remains untouched; XSDLC auto-creates a dedicated GitOps repository per application that holds dry Kustomize manifests on the \texttt{main} branch and hydrated output on per-environment branches (the layout below uses the reference application's historical source identifier \texttt{perfect-api}; see the naming note in Chapter~\ref{ch:kubernetes}):

{\footnotesize
\begin{verbatim}
perfect-api/                    # Software repository (untouched)
  src/                          # Application source
  Dockerfile                    # Build specification

perfect-api-gitops/             # GitOps repository (auto-created)
  main branch:
    dry/
      base/                     # Shared manifests
        kustomization.yaml      # refs deployment.yaml + service.yaml
        deployment.yaml
        service.yaml
      overlays/                 # Per-environment customization
        {dev,staging,prod}/kustomization.yaml

  environment/<env>-next     -> # ArgoCD-hydrated (per env)
  environment/<env>          -> # Promoter merges (gate passed)
\end{verbatim}
}

The GitOps repository's \texttt{main} branch holds dry Kustomize manifests organised as a base-plus-overlays structure. Each environment has its own overlay that references the shared base and can customize deployment parameters (replicas, resource limits, environment variables, image tags). The ArgoCD Source Hydrator~\cite{argocd-hydrator} renders each overlay independently and writes the hydrated output---along with a \texttt{hydrator.metadata} file containing the dry commit SHA---to the corresponding \texttt{environment/<name>-next} branch. The GitOps Promoter detects the new commit and creates a promotion PR from the \texttt{-next} branch to the active branch. Quality gates fire on these PRs; ArgoCD syncs from the active branch once the PR is merged.

Per-environment branches and their corresponding \texttt{-next} branches are created by the XSDLC composition via \texttt{provider-upjet-github}. The software repository is never modified---no workflows generated, no files committed, no branches created---so XSDLC can be adopted without any changes to the developer's existing repository structure, CI configuration, or branching strategy. Because each environment hydrates independently from \texttt{main}, deploying to a specific environment requires only updating its overlay---there is no requirement to propagate changes through earlier environments first.

% ----------------------------------------------------------------------------
\subsection{Bring Your Own CI (BYOCI)}
\label{subsec:byoci}
% ----------------------------------------------------------------------------

The two-repo model embodies a deliberate design principle: \textbf{XSDLC owns delivery, not CI}. The boundary is explicit: \textit{XSDLC's responsibility begins when dry manifests are committed to the \texttt{main} branch of the GitOps repository}.

Everything \textit{before} that point is the developer's responsibility: building the application, running unit tests, generating the container image, and updating dry manifests on the \texttt{main} branch. These tasks are inherently application-specific---a Python FastAPI service uses different build tools, test frameworks, and container patterns than a Go gRPC service. XSDLC does not generate workflows, provide build templates, or prescribe how dry manifests are authored; the developer can use GitHub Actions, GitLab CI, Jenkins, a shell script, or a manual \texttt{git push}.

Everything \textit{after} the commit is XSDLC's responsibility: hydration, promotion PRs, source-environment validation, commit-status-gated merges, and ArgoCD sync. These tasks are platform-generic---the same pattern applies regardless of the application's language, framework, or build tool.

This separation contrasts with opinionated CD platforms (Tekton Pipelines, Jenkins X) that attempt to own the full CI/CD lifecycle. Such platforms trade flexibility for integration: they work well when the application fits their model and poorly when it does not. XSDLC is composable rather than monolithic---it integrates with any CI system that can commit manifests to a Git branch.

% ----------------------------------------------------------------------------
\subsection{Manifest Delivery}
\label{subsec:manifest-delivery}
% ----------------------------------------------------------------------------

The quality gate pipeline is triggered by a single primitive: \textit{a commit to the \texttt{main} branch of the GitOps repository that modifies dry manifests}. This is the entire integration contract between the developer's CI and the XSDLC delivery platform. The developer edits the shared base (\texttt{dry/base/}) for cross-environment changes or a specific overlay (\texttt{dry/overlays/<env>/}) for environment-specific customization. Releasing a new version to staging, for example, is a one-line edit setting \texttt{newTag:\ v1.4.2} in \texttt{dry/overlays/staging/kustomization.yaml}; the hydrator re-renders only the staging overlay to \texttt{environment/staging-next}, opening a gated staging promotion PR while the other environments are untouched. The developer never creates environment branches, overlay directories, promotion PRs, ArgoCD Applications, or quality gate infrastructure---the \texttt{XSDLC} custom resource provisions all of these.

\section{Multi-Environment Promotion}
\label{sec:multi-env-promotion}
% ============================================================================

The GitOps Promoter~\cite{gitops-promoter} automates environment promotion by watching for commit status signals and managing promotion pull requests. Figure~\ref{fig:multi-env-promotion} shows the three-environment model.

\begin{figure}[htbp]
\centering
\resizebox{\textwidth}{!}{%
\input{figures/multi-env-promotion.tex}%
}
\caption{Multi-environment promotion model. Development auto-syncs; staging promotion is gated by SDT validation (commit status); production requires manual approval.}
\label{fig:multi-env-promotion}
\end{figure}

The dev~$\rightarrow$~staging~$\rightarrow$~prod chain in Figure~\ref{fig:multi-env-promotion} is an \textit{ordering} over environments, not a propagation path: no hydrated manifest ever moves from the staging branch to the production branch. Each environment hydrates independently from the dry manifests on \texttt{main} (Section~\ref{subsec:why-two-repo}), and every transition merges that environment's own \texttt{-next} branch under that environment's own gate. A change touching only the staging overlay therefore cannot reach production---production's hydrated output is unchanged, so no production promotion PR is created. A change reaches production only by altering production's own hydrated output (via the shared base or the production overlay), and then only through production's gated, manually approved promotion PR.

% ----------------------------------------------------------------------------
\subsection{PromotionStrategy Generation}
\label{subsec:promotion-strategy}
% ----------------------------------------------------------------------------

The PromotionStrategy is not authored manually. The XSDLC composition generates it declaratively from the \texttt{environments[]} array in the XRD spec. Each environment entry produces a corresponding element in the PromotionStrategy's environment chain, with three derived fields computed automatically:

\begin{itemize}
    \item \textbf{Branch}: defaults to \texttt{environment/<name>} but overridable per environment via \texttt{branch}.
    \item \textbf{autoMerge}: defaults to \texttt{true}; set to \texttt{false} on any environment that requires human approval before promotion.
    \item \textbf{commitStatusKey}: defaults to \texttt{<envName>-gate}; overridable via \texttt{gate.\allowbreak commitStatusKey}. The key must match between the PromotionStrategy (which watches for it) and the Argo Workflow (which posts it).
\end{itemize}

The generation model is environment-count agnostic, producing a PromotionStrategy with \textit{N} environments for any \textit{N} $\geq$ 2 (the composition mechanics are described in Chapter~\ref{ch:kubernetes}).

The key design property is \textit{per-environment composability}. Each environment independently controls three dimensions: \textit{whether} a gate exists (\texttt{gate} presence), \textit{what} the gate checks (\texttt{gate.checks[]} array), and \textit{how} promotion proceeds after the gate passes (\texttt{autoMerge}). A team can run static validation on staging and load testing on production, or functional tests on both, or no gate on any environment---all without modifying the underlying Crossplane composition or Helm chart.

% ----------------------------------------------------------------------------
\subsection{CommitStatus as Quality Signal}
\label{subsec:commit-status-signal}
% ----------------------------------------------------------------------------

The integration between DriveBy and the GitOps Promoter is mediated by two commit status mechanisms:

\textbf{GitHub commit status.} The workflow's set-pending and report-success steps post commit status updates to the PR's head SHA via the GitHub API. The context key (e.g.\ \texttt{staging-gate}) is watched by the PromotionStrategy as the gate signal. This mechanism works for any GitHub-based workflow and does not require the GitOps Promoter.

\textbf{CommitStatus CRD.} When the GitOps Promoter is enabled, the workflow additionally creates a CommitStatus custom resource in the \texttt{driveby} namespace. The CommitStatus transitions through three phases: \texttt{pending} (set at workflow start), \texttt{success} (set after validation passes), or \texttt{failure} (set by the exit handler). The Promoter controller watches this resource and uses its phase to determine whether to merge the promotion PR. This CRD-based mechanism provides a Kubernetes-native alternative to the GitHub API and enables the Promoter to function even in environments where direct GitHub API access is restricted.

% ----------------------------------------------------------------------------
\subsection{ChangeTransferPolicy}
\label{subsec:change-transfer-policy}
% ----------------------------------------------------------------------------

The ChangeTransferPolicy defines how changes flow between environments at the Git level. For each environment, the policy maps a \textit{proposed} branch (e.g.\ \texttt{staging-next}) to an \textit{active} branch (e.g.\ \texttt{staging}). The Promoter creates pull requests from the proposed branch to the active branch and merges them when commit status gates pass. This branch-based model integrates naturally with Git-based review workflows: promotion PRs appear in the repository's PR list, carry commit status checks, and leave an auditable merge history.

% ----------------------------------------------------------------------------
\subsection{Promoter Reconciliation Loop}
\label{subsec:promoter-reconciliation}
% ----------------------------------------------------------------------------

The GitOps Promoter is itself a Kubernetes controller that implements the observe-diff-act pattern (Section~\ref{subsec:reconciliation-loop}) at the Git level rather than the cluster level. It \textit{observes} GitRepository and CommitStatus resources; it \textit{diffs} each proposed branch (\texttt{environment/<name>-next}) against its active branch and checks whether all required CommitStatuses report \texttt{success}; and it \textit{acts} by creating a promotion PR when the branches differ, merging it when all gates pass and \texttt{autoMerge} is \texttt{true}, and leaving it open for human review otherwise. Any \texttt{failure} or \texttt{pending} CommitStatus blocks the promotion.

The ChangeTransferPolicy is itself a second reconciliation layer: it is auto-created by the PromotionStrategy controller when the PromotionStrategy is applied. The PromotionStrategy reconciles the \textit{promotion logic} (which environments exist, what gates are required); the ChangeTransferPolicy reconciles the \textit{branch mechanics} (which branches map to which environments, when to create PRs). This two-layer design separates strategic configuration (the promotion chain) from tactical execution (the branch operations).

\section{Human-in-the-Loop Patterns}
\label{sec:human-in-the-loop}
% ============================================================================

The quality gate system is not fully autonomous. It automates objective assessments---SDT validation, health checks, load testing---while preserving human judgment for subjective assessments. This section maps the automation spectrum and identifies the decision points where human intervention is required or optional.

% ----------------------------------------------------------------------------
\subsection{The Automation Spectrum}
\label{subsec:automation-spectrum}
% ----------------------------------------------------------------------------

The system supports four points on the automation spectrum, controlled by two boolean parameters: \texttt{autoMerge} (on the PromotionStrategy, controlling whether the Promoter automatically merges promotion PRs) and \texttt{automated.selfHeal} (on the ArgoCD Application, controlling whether ArgoCD automatically syncs and self-heals).

\begin{enumerate}
    \item \textbf{Fully automated} (development): \texttt{autoMerge: true}, automated sync. After the developer triggers a deploy, changes flow from the \texttt{-next} branch, are auto-merged by the Promoter, and auto-synced by ArgoCD. No further human intervention after the initial trigger.
    \item \textbf{Automated with quality gate} (staging): \texttt{autoMerge: true}, automated sync, with a commit status gate. The Promoter waits for SDT validation to report success before merging. If validation fails, the PR remains open until the developer fixes the issue and re-pushes. Once the gate passes, promotion and sync are automatic.
    \item \textbf{Gated with human approval} (production): \texttt{autoMerge: false}, auto-sync. The Promoter creates the PR and SDT validates the source environment, but a human must explicitly merge the promotion PR. Once merged, ArgoCD auto-syncs the change. The single human checkpoint is the merge decision---ArgoCD always reflects the branch state.
    \item \textbf{Fully manual merge}: no quality gate, manual merge, auto-sync. This mode is unused in the reference deployment---it offers no advantage over the gated model---but suits an exploratory or manual-QA environment, where a tester keeps the promotion PR open while exercising the candidate in the source environment and merges when manual testing is complete. ArgoCD still auto-syncs once the branch is updated.
\end{enumerate}

Figure~\ref{fig:human-in-the-loop} illustrates how these two configurable slots---quality gate and merge policy---compose independently per environment; ArgoCD always auto-syncs, so the sync policy is fixed. Adding a quality gate or switching from auto-merge to manual approval are each single-field changes in the XSDLC spec that affect one slot without impacting the other.

\centering

\caption{Modular automation spectrum. Each environment is a pipeline of four stages with two independently configurable slots: quality gate (\texttt{gate.checks[]}) and merge policy (\texttt{autoMerge}). ArgoCD always auto-syncs. % ----------------------------------------------------------------------------
\subsection{Automation with Human Override}
\label{subsec:automation-override}
% ----------------------------------------------------------------------------

The design philosophy is: \textit{automate objective assessments, preserve human judgment for subjective assessments}. SDT validation, health checks, and load testing produce binary signals (pass/fail) based on measurable criteria. These are objective and automatable. Production readiness, business timing, and release coordination involve context that no automated system can capture. These are subjective and require human judgment.

The \texttt{autoMerge: false} setting is a deliberate architectural choice, not a limitation. It reflects the principle that the final decision to deploy to production should be an affirmative human act, even when all automated checks have passed. The quality gate provides confidence; the human provides authorization.

% ----------------------------------------------------------------------------
\subsection{Auditability and Compliance}
\label{subsec:auditability}
% ----------------------------------------------------------------------------

A consequence of the PR-based promotion model is that every quality gate decision produces a complete, immutable audit trail. Each promotion---whether approved, rejected, or pending---is recorded through multiple complementary artefacts:

\begin{enumerate}
    \item \textbf{Promotion PRs.} Every environment transition is a GitHub pull request (PR). The PR records the proposed change (hydrated manifests on the \texttt{-next} branch), the target branch, the timestamp, and the actor who created it (the Promoter). For \texttt{autoMerge: false} environments, the PR also records who approved and merged it.
    \item \textbf{Commit status checks.} Each gate writes a GitHub commit status (\texttt{success} or \texttt{failure}) on the PR's head SHA. Branch protection rules require these checks to pass before merge is permitted. The commit status persists as a permanent record of the gate verdict.
    \item \textbf{PR comments.} The exit handler posts a structured DriveBy report as a PR comment: per-principle pass/fail, severity breakdown, remediation guidance (``How to Pass This Gate''), and a link to the Argo Workflow run. Failed gates explain which principles blocked promotion and why.
    \item \textbf{CommitStatus CRDs.} The Kubernetes-native \texttt{CommitStatus} custom resource (managed by the GitOps Promoter) records the gate phase (\texttt{pending}, \texttt{success}, \texttt{failure}) for each SHA. These CRDs persist in the cluster and can be queried for historical gate decisions.
    \item \textbf{Workflow logs.} Argo Workflow archives contain the full execution trace: health check attempts, DriveBy validation output (JSON), functional test endpoint results, and load test metrics. These logs are accessible via the Argo Workflows UI and persist according to the cluster's retention policy.
\end{enumerate}

This multi-layer audit trail is an intrinsic byproduct of the GitOps promotion model, not a separate observability system: for any deployment in any environment, an auditor can trace back to the exact PR, the exact validation results, and the exact human (or automated) decision that approved the promotion. The \texttt{autoMerge: false} setting on production environments adds an explicit human authorization step to this trail---the PR comment provides the evidence (``6/6 principles passed, load test P95: 4.9\,ms''), the human makes the merge decision---satisfying the separation-of-duties requirement common in regulated environments.

\section{Quality Gate as Control Loop}
\label{sec:control-loop}
% ============================================================================

The quality gate system forms a \textit{closed-loop negative feedback} controller~\cite{astrom-feedback}. The plant is the \textit{delivery system itself}---the promotion pipeline, whose state comprises promotion PRs, environment branches, and per-environment sync state. The setpoint is a \textit{promotion-policy predicate} over artefacts and delivery state, defined by two declarative artefacts: the OpenAPI specification declares the contract a deployed artefact must satisfy before it may transition, and the XSDLC manifest declares which transitions are gated, by what checks, and under what merge policy. DriveBy measures the deployed API and emits a \textit{validation verdict}; the actuator (CommitStatus and Promoter) merges or blocks the promotion PR, so that only policy-conforming transitions occur. This section first presents this block-diagram mapping, then decomposes its abstract ``Controller'' into the two-tier stack the implementation instantiates---a verdict tier emitting the measurement and a platform tier performing continuous closed-loop repair of the pipeline machinery.

% ----------------------------------------------------------------------------

\label{subsec:control-mapping}
% ----------------------------------------------------------------------------

The key property is that the feedback is \textit{negative}: validation failure blocks promotion rather than advancing it. Without this, a failing API would propagate unchecked from development to staging to production---the shift-right antipattern that SDT explicitly prevents. Under this mapping the loop is genuinely closed on its plant: the merge/block decision is a corrective action \textit{on the delivery system}, admitting only artefacts that satisfy the policy predicate. The loop deliberately does not repair the API or its specification; Section~\ref{subsec:controller-stack} develops that boundary and decomposes the abstract ``Controller'' into the stack of reconcilers that realises it on the cluster.

% ----------------------------------------------------------------------------
\subsection{The Controller is a Stack: Verdict Tier and Platform Tier}
\label{subsec:controller-stack}
% ----------------------------------------------------------------------------

The classical mapping in Table~\ref{tab:control-mapping} and Figure~\ref{fig:quality-control-loop} is pedagogically useful but architecturally lossy: it collapses what is in fact a \emph{stack of controllers} into a single ``Controller'' block. The system separates cleanly into two tiers with different control-theoretic character.

\textbf{Verdict tier} (open-loop). The verdict tier contains the DriveBy CLI as sensor and the Argo Workflow as the controller that emits a pass/fail signal materialised as a \texttt{CommitStatus}. The controller observes the error $e(t) = r_{\text{OpenAPI}}(t) - H(y(t))$, where $H$ is the DriveBy validator and $y$ is the deployed API. It decides \emph{promote} or \emph{block}. This tier is honest about its limitation: \textit{it produces no actuation signal $u$ that reduces $e(t)$ by acting on the API or its specification}---its only actuation is on the delivery system (the plant of Table~\ref{tab:control-mapping}), via the merge/block decision. There is no spec re-write, no implementation patch, no automated remediation. The error signal is exported as a structured report; the corrective action is performed externally---by a developer who reads the report, or, in the experiment of Section~\ref{sec:sdt-feedback-experiment}, by an AI coding agent that consumes the same report as machine-actionable input. The verdict tier is the deliberate, scoped open-loop component of an otherwise self-reconciling system; closing it with autonomous remediation is recorded as future work (Chapter~\ref{ch:conclusion}, Section~\ref{sec:future-work}).

\textbf{Platform tier} (closed-loop, autonomous). Beneath the verdict tier sits the second reference signal: $r_{\text{XSDLC}}$, the XSDLC manifest, which declares the entire delivery pipeline---gate workflows, event sources, sensors, branch protection, the GitOps repository, the ArgoCD Application, the PromotionStrategy, ingress routes, RBAC. This reference is reconciled by a \emph{stack} of Kubernetes controllers, each with its own observe-diff-act loop in the sense of Section~\ref{subsec:reconciliation-loop}. Three of them perform continuous state reconciliation in the strict sense: Crossplane composes the $\sim$45--50 managed objects from the manifest and re-creates any that are deleted; ArgoCD reconciles cluster state against the GitOps repository (with \texttt{selfHeal} enabled); the GitOps Promoter reconciles promotion branches and reopens PRs that go missing; \texttt{provider-upjet-github} reconciles GitHub-side state, restoring branch protection rules and push secrets if they are removed. Two further controllers manage event-time machinery rather than persistent state: Argo Workflows executes the gate as a DAG and retries failed steps under its own retry policy, and Argo Events reconciles the EventSource and Sensor CRDs that keep the webhook plumbing armed. Crossplane plays the role of meta-orchestrator over the stack: the XSDLC composition is what creates and parameterises every controller-managed object in the first place. Figure~\ref{fig:controller-stack} draws the decomposition.

This two-tier reading sharpens what ``self-reconciling'' actually means in this thesis. The platform tier exhibits the classical closed-loop properties of Kubernetes controllers~\cite{k8s-controllers}: drift between $r_{\text{XSDLC}}$ and observed cluster state is detected and corrected without human intervention; transient failures of individual controllers do not produce permanent state divergence because the reconciliation is level-triggered. The verdict tier deliberately does not have these properties on the API contract---automatic spec or implementation repair is a research direction, not a present capability---but it inherits the platform tier's robustness for everything \textit{around} the verdict: missing gate workflows are recreated, deleted commit statuses are re-issued, drifted RBAC is restored.

The architectural value of the two-tier separation is precisely that it forces the open-loop component to be small, scoped, and visible. The system is honest about where it intervenes autonomously (platform configuration) and where it relies on a human or agent loop closure (specification and implementation quality).

Drift between specification and implementation deserves explicit treatment in this context, because it is sometimes incorrectly held to be a pre-condition that SDT must externally assume, and a continuous drift-watching loop is sometimes proposed as a missing capability. Both framings understate the architecture. P006 (Functional Testing) detects spec--implementation divergence \textit{at the moment the gate fires}---it probes the live API and compares observed behaviour against the declared contract---making drift detection a first-class capability of the verdict tier rather than an assumption.

The deeper point is that under the XSDLC promotion chain, \textit{the pipeline actively prevents drift from reaching production}---it does not merely detect it after the fact. ArgoCD synchronises a target environment exclusively from its \texttt{environment/<env>} branch; that branch is updated exclusively by Promoter-mediated merges from \texttt{<env>-next}; the Promoter blocks the merge as long as any required CommitStatus is not in the success state; CommitStatuses are written exclusively by gate workflows that run the principle checkers, including P006. GitHub-side branch protection, reconciled by \texttt{provider-upjet-github}, blocks direct pushes to the \texttt{environment/*} branches, preventing the chain from being bypassed at the source-control layer. There is therefore no path by which an implementation change can reach production without first passing a gate that has executed P006 against it---and blocked promotion if divergence was detected. The pipeline does not lack continuous drift detection; it makes continuous drift detection unnecessary by enforcing, at every transition, the very property that continuous detection would later have to recover. The only path by which undetected drift could appear in a production deployment is an out-of-band intervention that bypasses the pipeline altogether---a violation of the GitOps discipline that the architecture is designed to enforce, and a problem that precedes drift detection rather than being solved by it.

\subsection{Convergence and Robustness}
\label{subsec:negative-feedback}
% ----------------------------------------------------------------------------

Convergence has a distinct character in each tier. In the \textit{verdict tier}, each quality gate evaluation is a discrete sample: pass or fail. When validation fails, the developer (or agent) fixes the issue and re-triggers the deploy workflow. The new manifests land on the \texttt{-next} branch, the Promoter updates the PR, and the gate re-evaluates. The loop iterates until the API conforms to its specification---convergence is driven by external corrective action, gated by DriveBy's objective assessment. The verdict tier converges over PRs, not over time within a PR.

In the \textit{platform tier}, convergence is autonomous and continuous. The Kubernetes controller model (Section~\ref{subsec:reconciliation-loop}) makes the platform tier robust to transient failures by construction. Two failure classes are distinguished. \textit{Transient infrastructure failures}---pod eviction, network timeout---are absorbed within the workflow run: Argo Workflows retries the failed step, so validation completes without developer involvement. If a workflow fails terminally, the exit handler posts a \texttt{failure} status and promotion remains blocked (fail-closed); the same change can be re-evaluated without a new commit---the Sensor's \texttt{reopened} filter re-fires the gate against the unchanged \texttt{-next} branch when the promotion PR is closed and reopened (or the workflow is resubmitted from the Argo UI). \textit{Genuine validation failures} require a corrective commit by design: the re-push is the corrective action itself and re-triggers evaluation through the normal hydration path. If a generated child resource is deleted, the Crossplane composition controller re-creates it on the next reconciliation pass. If a branch protection rule is removed manually, \texttt{provider-upjet-github} restores it. No manual re-triggering is needed because the system is level-triggered: it reacts to current state, not to events it might have missed.

The two convergence modes compose. The platform tier guarantees that the gate machinery itself remains in its declared configuration even under operator error or transient infrastructure failure; the verdict tier then operates on top of that guarantee, with developer-driven (or agent-driven) iteration the only loop that requires external action.

\subsection{Connecting Axioms to Control Requirements}
\label{subsec:theory-implementation}
% ----------------------------------------------------------------------------

This control-theoretic framing connects to the ontological state reconciliation pattern introduced in Section~\ref{subsec:ontological-reconciliation}: each tier has its own ontological artefact and its own reconciliation agent. The OpenAPI specification is the ontological artefact for the verdict tier, with DriveBy as reconciliation sensor and the developer (or agent) as the external corrective actor; the XSDLC manifest is the ontological artefact for the platform tier, with Crossplane and the downstream controllers as the autonomous reconciliation stack.

The three SDT axioms map to necessary control-loop properties. \textit{Completeness} requires that the setpoint fully characterises the desired behaviour---an incomplete specification produces an under-determined loop that cannot distinguish conforming from non-conforming APIs. \textit{Determinism} requires consistent sensor output---a non-deterministic validator would oscillate between pass and fail for identical states. \textit{Observability} requires structured, actionable output---without it, feedback degenerates into a binary gate with no diagnostic value, and developers cannot identify what to fix.\footnote{This control-theoretic framing is illustrative rather than formally rigorous. The system does not satisfy the classical control-theory definitions of \textit{stability} (convergence of the error signal under a defined metric), \textit{controllability} (state reachability), or \textit{observability} (state reconstructibility from outputs); the use of the latter term in the SDT axiom set is deliberately coincidental in language but distinct in content---SDT's Observability axiom refers to structured, machine-readable output, not state-reconstructibility. What the framing does capture is the structural \textit{pattern} of closed-loop feedback control: a setpoint (the specification), a sensor (the validator), a controller (the gate workflow), and an actuator (the promoter) that together drive the system toward the declared state and self-correct deviations. A fully formal control-theoretic treatment would require additional assumptions about API behaviour and validator determinism that exceed the scope of this thesis; it is recorded as a research direction in Chapter~\ref{ch:conclusion}, Section~\ref{sec:future-work}.}

This is not a metaphorical mapping: each component---setpoint, sensor, controller, actuator, feedback path---has a concrete implementation, and the two-tier decomposition is faithful to the architecture. The correspondence explains why the platform tier converges autonomously, why the verdict tier requires external loop closure today, and why the axiomatic foundation is necessary rather than merely desirable---giving future work on autonomous remediation a precise object of study.

\section{CI/CD of DriveBy Itself}
\label{sec:cicd-driveby}
% ============================================================================

DriveBy's own development pipeline serves as a reflexive demonstration of the SDT framework: the tool that validates API quality is itself subject to automated quality gates at every stage of delivery. The pipeline design follows three principles: (1)~a \textit{test gate} that blocks all artefact production---no binary, image, or chart is published unless tests pass; (2)~\textit{parallel artefact generation}---independent outputs (binaries, container images, Helm charts) are produced concurrently to minimise release latency; and (3)~\textit{multi-format distribution}---a single Git tag produces version-aligned artefacts across three distribution channels, ensuring that consumers always reference a consistent release. Three GitHub Actions~\cite{github-actions} workflows implement these principles.

% ----------------------------------------------------------------------------
\subsection{Continuous Integration}
\label{subsec:ci-pipeline}
% ----------------------------------------------------------------------------

The \texttt{ci.yml} workflow implements a layered validation strategy: compilation verifies build integrity, static analysis detects code-level defects, testing validates behavioural correctness, and a documentation check---an SDT-adjacent meta-validation---fails the build when CLAUDE.md files and documentation entries diverge from the source tree. Although the cheapest layer, the documentation check deliberately runs last: a documentation-divergence report against broken code would be noise---the code, not the documentation, must change first.

The workflow uses a two-tier triggering strategy: pull requests run all four validation layers with coverage artefacts for fast feedback, while pushes to \texttt{main} additionally build the container image (without pushing), maintaining the stricter invariant that every commit on \texttt{main} is both tested and container-buildable.

% ----------------------------------------------------------------------------
\subsection{Docker Image Publishing}
\label{subsec:docker-publish}
% ----------------------------------------------------------------------------

The \texttt{docker-publish.yml} workflow uses path-scoped triggering: it fires only when files under \texttt{driveby-cli/} change on pushes to \texttt{main}, so the container image is rebuilt exactly when the validation logic changes and not otherwise.

The workflow produces images with a dual-tagging strategy: the mutable \texttt{latest} tag serves development clusters and Argo Workflows templates that should always run the newest version, while the short commit SHA tag provides an immutable reference for production traceability. Docker Buildx~\cite{docker-buildx} handles multi-platform builds with GitHub Actions layer caching. The resulting image at \texttt{ghcr.io/meter-peter/driveby} is the same image used by the Argo Workflows validation pipeline.

% ----------------------------------------------------------------------------
\subsection{Release Pipeline}
\label{subsec:release-pipeline}
% ----------------------------------------------------------------------------

The \texttt{release.yml} workflow implements a fan-out pattern: a single semantic version tag push (\texttt{v*}) triggers a test gate, and three independent artefact producers run in parallel after the gate passes. Figure~\ref{fig:release-pipeline} shows the pipeline structure.

\begin{figure}[htbp]
\centering
\resizebox{\textwidth}{!}{%
\input{figures/release-pipeline.tex}%
}
\caption{Release pipeline triggered by a version tag push. After the test gate passes, three parallel jobs produce platform binaries, Docker images, and a Helm chart.}
\label{fig:release-pipeline}
\end{figure}

The test gate re-runs static analysis and the test suite; all subsequent jobs depend on it. This is the release-level analog of the quality gate pattern: just as SDT blocks promotion on validation failure, the test gate blocks artefact production on test failure.

The three parallel producers each address a distinct distribution channel: GoReleaser~\cite{goreleaser} produces cross-compiled platform binaries with SHA256 checksums and an auto-generated changelog; the Docker job produces container images with a semver-derived tagging strategy (full version, major.minor, \texttt{latest}) that lets consumers choose their stability-versus-freshness trade-off; and the Helm job packages the chart and pushes it to the OCI registry (Section~\ref{subsec:oci-distribution}).

The key design property is \textit{version alignment}: the chart version, container image tags, and CLI binary version are all derived from the same Git tag, so consumers can verify artefact provenance without cross-referencing build logs. Parallel execution minimises release latency while the shared test gate ensures atomicity: either all three artefacts are produced from tested code, or none are.

\section{Operational Deployment}
\label{sec:operational-deployment}
% ============================================================================

The quality gate system follows a \textit{platform-inherited} deployment model: it does not install its own infrastructure but instead declares references to shared platform capabilities that are assumed to be present. This is a deliberate architectural choice that aligns with the separation between Day~0 (platform installation) and Day~1 (pipeline creation) described in Section~\ref{subsec:day0}. The proof-of-concept deployment runs on \texttt{private.novelcore.org}, a Kubernetes cluster managed by KubeCore.

% ----------------------------------------------------------------------------
\subsection{Prerequisites}
\label{subsec:prerequisites}
% ----------------------------------------------------------------------------

The deployment depends on six cluster components, each addressing a distinct concern in the quality gate lifecycle. Crossplane~\cite{crossplane} provides the declarative provisioning layer that translates \texttt{XSDLC} custom resources into managed child resources. ArgoCD~\cite{argocd} provides the GitOps synchronisation layer that deploys applications from environment branches. Argo Workflows~\cite{argo-workflows} and Argo Events~\cite{argo-events} provide the event-driven execution layer that triggers and orchestrates validation pipelines. Traefik and cert-manager provide the network ingress layer that routes external webhooks and terminates TLS.

The DriveBy Helm chart creates resources that \textit{reference} components at each layer (Ingress resources reference the Traefik ingress class, certificate annotations reference the cert-manager issuer, workflow submissions reference the Argo Workflows controller) without installing them, so DriveBy can be added to any cluster that already runs these components without conflicting with existing installations.

The proof-of-concept deployment on \texttt{private.novelcore.org} validates this surgical coexistence model. The cluster hosts Novelcore's Internal Developer Platform (IDP), with ArgoCD, Argo Workflows, Argo Events, and Traefik already running in production for other workloads; GitHub is the SCM provider because Novelcore already operates on GitHub. DriveBy was installed into this \textit{existing, active cluster} without modifying any pre-existing installation. The same property holds in reverse: deleting an \texttt{XSDLC} CR removes all DriveBy-managed child resources (WorkflowTemplates, Sensors, EventSources, Ingresses, BranchProtection rules) while leaving the platform components untouched, and \texttt{helm uninstall} removes the XRD and composition definitions themselves. Because DriveBy never owns the infrastructure it depends on, installation and removal require no restart, reconfiguration, or redeployment of any platform component.

% ----------------------------------------------------------------------------
\subsection{Verification}
\label{subsec:verification}
% ----------------------------------------------------------------------------

Post-deployment verification is the \textit{platform operator's} responsibility and proceeds layer by layer, validating each abstraction level independently to isolate failures. Steps~1--3 run once after applying an \texttt{XSDLC} CR (Day~1), with step~3 also exercising the ingress and certificate components installed at platform installation (Day~0); step~4 exercises the steady-state path (Day~2) that ordinary PR commits subsequently trigger:

\begin{enumerate}
    \item \textbf{Declarative provisioning}: All \texttt{XSDLC} composites report \texttt{READY=True}, verifying that Crossplane generated and reconciled all child resources; a non-ready composite indicates a composition rendering error or provider authentication failure.

    \item \textbf{Event infrastructure}: The EventBus, EventSource, and Sensor resources are healthy; a failing EventBus typically indicates a NATS JetStream configuration issue, a failing Sensor a filter or template reference error.

    \item \textbf{Network path}: A test webhook payload to the Ingress endpoint returns 200, confirming the path from the external domain to the EventSource; a failure isolates the problem to DNS, TLS provisioning, or ingress routing.

    \item \textbf{End-to-end behaviour}: A test PR triggers a complete validation cycle---workflow completion, commit status on the PR, and a posted validation report confirm that all layers function together.
\end{enumerate}

\section{Summary}
\label{sec:pipeline-summary}
% ============================================================================

This chapter described the operational GitOps pipeline that connects DriveBy's validation engine to a fully declarative delivery lifecycle: the BYOCI boundary (Section~\ref{sec:two-repo}) leaves CI to the developer, while a single \texttt{XSDLC} custom resource (\(\sim\)35 lines of YAML) provisions hydration, promotion PRs, per-environment quality gates, and a tunable human-in-the-loop merge policy (Section~\ref{sec:human-in-the-loop}). The control-theoretic framing (Section~\ref{sec:control-loop}) explains why the design converges: negative feedback blocks non-conforming promotions, and the three SDT axioms---Completeness, Determinism, Observability---are necessary conditions for the loop to function. Chapter~\ref{ch:evaluation} evaluates this system empirically, measuring SDT's effectiveness across controlled and large-scale settings.
