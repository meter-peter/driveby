\chapter{GitOps Pipeline and CI/CD}
\label{ch:workflow}

Chapter~\ref{ch:kubernetes} described the Kubernetes infrastructure---Crossplane XRDs, Argo Events, Argo Workflows---that implements the quality gate system. This chapter describes how that infrastructure operates within the broader GitOps pipeline: the promotion-driven quality gate flow, the event-driven validation pipeline end-to-end, the two-repo architecture and its ``Bring Your Own CI'' (BYOCI) design principle, the GitOps Promoter's multi-environment model, human-in-the-loop decision patterns, and the quality gate as a closed-loop control system. The chapter also describes how DriveBy itself is released---binaries, container images, and Helm charts---through automated GitHub Actions pipelines.

Together, Chapters~\ref{ch:architecture},~\ref{ch:kubernetes}, and this chapter form a three-layer value chain: the DriveBy CLI provides the validation logic, Kubernetes infrastructure orchestrates its execution, and GitOps pipelines make validation results drive promotion decisions. This chapter describes the outermost layer---the point where validation results become operational signals that advance or block software delivery.

The chapter addresses Research Question~3 (RQ3): \textit{How effectively does specification-driven quality assurance integrate into cloud-native GitOps pipelines as an autonomous quality gate?} The answer is demonstrated through a proof-of-concept deployment on the \texttt{private.novelcore.org} cluster, where DriveBy validates five evaluation APIs across three environments.

\section{Promotion-Driven Quality Gate}
\label{sec:promotion-driven-gate}
% ============================================================================

The quality gate operates on a key insight: \textit{validate the source environment, not the target}. The developer's own CI builds a new container image (the BYOCI boundary described in Section~\ref{subsec:byoci}), then commits the updated dry manifests and image tag to the \texttt{main} branch of the dedicated gitops repository. The ArgoCD Source Hydrator~\cite{argocd-hydrator} renders each environment's Kustomize overlay and writes hydrated output to the corresponding \texttt{-next} branch. The GitOps Promoter creates a promotion PR from the \texttt{-next} branch to the active branch, and ArgoCD~\cite{argocd} synchronizes the environment once the PR is merged.

This promotion PR triggers the quality gate. The GitHub webhook fires, the EventSource receives the event, the Sensor filters for PR actions, and the Workflow executes validation against the \textit{development} environment---the environment where the new code is already running. The validation results determine whether the promotion PR is approved (merged) or blocked (left open with a failure status).

This inversion is deliberate. Validating the source environment ensures that quality is assessed against the actual deployment rather than a hypothetical future state. If the API in development passes strict SDT validation, the same code deployed to staging will behave identically (assuming equivalent infrastructure). The alternative---validating the target environment after promotion---would detect problems only after the potentially breaking change has already been deployed, violating the shift-left principle~\cite{shift-left}.

\section{Event-Driven Validation Pipeline}
\label{sec:event-pipeline-detail}
% ============================================================================

The event-driven pipeline transforms an external webhook into a structured validation workflow through five stages: ingress, event capture, event filtering, workflow submission, and feedback reporting. This section traces a single validation trigger through the entire pipeline.

% ----------------------------------------------------------------------------
\subsection{Webhook Delivery and Ingress}
\label{subsec:webhook-delivery}
% ----------------------------------------------------------------------------

The pipeline begins when an external event---a promotion PR opened on GitHub---must be routed to the correct in-cluster EventSource. This is a routing problem: multiple APIs and multiple environments share a single cluster, so each quality gate needs a unique, predictable endpoint that both GitHub and the cluster agree on without manual coordination.

The composition solves this through a convention-over-configuration mechanism. Both the webhook URL and the Ingress resource that exposes it are derived deterministically from two identity fields in the \texttt{XSDLC} spec: the application name and the gated environment name. The URL follows the pattern \texttt{https://\{app\}-\{gate\}-webhook.\{domain\}/\{app\}-\{gate\}-pr-trigger}. Because the Ingress resource, the EventSource endpoint, and the GitHub webhook configuration are all generated from the same identity fields by the same composition, they are guaranteed to agree. This provides three properties: (1)~no manual URL management---the operator never configures webhook endpoints; (2)~uniqueness---each gate in the cluster receives a distinct URL; and (3)~predictability---an operator can determine the webhook URL for any gate from the \texttt{XSDLC} CR's fields alone.

The Ingress resource carries a cert-manager annotation that triggers automatic TLS certificate provisioning. TLS termination happens at the Ingress controller (Traefik), so the EventSource receives plaintext HTTP on port~12000 internally. This is an instance of the platform inheritance design goal (Section~\ref{subsec:k8s-design-goals}): the application developer never configures TLS certificates or ingress routing; the platform provides these capabilities, and the composition references them. For the reference deployment, the staging gate resolves to \texttt{https://perfect-api-staging-gate-webhook.private.novelcore.org/\allowbreak perfect-api-staging-gate-pr-trigger}.

% ----------------------------------------------------------------------------
\subsection{Event Processing}
\label{subsec:event-processing}
% ----------------------------------------------------------------------------

The EventSource receives the webhook payload and publishes it to the EventBus (NATS JetStream). The Sensor subscribes to the EventBus and evaluates the event against its configured filters. For promotion PR validation, the Sensor checks that the event type is \texttt{pull\_request} and the action is one of \texttt{opened}, \texttt{reopened}, or \texttt{synchronize}. Events that do not match---such as PR label changes, review requests, or comment events---are silently discarded.

For matching events, the Sensor extracts ten parameters from the webhook payload using JSONPath expressions (detailed in Table~\ref{tab:sensor-params} of Chapter~\ref{ch:kubernetes}) and constructs a workflow submission request. The submission references the WorkflowTemplate generated by the \texttt{XSDLC} composition and passes the extracted parameters as workflow arguments.

% ----------------------------------------------------------------------------
\subsection{Latency Analysis}
\label{subsec:latency}
% ----------------------------------------------------------------------------

The end-to-end latency from webhook delivery to workflow completion depends on three factors: event processing overhead (typically under 2~seconds for EventSource $\rightarrow$ EventBus $\rightarrow$ Sensor $\rightarrow$ workflow submission), source readiness wait (0--120~seconds, depending on whether the deployment is already healthy), and validation execution time (10--60~seconds, depending on specification size and validation mode). In practice, a successful validation cycle typically completes in 10--30~seconds from PR creation to commit status posted. The five-API evaluation (Section~\ref{sec:multi-api-eval}) measured 10--12~seconds for gates with static validation only, 18--28~seconds for gates that include functional or load testing, and approximately 5~minutes for gates where the source environment is unreachable (the health check retries for 60 attempts at 5-second intervals before timing out).

\section{Two-Repo Architecture}
\label{sec:two-repo}
% ============================================================================

The quality gate system operates within a \textit{two-repository} model that enforces a clean separation between the developer's software and the platform's delivery infrastructure. The software repository is entirely developer-owned and untouched by XSDLC. A dedicated GitOps repository is auto-created by the XSDLC composition to hold Kubernetes manifests on per-environment branches. This section describes the architectural rationale, the boundary between developer and platform responsibilities, and the BYOCI integration contract.

% ----------------------------------------------------------------------------
\subsection{Why a Dedicated GitOps Repository}
\label{subsec:why-two-repo}
% ----------------------------------------------------------------------------

Traditional GitOps deployments face a tension between two concerns: the developer wants to keep manifests close to the source code for co-evolution, while the platform needs a clean Git-based state store that ArgoCD can watch without being polluted by source code history, CI artifacts, or unrelated commits. Single-repo models that embed manifests in the application repository conflate these concerns: every source commit appears in the ArgoCD diff view, and environment branches---which contain only Kubernetes manifests---create orphan or divergent histories when created in a repository whose \texttt{main} branch carries application source code, tests, and CI configuration. These divergent branches are confusing to developers, pollute the branch namespace, and make the repository's Git history difficult to reason about.

The XSDLC v3.0.0 model resolves this tension by separating the two concerns into two repositories. The software repository remains untouched; XSDLC auto-creates a dedicated GitOps repository per application that holds dry Kustomize manifests on the \texttt{main} branch and hydrated output on per-environment branches:

\begin{verbatim}
perfect-api/                    # Software repository (untouched)
  src/                          # Application source
  Dockerfile                    # Build specification

perfect-api-gitops/             # GitOps repository (auto-created)
  main branch:
    dry/
      base/                     # Shared manifests
        kustomization.yaml      # references deployment.yaml + service.yaml
        deployment.yaml
        service.yaml
      overlays/                 # Per-environment customization
        dev/kustomization.yaml
        staging/kustomization.yaml
        prod/kustomization.yaml

  environment/dev-next   →      # Hydrated by ArgoCD (manifests/ + hydrator.metadata)
  environment/dev        →      # Merged by Promoter from dev-next
  environment/staging-next →    # Hydrated by ArgoCD (manifests/ + hydrator.metadata)
  environment/staging    →      # Merged by Promoter (after gate passes)
  environment/prod-next  →      # Hydrated by ArgoCD (manifests/ + hydrator.metadata)
  environment/prod       →      # Merged by Promoter (after gate passes)
\end{verbatim}

The GitOps repository's \texttt{main} branch holds dry Kustomize manifests organized as a base-plus-overlays structure. Each environment has its own overlay that references the shared base and can customize deployment parameters (replicas, resource limits, environment variables, image tags). The ArgoCD Source Hydrator~\cite{argocd-hydrator} renders each overlay independently and writes the hydrated output---along with a \texttt{hydrator.metadata} file containing the dry commit SHA---to the corresponding \texttt{environment/<name>-next} branch. The GitOps Promoter detects the new commit and creates a promotion PR from the \texttt{-next} branch to the active branch. Quality gates fire on these PRs; ArgoCD syncs from the active branch once the PR is merged.

Per-environment branches and their corresponding \texttt{-next} branches are created by the XSDLC composition via \texttt{provider-upjet-github}. The software repository is never modified by XSDLC---no workflows are generated, no files are committed, no branches are created. This zero-touch property means that XSDLC can be adopted without any changes to the developer's existing repository structure, CI configuration, or branching strategy.

The developer updates dry manifests on the \texttt{main} branch of the GitOps repository. The hydrator and Promoter handle the rest: rendering overlays, writing to \texttt{-next} branches, creating promotion PRs, triggering quality gates, and merging when gates pass. Because each environment hydrates independently from \texttt{main}, deploying to a specific environment requires only updating its overlay---there is no requirement to propagate changes through earlier environments first.

% ----------------------------------------------------------------------------
\subsection{Bring Your Own CI (BYOCI)}
\label{subsec:byoci}
% ----------------------------------------------------------------------------

The two-repo model embodies a deliberate design principle: \textbf{XSDLC owns delivery, not CI}. The boundary is explicit: \textit{XSDLC's responsibility begins when dry manifests are committed to the \texttt{main} branch of the GitOps repository}.

Everything \textit{before} that point is the developer's responsibility: building the application, running unit tests, generating the container image, and updating dry manifests (base resources or per-environment overlays) on the \texttt{main} branch. These tasks are inherently application-specific---a Python FastAPI service uses different build tools, test frameworks, and container patterns than a Go gRPC service. XSDLC does not generate workflows, provide build templates, or prescribe how dry manifests are authored. The developer can use GitHub Actions, GitLab CI, Jenkins, a shell script, or a manual \texttt{git push}---the platform is agnostic.

Everything \textit{after} the commit is XSDLC's responsibility. The ArgoCD Source Hydrator renders the Kustomize overlays and writes hydrated output to \texttt{-next} branches. The GitOps Promoter detects the change, creates promotion PRs, quality gates validate the source environment, commit statuses gate merges, and ArgoCD auto-syncs the result. These tasks are platform-generic---the same hydration, promotion, gating, and sync pattern applies regardless of the application's language, framework, or build tool.

This separation contrasts with opinionated CD platforms (Tekton Pipelines, Jenkins X) that attempt to own the full CI/CD lifecycle. Such platforms trade flexibility for integration: they work well when the application fits their model and poorly when it does not. XSDLC is composable rather than monolithic---it integrates with any CI system that can commit manifests to a Git branch.

% ----------------------------------------------------------------------------
\subsection{Manifest Delivery}
\label{subsec:manifest-delivery}
% ----------------------------------------------------------------------------

The quality gate pipeline is triggered by a single primitive: \textit{a commit to the \texttt{main} branch of the GitOps repository that modifies dry manifests}. This is the entire integration contract between the developer's CI and the XSDLC delivery platform. XSDLC generates no workflows, commits no files to the software repository, and prescribes no tooling. Any system---GitHub Actions, GitLab CI, Jenkins, a shell script, or a manual \texttt{git push}---that can update Kustomize manifests on the \texttt{main} branch can trigger the full hydration, promotion, and quality gate flow.

The contract requires only that valid Kustomize manifests appear on the \texttt{main} branch. The developer edits the shared base (\texttt{dry/base/}) for cross-environment changes or a specific overlay (\texttt{dry/overlays/<env>/}) for environment-specific customization (replicas, image tags, resource limits). The ArgoCD Source Hydrator renders each affected overlay and writes hydrated output to the corresponding \texttt{-next} branch. The Promoter detects the change, creates a promotion PR to the active branch, triggers quality gates if configured, and merges the PR when gates pass (or waits for human approval if \texttt{autoMerge: false}). ArgoCD auto-syncs the active branch's \texttt{manifests/} path to the target namespace.

The GitOps repository, its environment branches, and its dry manifest scaffolding are provisioned automatically by XSDLC. The developer never creates environment branches, overlay directories, promotion PRs, ArgoCD Applications, or quality gate infrastructure---the \texttt{XSDLC} custom resource provisions all of these. The developer's sole responsibility is updating dry manifests on \texttt{main}.

\subsection{PromotionStrategy Generation}
\label{subsec:promotion-strategy}
% ----------------------------------------------------------------------------

The PromotionStrategy is not authored manually. The XSDLC composition generates it declaratively from the \texttt{environments[]} array in the XRD spec. Each environment entry produces a corresponding element in the PromotionStrategy's environment chain, with three derived fields computed automatically:

\begin{itemize}
    \item \textbf{Branch}: defaults to \texttt{environment/<name>} but overridable per environment via \texttt{branch}.
    \item \textbf{autoMerge}: defaults to \texttt{true}; set to \texttt{false} on any environment that requires human approval before promotion.
    \item \textbf{commitStatusKey}: defaults to \texttt{<envName>-gate}; overridable via \texttt{gate.commitStatusKey}. The key must match between the PromotionStrategy (which watches for it) and the Argo Workflow (which posts it).
\end{itemize}

This generation model is environment-count agnostic. The composition iterates over the \texttt{environments[]} array with \texttt{range}, producing a PromotionStrategy with \textit{N} environments for any \textit{N} $\geq$ 2. A two-environment chain (dev $\rightarrow$ prod) and a five-environment chain (dev $\rightarrow$ qa $\rightarrow$ staging $\rightarrow$ preprod $\rightarrow$ prod) are both expressed as XSDLC arrays; the composition handles both without modification.

The key design property is \textit{per-environment composability}. Each environment independently controls three dimensions: \textit{whether} a gate exists (\texttt{gate} presence), \textit{what} the gate checks (\texttt{gate.checks[]} array), and \textit{how} promotion proceeds after the gate passes (\texttt{autoMerge}). This produces a combinatorial space of pipeline configurations from a single composition template. For example, a team can run static validation on staging and load testing on production, or functional tests on both, or no gate on any environment---all without modifying the underlying Crossplane composition or Helm chart.

% ----------------------------------------------------------------------------
\subsection{CommitStatus as Quality Signal}
\label{subsec:commit-status-signal}
% ----------------------------------------------------------------------------

The integration between DriveBy and the GitOps Promoter is mediated by two commit status mechanisms:

\textbf{GitHub commit status.} The workflow's set-pending and report-success steps post commit status updates to the PR's head SHA via the GitHub API. The context key (e.g., \texttt{staging-gate}) is watched by the PromotionStrategy as the gate signal. This mechanism works for any GitHub-based workflow and does not require the GitOps Promoter.

\textbf{CommitStatus CRD.} When the GitOps Promoter is enabled, the workflow additionally creates a CommitStatus custom resource in the \texttt{driveby} namespace. The CommitStatus transitions through three phases: \texttt{pending} (set at workflow start), \texttt{success} (set after validation passes), or \texttt{failure} (set by the exit handler). The Promoter controller watches this resource and uses its phase to determine whether to merge the promotion PR. This CRD-based mechanism provides a Kubernetes-native alternative to the GitHub API and enables the Promoter to function even in environments where direct GitHub API access is restricted.

% ----------------------------------------------------------------------------
\subsection{ChangeTransferPolicy}
\label{subsec:change-transfer-policy}
% ----------------------------------------------------------------------------

The ChangeTransferPolicy defines how changes flow between environments at the Git level. For each environment, the policy maps a \textit{proposed} branch (e.g., \texttt{staging-next}) to an \textit{active} branch (e.g., \texttt{staging}). The Promoter creates pull requests from the proposed branch to the active branch and merges them when commit status gates pass. This branch-based model integrates naturally with Git-based review workflows: promotion PRs appear in the repository's PR list, carry commit status checks, and leave an auditable merge history.

% ----------------------------------------------------------------------------
\subsection{Promoter Reconciliation Loop}
\label{subsec:promoter-reconciliation}
% ----------------------------------------------------------------------------

The GitOps Promoter is itself a Kubernetes controller that implements the observe-diff-act pattern (Section~\ref{subsec:reconciliation-loop}) at the Git level rather than the cluster level.

\textbf{Observe.} The PromotionStrategy controller watches two resource types: GitRepository (which tracks the gitops repository) and CommitStatus (which reports quality gate results). It periodically polls the Git repository to detect changes on proposed branches and reads CommitStatus resources to determine gate outcomes.

\textbf{Diff.} For each environment in the promotion chain, the controller compares the proposed branch (\texttt{environment/<name>-next}) against the active branch (\texttt{environment/<name>}). If the branches differ, a promotion is pending. It then checks whether all required CommitStatuses report \texttt{success}. If any CommitStatus reports \texttt{failure} or \texttt{pending}, the promotion is blocked.

\textbf{Act.} When the proposed and active branches differ, the controller creates a promotion PR. When all commit status gates pass and \texttt{autoMerge} is \texttt{true}, the controller merges the PR automatically. When \texttt{autoMerge} is \texttt{false}, the PR remains open for human review.

The ChangeTransferPolicy is itself a second reconciliation layer: it is auto-created by the PromotionStrategy controller when the PromotionStrategy is applied. The PromotionStrategy reconciles the \textit{promotion logic} (which environments exist, what gates are required); the ChangeTransferPolicy reconciles the \textit{branch mechanics} (which branches map to which environments, when to create PRs). This two-layer design separates strategic configuration (the promotion chain) from tactical execution (the branch operations).

\section{Human-in-the-Loop Patterns}
\label{sec:human-in-the-loop}
% ============================================================================

The quality gate system is not fully autonomous. It automates objective assessments---SDT validation, health checks, load testing---while preserving human judgment for subjective assessments. This section maps the automation spectrum and identifies the decision points where human intervention is required or optional.

% ----------------------------------------------------------------------------
\subsection{The Automation Spectrum}
\label{subsec:automation-spectrum}
% ----------------------------------------------------------------------------

The system supports four points on the automation spectrum, controlled by two boolean parameters: \texttt{autoMerge} (on the PromotionStrategy, controlling whether the Promoter automatically merges promotion PRs) and \texttt{automated.selfHeal} (on the ArgoCD Application, controlling whether ArgoCD automatically syncs and self-heals).

\begin{enumerate}
    \item \textbf{Fully automated} (development): \texttt{autoMerge: true}, automated sync. After the developer triggers a deploy, changes flow from the \texttt{-next} branch, are auto-merged by the Promoter, and auto-synced by ArgoCD. No further human intervention after the initial trigger.
    \item \textbf{Automated with quality gate} (staging): \texttt{autoMerge: true}, automated sync, with a commit status gate. The Promoter waits for SDT validation to report success before merging. If validation fails, the PR remains open until the developer fixes the issue and re-pushes. Once the gate passes, promotion and sync are automatic.
    \item \textbf{Gated with human approval} (production): \texttt{autoMerge: false}, auto-sync. The Promoter creates the PR and SDT validates the source environment, but a human must explicitly merge the promotion PR. Once merged, ArgoCD auto-syncs the change. The single human checkpoint is the merge decision---ArgoCD always reflects the branch state.
    \item \textbf{Fully manual merge}: no quality gate, manual merge, auto-sync. This mode is possible but unused in the reference deployment---it offers no advantage over the gated model. ArgoCD still auto-syncs once the branch is updated.
\end{enumerate}

Figure~\ref{fig:human-in-the-loop} illustrates how these two configurable slots---quality gate and merge policy---compose independently per environment. ArgoCD always auto-syncs; the sync policy is fixed. Each configurable slot is a modular parameter in the XSDLC spec; the composition renders the appropriate infrastructure (branch protection rules, CommitStatus gates) based on the selected values. Adding a quality gate or switching from auto-merge to manual approval are each single-field changes that independently affect one slot without impacting the other.

\centering

Each environment is a pipeline of four stages with two independently configurable slots: quality gate (\texttt{gate.checks[]}) and merge policy (\texttt{autoMerge}). ArgoCD always auto-syncs. % ----------------------------------------------------------------------------
\subsection{Automation with Human Override}
\label{subsec:automation-override}
% ----------------------------------------------------------------------------

The design philosophy is: \textit{automate objective assessments, preserve human judgment for subjective assessments}. SDT validation, health checks, and load testing produce binary signals (pass/fail) based on measurable criteria. These are objective and automatable. Production readiness, business timing, and release coordination involve context that no automated system can capture. These are subjective and require human judgment.

The \texttt{autoMerge: false} setting is a deliberate architectural choice, not a limitation. It reflects the principle that the final decision to deploy to production should be an affirmative human act, even when all automated checks have passed. The quality gate provides confidence; the human provides authorization.

% ----------------------------------------------------------------------------
\subsection{Auditability and Compliance}
\label{subsec:auditability}
% ----------------------------------------------------------------------------

A consequence of the PR-based promotion model is that every quality gate decision produces a complete, immutable audit trail. Each promotion---whether approved, rejected, or pending---is recorded through multiple complementary artifacts:

\begin{enumerate}
    \item \textbf{Promotion PRs.} Every environment transition is a GitHub pull request. The PR records the proposed change (hydrated manifests on the \texttt{-next} branch), the target branch, the timestamp, and the actor who created it (the Promoter). For \texttt{autoMerge: false} environments, the PR also records who approved and merged it.
    \item \textbf{Commit status checks.} Each gate writes a GitHub commit status (\texttt{success} or \texttt{failure}) on the PR's head SHA. Branch protection rules require these checks to pass before merge is permitted. The commit status persists as a permanent record of the gate verdict.
    \item \textbf{PR comments.} The exit handler posts a structured DriveBy report as a PR comment: per-principle pass/fail, severity breakdown, remediation guidance (``How to Pass This Gate''), and a link to the Argo Workflow run. Failed gates explain which principles blocked promotion and why.
    \item \textbf{CommitStatus CRDs.} The Kubernetes-native \texttt{CommitStatus} custom resource (managed by the GitOps Promoter) records the gate phase (\texttt{pending}, \texttt{success}, \texttt{failure}) for each SHA. These CRDs persist in the cluster and can be queried for historical gate decisions.
    \item \textbf{Workflow logs.} Argo Workflow archives contain the full execution trace: health check attempts, DriveBy validation output (JSON), functional test endpoint results, and load test metrics. These logs are accessible via the Argo Workflows UI and persist according to the cluster's retention policy.
\end{enumerate}

This multi-layer audit trail is not a separate observability system bolted onto the pipeline---it is an intrinsic byproduct of the GitOps promotion model. The PR is the unit of change, the commit status is the gate verdict, the comment is the evidence, and the workflow log is the execution trace. Together, they provide the traceability required for compliance audits: for any deployment in any environment, an auditor can trace back to the exact PR, the exact validation results, and the exact human (or automated) decision that approved the promotion.

The \texttt{autoMerge: false} setting on production environments adds an explicit human authorization step to this trail. The PR comment provides the evidence (``6/6 principles passed, load test P95: 1.8ms''); the human reviews the evidence and makes the merge decision. This pattern satisfies the separation-of-duties requirement common in regulated environments: the automated system assesses quality, but a human authorizes deployment.

\section{Quality Gate as Control Loop}
\label{sec:control-loop}
% ============================================================================

The quality gate system forms a \textit{closed-loop negative feedback} controller~\cite{astrom-feedback}: the OpenAPI specification defines the desired contract, DriveBy measures the deployed API against it, and the result either advances or blocks promotion. This section maps the system's components to control-theoretic primitives and explains why this framing matters for convergence and robustness.

% ----------------------------------------------------------------------------
\subsection{Control Theory Mapping}
\label{subsec:control-mapping}
% ----------------------------------------------------------------------------

Table~\ref{tab:control-mapping} maps each control-theoretic role to its concrete implementation in the DriveBy architecture.

\begin{table}[htbp]
\centering
\caption{Control theory mapping to DriveBy quality gate components.}
\label{tab:control-mapping}
\small
\begin{tabular}{@{}lll@{}}
\toprule
\textbf{Control Role} & \textbf{Implementation} & \textbf{Function} \\
\midrule
Setpoint       & OpenAPI specification       & Desired API contract \\
Plant          & API deployment (source env) & Running service under test \\
Sensor         & DriveBy CLI                 & Validates spec against live API \\
Controller     & Argo Workflow DAG           & Orchestrates checks, emits pass/fail \\

The key property is that the feedback is \textit{negative}: validation failure blocks promotion rather than advancing it. Without this, a failing API would propagate unchecked from development to staging to production---the shift-right antipattern that SDT explicitly prevents.

% ----------------------------------------------------------------------------
\subsection{Convergence and Robustness}
\label{subsec:negative-feedback}
% ----------------------------------------------------------------------------

Each quality gate evaluation is a discrete sample: pass or fail. When validation fails, the developer fixes the issue and re-triggers the deploy workflow. The new manifests land on the \texttt{-next} branch, the Promoter updates the PR, and the gate re-evaluates. The loop iterates until the API conforms to its specification---convergence is driven by the developer's corrective action, gated by DriveBy's objective assessment.

The Kubernetes controller model (Section~\ref{subsec:reconciliation-loop}) makes this loop robust to transient failures. If a workflow fails due to pod eviction or network timeout, the exit handler posts a ``failure'' status. On the next branch change, the Promoter triggers re-evaluation automatically. No manual re-triggering is needed because the system is level-triggered: it reacts to current state, not to events it might have missed.

% ----------------------------------------------------------------------------
\subsection{Connecting Axioms to Control Requirements}
\label{subsec:theory-implementation}
% ----------------------------------------------------------------------------

This control-theoretic framing connects to the ontological state reconciliation pattern introduced in Section~\ref{subsec:ontological-reconciliation}: the specification is the ontological artifact, the DriveBy CLI is the reconciliation agent, and the quality gate is the correction mechanism.

The three SDT axioms map to necessary control-loop properties. \textit{Completeness} requires that the setpoint fully characterizes the desired behavior---an incomplete specification produces an under-determined loop that cannot distinguish conforming from non-conforming APIs. \textit{Determinism} requires consistent sensor output---a non-deterministic validator would oscillate between pass and fail for identical states. \textit{Observability} requires structured, actionable output---without it, feedback degenerates into a binary gate with no diagnostic value, and developers cannot identify what to fix.

This is not a metaphorical mapping. Each component---setpoint, sensor, controller, actuator, feedback path---has a concrete implementation. The correspondence explains why the system converges, why it self-heals, and why the axiomatic foundation is necessary rather than merely desirable.

\section{CI/CD of DriveBy Itself}
\label{sec:cicd-driveby}
% ============================================================================

DriveBy's own development pipeline serves as a reflexive demonstration of the SDT framework: the tool that validates API quality is itself subject to automated quality gates at every stage of delivery. The pipeline design follows three principles: (1)~a \textit{test gate} that blocks all artifact production---no binary, image, or chart is published unless tests pass; (2)~\textit{parallel artifact generation}---independent outputs (binaries, container images, Helm charts) are produced concurrently to minimize release latency; and (3)~\textit{multi-format distribution}---a single Git tag produces version-aligned artifacts across three distribution channels, ensuring that consumers always reference a consistent release. Three GitHub Actions~\cite{github-actions} workflows implement these principles.

% ----------------------------------------------------------------------------
\subsection{Continuous Integration}
\label{subsec:ci-pipeline}
% ----------------------------------------------------------------------------

The \texttt{ci.yml} workflow implements a layered validation strategy where each layer provides a different kind of assurance: compilation verifies build integrity, static analysis detects code-level defects, testing validates behavioral correctness, and a documentation check enforces meta-validation---that documentation artifacts remain synchronized with the codebase. This last layer embodies a SDT-adjacent principle: documentation completeness should be verified automatically, not assumed. The documentation check scans CLAUDE.md files and documentation entries against the source tree, failing the build when they diverge.

The workflow uses a two-tier triggering strategy. On pull requests, it runs all four validation layers and uploads coverage artifacts for review, providing fast feedback during development. On pushes to \texttt{main}, it additionally builds the container image (without pushing) to verify that the Docker build remains functional on the mainline. This tiered approach ensures that PRs receive rapid validation while the mainline maintains a stricter invariant: every commit on \texttt{main} is both tested and container-buildable.

% ----------------------------------------------------------------------------
\subsection{Docker Image Publishing}
\label{subsec:docker-publish}
% ----------------------------------------------------------------------------

The \texttt{docker-publish.yml} workflow uses path-scoped triggering: it fires only when files under \texttt{driveby-cli/} change on pushes to \texttt{main}, avoiding unnecessary image builds for documentation-only or thesis-only changes. This scoping mechanism ensures that the container image is rebuilt exactly when the validation logic changes and not otherwise.

The workflow produces images with a dual-tagging strategy that serves two distinct consumers. The \texttt{latest} tag provides a mutable reference for development clusters and Argo Workflows templates that should always run the newest version. The short commit SHA tag provides an immutable reference for production traceability---given a workflow run, an operator can trace the exact binary that executed by inspecting the image tag. Docker Buildx~\cite{docker-buildx} handles multi-platform builds, and layer caching via GitHub Actions Cache reduces build times for incremental changes. The resulting image at \texttt{ghcr.io/meter-peter/driveby} is the same image used by the Argo Workflows validation pipeline.

% ----------------------------------------------------------------------------
\subsection{Release Pipeline}
\label{subsec:release-pipeline}
% ----------------------------------------------------------------------------

The \texttt{release.yml} workflow implements a fan-out pattern: a single semantic version tag push (\texttt{v*}) triggers a test gate, and three independent artifact producers run in parallel after the gate passes. Figure~\ref{fig:release-pipeline} shows the pipeline structure.

\begin{figure}[htbp]
\centering
\resizebox{\textwidth}{!}{%
\input{figures/release-pipeline.tex}%
}
\caption{Release pipeline triggered by a version tag push. After the test gate passes, three parallel jobs produce platform binaries, Docker images, and a Helm chart.}
\label{fig:release-pipeline}
\end{figure}

The test gate re-runs static analysis and the test suite. All subsequent jobs depend on this gate, enforcing the invariant that no artifacts are produced from untested code. This is the release-level analog of the quality gate pattern: just as SDT blocks promotion on validation failure, the test gate blocks artifact production on test failure.

The three parallel producers each address a distinct distribution channel. GoReleaser~\cite{goreleaser} produces cross-compiled platform binaries with SHA256 checksums and an auto-generated changelog, targeting direct CLI consumption. The Docker job produces container images with a semver-derived tagging strategy---full version, major.minor, and \texttt{latest}---that lets consumers choose their stability-versus-freshness trade-off: pinning to a patch version for reproducibility, tracking a minor version for compatible updates, or always using the latest release. The Helm job packages the chart and pushes it to the OCI registry (Section~\ref{subsec:oci-distribution}).

The key design property is \textit{version alignment}: the chart version, container image tags, and CLI binary version are all derived from the same Git tag. This single-source-of-truth mechanism ensures that consumers can verify artifact provenance---a chart version \texttt{2.0.0} always corresponds to image tag \texttt{2.0.0} and binary version \texttt{2.0.0}---without cross-referencing build logs. The parallel execution of all three producers minimizes release latency while the shared test gate ensures atomicity: either all three artifacts are produced from tested code, or none are.

\section{Operational Deployment}
\label{sec:operational-deployment}
% ============================================================================

The quality gate system follows a \textit{platform-inherited} deployment model: it does not install its own infrastructure but instead declares references to shared platform capabilities that are assumed to be present. This is a deliberate architectural choice that aligns with the separation between Day~0 (platform installation) and Day~1 (pipeline creation) described in Section~\ref{subsec:day0}. The proof-of-concept deployment runs on \texttt{private.novelcore.org}, a Kubernetes cluster managed by Kubecore.

% ----------------------------------------------------------------------------
\subsection{Prerequisites}
\label{subsec:prerequisites}
% ----------------------------------------------------------------------------

The deployment depends on six cluster components, each addressing a distinct concern in the quality gate lifecycle. Crossplane~\cite{crossplane} provides the declarative provisioning layer that translates \texttt{XSDLC} custom resources into managed child resources. ArgoCD~\cite{argocd} provides the GitOps synchronization layer that deploys applications from environment branches. Argo Workflows~\cite{argo-workflows} and Argo Events~\cite{argo-events} provide the event-driven execution layer that triggers and orchestrates validation pipelines. Traefik and cert-manager provide the network ingress layer that routes external webhooks and terminates TLS.

These components form a layered dependency: each layer addresses a distinct concern, and the DriveBy Helm chart creates resources that \textit{reference} components at each layer (Ingress resources reference the Traefik ingress class, certificate annotations reference the cert-manager issuer, workflow submissions reference the Argo Workflows controller) without installing them. This referencing model means that DriveBy can be added to any cluster that already runs these components---a common profile for cloud-native platform teams---without conflicting with existing installations or requiring dedicated infrastructure.

The proof-of-concept deployment on \texttt{private.novelcore.org} validates this surgical coexistence model. The cluster is Novelcore's internal development platform (IDP), built entirely on Kubernetes operators and Crossplane compositions, with ArgoCD, Argo Workflows, Argo Events, and Traefik already running in production for other workloads. GitHub is used as the SCM provider because Novelcore already operates on GitHub as its source control platform. DriveBy was installed into this \textit{existing, active cluster} without modifying any of these pre-existing installations---it created resources that reference them, not resources that replace them. The same property holds in reverse: deleting an \texttt{XSDLC} CR removes all DriveBy-managed child resources (WorkflowTemplates, Sensors, EventSources, Ingresses, BranchProtection rules) while leaving ArgoCD, Argo Workflows, and Argo Events completely untouched. Running \texttt{helm uninstall} removes the XRD and composition definitions themselves. At no point does installation or removal require restarting, reconfiguring, or redeploying any platform component. This surgical install/uninstall property is a direct consequence of the referencing model: because DriveBy never owns the infrastructure it depends on, removing DriveBy cannot destabilize the infrastructure it depends on.

% ----------------------------------------------------------------------------
\subsection{Verification}
\label{subsec:verification}
% ----------------------------------------------------------------------------

Post-deployment verification follows a layer-by-layer strategy, validating each abstraction level independently to isolate failures:

\begin{enumerate}
    \item \textbf{Declarative provisioning}: Confirming that all \texttt{XSDLC} composites report \texttt{READY=True} verifies that Crossplane successfully generated and reconciled all child resources. A non-ready composite indicates a composition rendering error or a provider authentication failure.

    \item \textbf{Event infrastructure}: Verifying that the EventBus, EventSource, and Sensor resources are healthy confirms that the event pipeline is operational. A failing EventBus typically indicates a NATS JetStream configuration issue; a failing Sensor indicates a filter or template reference error.

    \item \textbf{Network path}: Sending a test webhook payload to the Ingress endpoint and receiving a 200 response confirms the end-to-end network path from the external domain through the Ingress controller to the EventSource. A failure here isolates the problem to DNS resolution, TLS certificate provisioning, or ingress routing.

    \item \textbf{End-to-end behavior}: Opening a test PR on the monitored repository triggers a complete validation cycle. Verifying that the workflow completes, commit status appears on the PR, and a validation report is posted as a PR comment confirms that all layers---event pipeline, workflow orchestration, GitHub API integration, and commit status reporting---function together.
\end{enumerate}

\section{Summary}
\label{sec:pipeline-summary}
% ============================================================================

This chapter described the operational GitOps pipeline that connects DriveBy's validation engine to a fully declarative, Kubernetes-native software delivery lifecycle.

The central contribution is \textit{modularity through separation of concerns}. The BYOCI principle (Section~\ref{sec:two-repo}) draws a clean boundary: developers own their CI (build, test, image), while XSDLC owns delivery (promotion, quality gates, environment management). This separation means that onboarding a new API requires no pipeline authoring---a single \texttt{XSDLC} custom resource (\(\sim\)25 lines of YAML) provisions the complete delivery pipeline, including environment branches, ArgoCD Applications, webhook-triggered quality gates, and promotion automation.

The flow is straightforward. A developer commits updated dry manifests to the \texttt{main} branch of the gitops repository. The ArgoCD Source Hydrator renders each environment's Kustomize overlay and writes hydrated output to the corresponding \texttt{-next} branch. The GitOps Promoter creates a promotion PR from \texttt{-next} to the active branch. If a quality gate is defined, it fires automatically: the event-driven pipeline (Section~\ref{sec:event-pipeline-detail}) processes the webhook in under 90~seconds, running whatever checks the gate specifies---static validation, functional testing, load testing, or any combination. The gate result (commit status) determines whether the Promoter merges the PR or blocks it.

This composability is the key design property. Each gate's \texttt{checks[]} array is independently configurable per environment: staging might run \texttt{validate-only} + \texttt{functional-test}, production might run \texttt{validate-only} + \texttt{load-test} with stricter thresholds, and development might have no gate at all. Adding or removing checks is a one-line YAML change; the Crossplane composition regenerates the Argo Workflows DAG automatically.

The human-in-the-loop model (Section~\ref{sec:human-in-the-loop}) provides a tunable automation spectrum. The \texttt{autoMerge} flag controls whether promotion is fully automated (development, staging after gate passes) or requires explicit human approval (production). ArgoCD always auto-syncs; the \texttt{autoMerge} flag controls only the Promoter's PR merge behavior, not ArgoCD synchronization. The result is a system where objective assessments are automated and subjective decisions---production readiness, business timing---remain with humans.

The control-theoretic framing (Section~\ref{sec:control-loop}) explains \textit{why} this design converges: the OpenAPI specification is the setpoint, DriveBy is the sensor, and the Promoter is the actuator. Negative feedback blocks promotion on failure, driving developers to fix issues until their API conforms. The three SDT axioms---Completeness, Determinism, Observability---are necessary conditions for this loop to function, connecting the theoretical foundations of Chapter~\ref{ch:related-work} to the concrete implementation.

DriveBy's own release pipeline (Section~\ref{sec:cicd-driveby}) demonstrates that the project practices what it preaches: automated test gates, parallel artifact production (binaries, Docker images, Helm charts), and OCI-based distribution to the GitHub Container Registry.

Chapter~\ref{ch:evaluation} evaluates this system empirically, measuring SDT's effectiveness across controlled and large-scale settings.
