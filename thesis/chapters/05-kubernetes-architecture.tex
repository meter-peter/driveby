\chapter{Kubernetes Architecture}
\label{ch:kubernetes}

Chapter~\ref{ch:architecture} described the DriveBy CLI as a standalone validation binary. This chapter describes how that binary is embedded in a Kubernetes-native infrastructure that provisions quality gates declaratively, triggers validation from external events, and orchestrates multi-step validation pipelines as container-native workflows. The result is a system where creating a new API quality gate requires writing a single custom resource---the Kubernetes control plane handles the rest.

The architecture draws on four technologies: Crossplane~\cite{crossplane} for declarative resource provisioning, Argo Events~\cite{argo-events} for event-driven triggering, Argo Workflows~\cite{argo-workflows} for container-native pipeline orchestration, and the GitOps Promoter~\cite{gitops-promoter} for automated environment promotion. Each technology addresses a distinct concern in the quality gate lifecycle, and together they realize the ontological state reconciliation pattern introduced in Section~\ref{subsec:ontological-reconciliation} of Chapter~\ref{ch:related-work}.

% ============================================================================
\section{From CLI Tool to Custom Resource}
\label{sec:cli-to-cr-evolution}
% ============================================================================

The progression from Chapter~\ref{ch:architecture} to this chapter reflects a fundamental shift in how validation integrates into modern software delivery. Understanding this shift requires tracing the architectural evolution through five stages, each subsuming the previous while adding a new capability.

% ----------------------------------------------------------------------------
\subsection{Stage 1: Shell Script}
\label{subsec:stage-shell}
% ----------------------------------------------------------------------------

The earliest form of API validation is a shell pipeline: \texttt{curl} fetches the specification, \texttt{jq} extracts fields, and conditional logic checks for missing descriptions or undocumented error codes. This approach is immediate and requires no tooling beyond a POSIX shell. However, it lacks structure (checks are ad-hoc string matches), reusability (each API requires a custom script), and determinism (different developers write different checks with different thresholds). Shell scripts cannot produce structured reports, cannot be composed into pipelines, and cannot participate in automated decision-making.

% ----------------------------------------------------------------------------
\subsection{Stage 2: Go CLI}
\label{subsec:stage-cli}
% ----------------------------------------------------------------------------

The DriveBy CLI (Chapter~\ref{ch:architecture}) addresses these limitations by introducing typed principles, a version-agnostic spec abstraction (\texttt{APISpec}), a deterministic validation engine, and structured JSON reporting. The SDT framework defines nine principles (P001--P009); the CLI implements seven as \texttt{PrincipleChecker} instances (P001--P005, P008, P009), with P006 (functional testing) and P007 (performance testing) handled by dedicated test runners (Section~\ref{subsec:gate-types}). The same principle set runs on every specification, producing comparable, machine-readable results. The CLI is a self-contained binary with zero runtime dependencies---it can validate any reachable OpenAPI specification from any machine.

% ----------------------------------------------------------------------------
\subsection{Stage 3: Container Image}
\label{subsec:stage-container}
% ----------------------------------------------------------------------------

Packaging the CLI as an OCI container image (\texttt{ghcr.io/meter-peter/driveby}) adds portability across execution environments. The same binary that runs on a developer's laptop runs inside any container runtime---Docker, containerd, CRI-O---without dependency management. The container image is the unit of deployment for all subsequent stages: workflow steps, CI jobs, and Crossplane-managed workflows all reference the same image.

% ----------------------------------------------------------------------------
\subsection{Stage 4: Argo Workflow Step}
\label{subsec:stage-workflow}
% ----------------------------------------------------------------------------

Embedding the container image as a step in an Argo Workflows DAG adds event-driven execution, dependency ordering, artifact persistence, and exit handling. The CLI becomes one step in a larger pipeline that includes health checking, commit status posting, and PR commenting. Argo Events triggers the workflow from GitHub webhooks; the workflow orchestrates the validation and posts results back to the Git control plane. This stage transforms the CLI from a manual tool into an automated quality gate.

% ----------------------------------------------------------------------------
\subsection{Stage 5: Crossplane Custom Resource}
\label{subsec:stage-cr}
% ----------------------------------------------------------------------------

The final stage---the \texttt{XSDLC} custom resource described in Section~\ref{sec:xrd-design}---declares the entire pipeline as a single Kubernetes resource. One CR (\(\sim\)25 lines of YAML) generates all workflow templates, event sources, sensors, ingress routes, RBAC rules, promotion strategies, branch structures, and ArgoCD applications. The operator does not configure individual components; they declare the desired end state, and Crossplane's reconciliation loop provisions everything.

The key insight is that each stage \textit{subsumes} the previous. The CR still runs the same CLI binary, inside the same container image, as a step in the same Argo Workflows DAG. Nothing is discarded; each layer adds a new capability (portability, automation, declarative management) while preserving the core validation logic. This subsumption property means that the CLI's design decisions---the \texttt{APISpec} abstraction, the principle checker interface, the separation of concerns (Section~\ref{subsec:design-goals})---are not retrofits but foundational choices that enabled the entire progression.

% ----------------------------------------------------------------------------
\subsection{Limitations Driving the Transition}
\label{subsec:limitations-transition}
% ----------------------------------------------------------------------------

The standalone CLI (Stage 2), however well-designed, cannot satisfy the operational demands of continuous delivery at scale. Three limitations motivate the transition to Kubernetes-native infrastructure.

First, \textit{execution must be automated}. A CLI that a developer runs manually is useful for debugging but cannot serve as a quality gate. Quality gates must fire on every relevant event---a promotion pull request, a scheduled regression, a new deployment---without human intervention. This requires an event-driven execution model that the CLI alone cannot provide.

Second, \textit{configuration must be declarative}. When validation is imperative (``run this command with these flags''), the configuration lives in scripts, CI pipelines, or developer knowledge. When validation is declarative (``this API must pass strict SDT validation before promotion to staging''), the configuration is a versioned, reconcilable Kubernetes resource. The declarative model enables drift detection, audit trails, and self-healing---properties that imperative scripts lack.

Third, \textit{results must drive automated decisions}. The CLI produces a JSON report and an exit code. These outputs are sufficient for a human reviewer but insufficient for a GitOps reconciliation loop. The promotion system requires structured commit statuses, webhook callbacks, and status conditions---signals that integrate with the Kubernetes and Git control planes rather than relying on stdout parsing.

These three limitations map directly to three abstraction layers. The CLI (Chapter~\ref{ch:architecture}) provides the \textit{validation logic}---the principle checkers, the spec abstraction, the report generator. The Kubernetes infrastructure (this chapter) provides the \textit{execution and provisioning layer}---Crossplane XRDs declare what gates exist, Argo Events trigger them, Argo Workflows orchestrate them. The GitOps pipeline (Chapter~\ref{ch:workflow}) provides the \textit{decision layer}---commit statuses gate promotion, the GitOps Promoter advances environments, ArgoCD reconciles the desired state.

The critical enabler of this progression is the CLI's architecture itself. The \texttt{types} package (zero internal dependencies) and the \texttt{spec.APISpec} interface (version-agnostic) make the validation logic portable across execution environments. The same principle checkers that run in a developer's terminal run inside an Argo Workflow container---the only difference is how the binary is invoked and where the results are consumed. The CLI was not retrofitted for Kubernetes integration; its separation of concerns (Section~\ref{subsec:design-goals}) was designed to support multiple deployment models from the outset.

The remainder of this chapter describes the Kubernetes-native layer: the controller pattern that underpins all operations (Section~\ref{sec:controller-pattern}), how Crossplane XRDs declare quality gates as custom resources (Section~\ref{sec:xrd-design}), the declarative lifecycle from installation through continuous operation (Section~\ref{sec:lifecycle-management}), and how Argo Events and Workflows execute validation pipelines (Sections~\ref{sec:argo-events-arch} and~\ref{sec:argo-workflows-dag}).

\section{Architecture Overview}

% ----------------------------------------------------------------------------
\subsection{Design Goals}
\label{subsec:k8s-design-goals}
% ----------------------------------------------------------------------------

The Kubernetes architecture is shaped by four design goals:

\begin{enumerate}
    \item \textbf{Declarative provisioning.} An operator declares what quality gates should exist; the system provisions all required infrastructure (event sources, sensors, workflows, ingress routes, RBAC) automatically. No imperative scripts or manual kubectl commands.

    \item \textbf{Separation of shared and per-API concerns.} Validation logic (the workflow template, RBAC, service accounts) is defined once and shared across all APIs. Event routing (webhooks, sensors, ingress) is defined per API. Changes to the shared validation pipeline propagate to all APIs without per-API updates.

    \item \textbf{Multi-environment awareness.} The system validates against a source environment (typically development) and gates promotion to a target environment (typically staging or production). This inversion---validating the source, not the target---ensures that quality is assessed before deployment, not after.

    \item \textbf{Progressive configurability.} Sensible defaults enable a minimal-configuration deployment. Every default can be overridden at two levels: chart-wide (Helm values) and per-resource (XRD spec fields).

    \item \textbf{Platform inheritance.} The system assumes the existence of shared platform capabilities---ArgoCD, Crossplane, Argo Events, Argo Workflows, Traefik, cert-manager---and references them rather than installing them. The application developer never configures TLS certificates, ingress controllers, or event buses directly; these are managed by the platform team and inherited by every \texttt{XSDLC} resource that references them.
\end{enumerate}

\section{The Kubernetes Controller Pattern}
\label{sec:controller-pattern}
% ============================================================================

Before describing the specific resources that constitute the DriveBy quality gate system, it is necessary to formalize the operational model that governs them. Every resource described in this chapter---from the \texttt{XSDLC} custom resource to individual Sensors and WorkflowTemplates---is managed by a Kubernetes controller that continuously reconciles declared state against observed reality. This section describes the controller pattern, its consistency guarantees, and how Crossplane extends it to serve as a universal control plane.

% ----------------------------------------------------------------------------
\subsection{The Reconciliation Loop}
\label{subsec:reconciliation-loop}
% ----------------------------------------------------------------------------

A Kubernetes controller implements a three-phase cycle: \textit{observe}, \textit{diff}, and \textit{act}~\cite{k8s-controllers}. In the observe phase, the controller reads the current state of the resources it manages---both the desired state declared in the resource's \texttt{spec} and the actual state reported in its \texttt{status} or observed from the cluster. In the diff phase, the controller computes the difference between the desired and actual states. In the act phase, the controller takes corrective action to drive the actual state toward the desired state: creating missing resources, updating drifted configurations, or deleting obsolete objects.

This cycle is \textit{level-triggered}, not \textit{edge-triggered}~\cite{k8s-up-and-running}. An edge-triggered system reacts to \textit{events}---it must observe every state change as it happens, and if it misses one (due to a crash, network partition, or restart), the missed event is lost. A level-triggered system reacts to \textit{state}---it periodically re-evaluates the current condition and takes action based on what it observes, regardless of how the system arrived at that state. If a controller crashes and restarts, it re-reads the current state and reconciles from scratch. No events are lost because no events need to be recorded; the state itself is the complete input.

The practical consequence is robustness. A Kubernetes controller can be killed, restarted, scaled horizontally, or temporarily disconnected without losing track of what it manages. When it resumes, it observes the current state and acts accordingly. This property is fundamental to the self-healing guarantees described in Section~\ref{subsec:self-healing}.

% ----------------------------------------------------------------------------
\subsection{Eventual Consistency and Self-Healing}
\label{subsec:self-healing}
% ----------------------------------------------------------------------------

Kubernetes does not guarantee immediate consistency. When a user creates an \texttt{XSDLC} resource, the system does not synchronously provision all child resources before returning. Instead, it accepts the declaration and returns immediately. The composition controller observes the new resource on its next reconciliation cycle, computes the desired children, and begins provisioning them. Each child resource is itself subject to its own controller's reconciliation loop. The system \textit{converges} toward the desired state over multiple reconciliation cycles, with each cycle reducing the gap between declared and actual state.

This eventual consistency model enables self-healing. If an operator manually deletes a Sensor resource that was generated by the \texttt{XSDLC} composition, the composition controller detects the missing child on its next reconciliation pass and re-creates it. No human intervention is required; no alert needs to fire; the system simply converges back to the declared state. The same mechanism handles configuration drift: if someone modifies a generated WorkflowTemplate, the composition controller detects the discrepancy and overwrites the manual change with the correct generated configuration.

This property connects directly to the ontological state reconciliation pattern introduced in Section~\ref{subsec:ontological-reconciliation} of Chapter~\ref{ch:related-work}. The \texttt{XSDLC} spec is the ontological artifact---the explicit specification of what should exist. The Crossplane composition controller is the reconciliation agent. The act of re-creating deleted resources or reverting drifted configurations is the correction mechanism. The three components of ontological state reconciliation are instantiated concretely in the Kubernetes controller model.

% ----------------------------------------------------------------------------
\subsection{Crossplane as Universal Control Plane}
\label{subsec:crossplane-control-plane}
% ----------------------------------------------------------------------------

Crossplane~\cite{crossplane} extends the Kubernetes controller pattern by allowing custom resources to declare not just in-cluster objects but any resource reachable through a provider API. A standard Kubernetes controller manages Pods, Services, and ConfigMaps. A Crossplane-managed composition can manage those same resources \textit{plus} cloud databases, DNS records, GitHub branches, and any other resource for which a Crossplane provider exists~\cite{crossplane-compositions}.

The \texttt{XSDLC} composition leverages this extension to manage resources across two control planes simultaneously. In-cluster resources (ServiceAccount, EventBus, WorkflowTemplate, ArgoCD Application, secrets) are provisioned through \texttt{provider-kubernetes}. GitHub resources (Repository, RepositoryFile, Branch, BranchProtection) are provisioned through \texttt{provider-upjet-github}. From the operator's perspective, this distinction is invisible: one \texttt{XSDLC} custom resource declares the entire pipeline, and the composition delegates each child resource to the appropriate provider.

Crossplane compositions function as \textit{meta-controllers}. A standard controller watches one resource type and reconciles its state directly. A Crossplane composition watches a composite resource (the XRD) and generates \textit{desired state for other controllers}. The composition's \texttt{function-go-templating} step renders the desired children; \texttt{function-auto-ready} aggregates their readiness. Each generated child is then reconciled by its own provider controller. This two-level reconciliation---composition generates desired children, providers reconcile each child against its target system---is what enables a single 25-line YAML declaration to produce and maintain a pipeline of approximately 44 managed resources.

% ----------------------------------------------------------------------------
\subsection{Provider Architecture}
\label{subsec:provider-architecture}
% ----------------------------------------------------------------------------

The \texttt{XSDLC} composition delegates resource management to two Crossplane providers:

\textbf{\texttt{provider-kubernetes}} (v0.14.1) manages all in-cluster resources. It uses \texttt{InjectedIdentity} for authentication, meaning it inherits the permissions of the Crossplane pod's service account. Every in-cluster resource generated by the composition---ServiceAccount, EventBus, Role, RoleBinding, WorkflowTemplate, EventSource, Sensor, Service, Ingress, PromotionStrategy, GitRepository, ScmProvider, ArgoCD Application, ArgoCD push secret, and per-namespace ghcr-creds secrets---is wrapped in a \texttt{provider-kubernetes} \texttt{Object} resource. The provider reconciles each \texttt{Object} by applying the embedded manifest to the cluster.

\textbf{\texttt{provider-upjet-github}} (v0.18.0) manages GitHub API resources. It authenticates via a GitHub personal access token stored in a Kubernetes secret. The provider exposes GitHub resources as Kubernetes custom resources: \texttt{Repository}, \texttt{Branch}, \texttt{BranchProtection}, and \texttt{RepositoryFile}. The composition generates these resources to auto-create a dedicated GitOps repository, seed it with boilerplate dry manifests, provision environment branches within it, and enforce branch protection rules.

The single-composition, dual-provider model means that the operator interacts with one Kubernetes API (\texttt{driveby.io/v1alpha1 XSDLC}) while the system manages resources across two distinct control planes---the Kubernetes cluster and the GitHub API---from a single custom resource declaration.

\section{Crossplane XRD Design}
\label{sec:xrd-design}
% ============================================================================

The quality gate infrastructure is provisioned through a single Crossplane Composite Resource Definition (XRD): \texttt{XSDLC} (API group \texttt{driveby.io/v1alpha1}). This single-CR model replaces an earlier two-XRD design that separated shared and per-API resources into distinct custom resources. The consolidation into a single XRD reduces the operator's cognitive load and deployment surface: one custom resource defines the entire SDLC pipeline for an application.

% ----------------------------------------------------------------------------
\subsection{XSDLC: Single-CR Pipeline Definition}
\label{subsec:xrd-xsdlc}
% ----------------------------------------------------------------------------

The \texttt{XSDLC} XRD requires only two fields: \texttt{gitopsRepository} (the GitHub owner and gitops repository name) and \texttt{environments} (the ordered list of environments in the promotion chain). The software repository is never referenced---XSDLC manages only the gitops repo. From these two inputs, the composition generates all resources needed for the full software delivery lifecycle pipeline.

A single \texttt{XSDLC} custom resource generates three categories of resources. \textit{App-level shared resources} are created once per CR:

\begin{enumerate}
    \item A \textbf{ServiceAccount} with image pull credentials for accessing the DriveBy container image from the GitHub Container Registry.
    \item An \textbf{EventBus} backed by NATS JetStream~\cite{nats-jetstream} for reliable event delivery between EventSources and Sensors.
    \item A \textbf{ScmProvider} authenticating to GitHub via a GitHub App.
    \item A \textbf{GitRepository} pointing to the GitOps repository.
    \item A \textbf{GitHub Repository} auto-creating a dedicated gitops repository.
    \item \textbf{RepositoryFiles} seeding the gitops repository with boilerplate dry manifests (base deployment, service, and kustomization).
    \item An \textbf{ArgoCD push secret} granting the Source Hydrator write access to the gitops repository.
    \item A \textbf{BranchProtection} rule protecting all \texttt{*-next} branches in the gitops repository.
\end{enumerate}

\textit{Per-environment resources} are created for each environment in the promotion chain:

\begin{enumerate}
    \item A \textbf{PromotionStrategy} defining the environment's auto-merge policy and commit status gates.
    \item Two \textbf{Branches} in the gitops repository (the environment branch and its \texttt{-next} counterpart).
    \item A \textbf{RepositoryFile} seeding the per-environment Kustomize overlay.
    \item A \textbf{ghcr-creds} secret copied into the environment namespace for image pull authentication.
    \item An \textbf{ArgoCD Application} using Source Hydrator to render the environment's overlay.
\end{enumerate}

\textit{Per-gate resources} are created for each environment that defines a \texttt{gate}:

\begin{enumerate}
    \item A \textbf{Role} granting permissions to create and manage Argo Workflows, read secrets and configmaps, manage persistent volume claims, and create and update CommitStatus custom resources.
    \item A \textbf{RoleBinding} associating the service account with the role.
    \item A \textbf{WorkflowTemplate} containing the validation DAG described in Section~\ref{sec:argo-workflows-dag}.
    \item An \textbf{EventSource} configured as a webhook listener on a configurable port (default: 12000).
    \item A \textbf{Sensor} that filters events (e.g., only \texttt{pull\_request} events with actions \texttt{opened}, \texttt{reopened}, or \texttt{synchronize}) and submits workflow runs with extracted parameters.
    \item A \textbf{Service} exposing the EventSource webhook.
    \item An \textbf{Ingress} with TLS termination (via cert-manager) routing external webhook traffic to the EventSource service.
    \item A \textbf{BranchProtection} rule requiring the gate's commit status check before merging into the environment branch.
\end{enumerate}

% ----------------------------------------------------------------------------
\subsection{Multi-Check Gate Model}
\label{subsec:multi-check-gates}
\label{subsec:gate-types}
% ----------------------------------------------------------------------------

Quality gates in the \texttt{XSDLC} model are composed from an ordered \texttt{checks[]} array. Each check becomes a sequential step in the Argo Workflows DAG, enabling gates that combine multiple validation concerns in a single promotion decision. Three check types are supported, each mapping to a distinct SDT concern:

\begin{itemize}
    \item \textbf{\texttt{validate-only}} --- runs the DriveBy CLI in static validation mode, evaluating the specification-level principles (P001--P005, P008, P009 in strict mode; a subset in minimal mode). Accepts an optional \texttt{validationConfig.validationMode} override.
    \item \textbf{\texttt{functional-test}} --- runs the DriveBy CLI in \texttt{function-only} mode, executing P006 functional tests against the live API in the source environment. Validates runtime behavioral conformance: correct response schemas, proper error codes, authenticated endpoint behavior.
    \item \textbf{\texttt{load-test}} --- runs the DriveBy CLI in \texttt{load-only} mode, executing vegeta-based load testing (P007) with configurable parameters: \texttt{concurrentUsers} (default: 10), \texttt{testDuration} (default: \texttt{5m}), \texttt{maxLatencyP95} (default: \texttt{500ms}), and \texttt{minSuccessRate} (default: 0.99).
\end{itemize}

The composition generates DAG steps with deterministic naming: \texttt{check-0-validate-only}, \texttt{check-1-functional-test}, and so on. Each step depends on the previous, forming a sequential chain. This ordering ensures that cheaper checks (static validation) run before expensive checks (load testing), failing fast when possible.

Different environment transitions compose different subsets. For the staging gate:

\begin{verbatim}
gate:
  checks:
    - type: validate-only
    - type: functional-test
\end{verbatim}

For the production gate:

\begin{verbatim}
gate:
  checks:
    - type: validate-only
    - type: load-test
      loadTestConfig:
        concurrentUsers: 50
        testDuration: "10m"
        maxLatencyP95: "200ms"
\end{verbatim}

% ----------------------------------------------------------------------------
\subsection{Minimal Configuration}
\label{subsec:minimal-config}
% ----------------------------------------------------------------------------

Listing~\ref{lst:xsdlc-cr} shows a representative \texttt{XSDLC} instance. The entire SDLC pipeline for the \texttt{perfect-api} application---three environments, a validation gate for staging promotion, and a load test gate for production promotion---is defined in approximately 25 lines of YAML.

\begin{lstlisting}[caption={XSDLC custom resource defining a three-environment pipeline with quality gates.},label={lst:xsdlc-cr}]
apiVersion: driveby.io/v1alpha1
kind: XSDLC
metadata:
  name: perfect-api
  namespace: driveby
spec:
  gitopsRepository:
    owner: novelcore
    name: perfect-api-gitops
  environments:
    - name: dev
    - name: staging
      gate:
        checks:
          - type: validate-only
          - type: functional-test
    - name: prod
      autoMerge: false
      gate:
        checks:
          - type: validate-only
          - type: load-test
\end{lstlisting}

From this declaration, Crossplane generates the shared resources (ServiceAccount, EventBus, ScmProvider, GitRepository, PromotionStrategy, ArgoCDCommitStatus) and the per-gate resources (RBAC, WorkflowTemplate, EventSource, Sensor, Service, Ingress) for each gated environment. The operator writes approximately 15 lines of meaningful configuration; the composition generates several hundred lines of Kubernetes manifests. All cluster-specific configuration---domain, image references, secret names, ingress class, certificate issuer---is inherited from Helm values, following the two-tier configuration model described in Section~\ref{sec:two-tier-config}.

Figure~\ref{fig:xrd-resource-hierarchy} visualizes the resource hierarchy generated by the \texttt{XSDLC} XRD.

\begin{figure}[htbp]
\centering

The single-CR model eliminates the template-instance indirection of the earlier two-XRD design. Rather than creating a template and then instantiating it per API, the operator declares the full pipeline in one resource. The composition handles the separation of shared and per-gate concerns internally. Adding a new API to the quality gate system requires creating one \texttt{XSDLC} custom resource; no other resources need to be created or modified.

\section{Declarative Lifecycle Management}
\label{sec:lifecycle-management}
% ============================================================================

The controller pattern and provider architecture described in Sections~\ref{sec:controller-pattern} and~\ref{subsec:provider-architecture} provide the theoretical and mechanical foundations. This section describes how these foundations manifest in the operational lifecycle of the quality gate system---from platform installation through pipeline creation, continuous operation, and eventual decommissioning.

% ----------------------------------------------------------------------------
\subsection{Day 0: Platform Installation}
\label{subsec:day0}
% ----------------------------------------------------------------------------

The Helm chart installs the \textit{platform layer}: the XRD definition, the composition template, the ProviderConfig for \texttt{provider-kubernetes}, the ProviderConfig for \texttt{provider-upjet-github}, and the Crossplane functions (\texttt{function-go-templating}, \texttt{function-auto-ready}). At this point, no \texttt{XSDLC} instances exist. The platform is ready to accept declarations but has not yet provisioned any quality gate infrastructure.

This separation between platform installation and pipeline creation is deliberate. The platform team installs the Helm chart once per cluster. Application teams create \texttt{XSDLC} custom resources independently, without requiring platform team involvement for each new API. The platform provides the \textit{capability}; individual CRs exercise it.

% ----------------------------------------------------------------------------
\subsection{Day 1: Pipeline Creation}
\label{subsec:day1}
% ----------------------------------------------------------------------------

When an operator applies an \texttt{XSDLC} custom resource, the Crossplane composition controller detects the new resource on its next reconciliation cycle and begins generating child resources. For the reference deployment (\texttt{perfect-api} with three environments and two quality gates), the composition generates approximately 44 child resources: the GitOps Repository, ServiceAccount, EventBus, ScmProvider, GitRepository, ArgoCD push secret, three PromotionStrategies, three ArgoCD Applications, six Branches, four RepositoryFiles (base manifests and per-environment overlays), three ghcr-creds secrets, BranchProtection rules, and the per-gate resources (Role, RoleBinding, WorkflowTemplate, EventSource, Sensor, Service, Ingress) for each gated environment.

Each child resource is itself subject to its provider's reconciliation loop. The \texttt{provider-kubernetes} controller applies each in-cluster manifest; the \texttt{provider-upjet-github} controller creates the gitops repository and its branches. The \texttt{function-auto-ready} function monitors all children and marks the \texttt{XSDLC} composite as \texttt{READY=True} only when every child has reached its own ready state.

Figure~\ref{fig:crossplane-reconciliation-loop} illustrates this reconciliation cycle.

\subsection{Day 2: Continuous Reconciliation}
\label{subsec:day2}
% ----------------------------------------------------------------------------

Once the pipeline is created, the controller pattern ensures continuous reconciliation. Two scenarios illustrate this property.

\textbf{Drift detection.} If an operator or automated process modifies a Crossplane-managed resource---for example, changing the Sensor's filter configuration---the composition controller detects the discrepancy on its next reconciliation pass and overwrites the change with the correct generated configuration. The \texttt{XSDLC} spec is the single source of truth; any deviation from the generated state is treated as drift and corrected.

\textbf{Self-healing.} If a managed resource is deleted---for example, \texttt{kubectl delete sensor perfect-api-staging-gate-sensor}---the composition controller detects the missing child and re-creates it. The provider reconciles the re-created resource against the cluster, and the pipeline returns to its declared state without human intervention.

The composition uses two deletion policies to distinguish shared and per-pipeline resources. \textit{Shared resources} (ServiceAccount, EventBus) use \texttt{deletionPolicy: Orphan}. If the \texttt{XSDLC} CR is deleted, these resources are left in place because other \texttt{XSDLC} instances in the same namespace may depend on them. \textit{Per-pipeline resources} (ScmProvider, GitRepository, PromotionStrategy, WorkflowTemplate, EventSource, Sensor, ghcr-creds secrets, ArgoCD push secret, and all per-gate resources) use \texttt{deletionPolicy: Delete}. When the \texttt{XSDLC} CR is deleted, these resources are cascade-deleted because they are specific to the pipeline being decommissioned. Similarly, GitHub \texttt{Branch} and \texttt{RepositoryFile} resources use \texttt{deletionPolicy: Orphan} to preserve branch history and manifest content even when the pipeline is removed.

% ----------------------------------------------------------------------------
\subsection{Day N: Updates and Deletion}
\label{subsec:day-n}
% ----------------------------------------------------------------------------

\textbf{Updates.} Modifying the \texttt{XSDLC} spec triggers a reconciliation delta. Adding a new environment generates the new ArgoCD Application, branches, and (if gated) per-gate resources. Removing an environment deletes the corresponding children. Changing a gate's check types regenerates the WorkflowTemplate with the updated DAG. The composition is \textit{idempotent}: applying the same spec twice produces no changes; applying a modified spec produces exactly the changes needed to reach the new desired state.

\textbf{Deletion.} Deleting the \texttt{XSDLC} CR triggers cascade deletion for all children with \texttt{deletionPolicy: Delete}. Resources with \texttt{deletionPolicy: Orphan} (ServiceAccount, EventBus, Branches) remain. This selective cascade ensures that shared infrastructure survives individual pipeline removal while pipeline-specific resources are cleaned up.

    \item \texttt{ready} (boolean): overall readiness, set by \texttt{function-auto-ready} when all children are healthy.
    \item \texttt{environmentCount} (integer): number of environments in the promotion chain.

\section{Composition Pipeline}
\label{sec:composition-pipeline}
% ============================================================================

% ----------------------------------------------------------------------------
\subsection{Pipeline-Mode Compositions}
\label{subsec:pipeline-mode}
% ----------------------------------------------------------------------------

The \texttt{XSDLC} XRD uses Crossplane's pipeline-mode composition, which processes the composite resource through a sequence of functions rather than relying on the legacy patch-and-transform approach. The composition pipeline follows a two-step pattern:

\begin{enumerate}
    \item \textbf{function-go-templating}: Renders Kubernetes manifests from Go templates, with access to the XRD spec and Helm-injected defaults. This function performs the bulk of the work: it iterates over the environments list, generates shared resources once and per-gate resources for each gated environment, resolves the two-tier configuration precedence, and handles the template escaping required when generating Argo Workflows templates that themselves contain Go template syntax.
    \item \textbf{function-auto-ready}: Automatically marks the composite resource as ready when all composed resources reach their ready state.
\end{enumerate}

The go-templating function evaluates the \texttt{checks[]} array per gate, generating the appropriate step templates (\texttt{driveby-validate}, \texttt{driveby-functional}, \texttt{driveby-loadtest}) based on each check's type. It resolves configuration values from either the XRD spec or Helm defaults and produces the complete set of Kubernetes manifests from a single template.

% ----------------------------------------------------------------------------
\subsection{Template Escaping}
\label{subsec:template-escaping}
% ----------------------------------------------------------------------------

A notable engineering challenge arises from the nested templating layers. The Crossplane composition uses Go templates to generate Argo Workflows manifests, which themselves use Go template syntax for parameter substitution (e.g., \texttt{\{\{workflow.parameters.app-name\}\}}). Without escaping, the Crossplane go-templating function would attempt to evaluate the Argo template expressions during composition rendering, causing failures.

The solution uses a double-escaping convention. Argo template expressions within the composition are written as:

\begin{verbatim}
{{ "{{" }}workflow.parameters.app-name{{ "}}" }}
\end{verbatim}

The outer Go template evaluates \verb|{{"{{" }}| to produce the literal string \verb|{{|, and similarly for the closing braces. The resulting manifest contains the intended Argo expression \verb|{{workflow.parameters.app-name}}| verbatim. This escaping is applied consistently across all workflow step definitions in the template composition.

% ----------------------------------------------------------------------------
\subsection{Generated GitHub Resources}
\label{subsec:generated-github}
% ----------------------------------------------------------------------------

When the GitHub provider is enabled, the \texttt{XSDLC} composition generates three categories of GitHub resources, all managed through \texttt{provider-upjet-github}.

\textbf{Branches.} For each environment in the promotion chain, the composition generates two branches: \texttt{environment/<name>} (the active branch that ArgoCD watches) and \texttt{environment/<name>-next} (the proposed branch where developers push manifest changes). Both branches are created in the dedicated gitops repository and sourced from its \texttt{main} branch. They use \texttt{deletionPolicy: Orphan} to preserve Git history when the pipeline is removed. For a three-environment pipeline, this produces six branches.

\textbf{Repository.} The composition auto-creates a dedicated GitOps repository under the same GitHub owner (e.g., \texttt{novelcore/perfect-api-gitops}). This repository is private and uses \texttt{deletionPolicy: Orphan} to preserve the repository when the XSDLC CR is deleted. The gitops repo holds Kubernetes manifests on per-environment branches; the software repository is never modified by XSDLC.

\textbf{Branch protection.} When enabled, the composition generates \texttt{BranchProtection} rules for gated environments. Each gated environment's active branch requires the corresponding commit status check to pass before merging. The \texttt{-next} branches receive protection to prevent accidental overwrites.

The key insight is that the GitOps repository and its branch topology are \textit{generated infrastructure}, not hand-authored configuration. The composition maintains them as part of the reconciliation loop, just as it maintains in-cluster resources. This eliminates manual repository setup: the operator declares the application and its environments, and the platform provisions the repository, branches, protection rules, and ArgoCD applications.

% ----------------------------------------------------------------------------
\subsection{ArgoCD Application Generation}
\label{subsec:argocd-generation}
% ----------------------------------------------------------------------------

The composition generates an ArgoCD Application for every environment in the promotion chain, not just gated environments. Every Application uses the ArgoCD Source Hydrator~\cite{argocd-hydrator} rather than a traditional \texttt{source} block. Each Application's \texttt{sourceHydrator} configuration points to the environment's Kustomize overlay on the \texttt{main} branch:

\begin{itemize}
    \item \texttt{drySource}: the gitops repository, path \texttt{dry/overlays/<envName>}, revision \texttt{main}
    \item \texttt{syncSource}: the environment's active branch (\texttt{environment/<name>}), path \texttt{manifests}
    \item \texttt{hydrateTo}: the environment's proposed branch (\texttt{environment/<name>-next})
\end{itemize}

When a developer updates dry manifests on the \texttt{main} branch, the hydrator renders the Kustomize overlay for each environment and writes the hydrated output---along with a \texttt{hydrator.metadata} file containing the dry commit SHA---to the corresponding \texttt{-next} branch. The GitOps Promoter detects the new commit on the \texttt{-next} branch and creates a promotion PR to the active branch. Quality gates fire on those PRs; ArgoCD syncs from the active branch's \texttt{manifests/} path once the PR is merged.

This per-environment overlay model provides three properties. First, each environment can customize its deployment independently (replicas, resource limits, environment variables, image tags) via its own Kustomize overlay without affecting other environments. Second, deploying to a specific environment requires only updating its overlay on \texttt{main}---there is no linear propagation chain where content must flow through earlier environments. Third, the \texttt{hydrator.metadata} file satisfies the GitOps Promoter's contract for tracking dry-to-hydrated commit provenance.

All generated Applications are configured with \texttt{automated.selfHeal: true} and \texttt{automated.prune: true}. ArgoCD automatically synchronizes changes and self-heals drifted resources regardless of the \texttt{autoMerge} setting. The \texttt{autoMerge} field exclusively controls the GitOps Promoter's behavior: when \texttt{true} (default), the Promoter automatically merges promotion PRs after gates pass; when \texttt{false}, the PR remains open for human review. This decoupling is deliberate---ArgoCD should always reflect the state of the environment branch, while the promotion decision (whether to update that branch) is where human judgment applies.

All generated Applications include \texttt{CreateNamespace=true} in their sync options, ensuring that the target namespace is created automatically if it does not exist. Each Application carries labels (\texttt{driveby.io/app}, \texttt{driveby.io/environment}) that enable the ArgoCDCommitStatus resource to aggregate health signals across all environments.

\textbf{Tier~1: Helm values} (\texttt{values.yaml}) provide chart-wide defaults that apply to all resources generated by the Helm chart. The elimination of the intermediate EnvironmentConfig tier---present in an earlier three-tier design---simplifies both the mental model and the composition logic without sacrificing meaningful flexibility.

\section{Argo Events Architecture}
\label{sec:argo-events-arch}
% ============================================================================

Argo Events provides the event-driven layer that connects external triggers (GitHub webhooks) to internal actions (workflow submissions). The architecture uses three Argo Events resources, each generated by the \texttt{XSDLC} composition for every environment that defines a quality gate.

% ----------------------------------------------------------------------------
\subsection{EventBus}
\label{subsec:eventbus}
% ----------------------------------------------------------------------------

The EventBus is the message transport layer between EventSources and Sensors. It is backed by NATS JetStream~\cite{nats-jetstream}, which provides persistent, at-least-once delivery semantics. The EventBus must be named \texttt{default} within each namespace (an Argo Events convention) and is configured with a single replica for the development deployment, though production deployments would scale to three replicas for high availability.

The JetStream backing ensures that webhook events are not lost if the Sensor is temporarily unavailable. Events are persisted to the JetStream stream and replayed when the Sensor reconnects, providing reliability without requiring external message queue infrastructure.

% ----------------------------------------------------------------------------
\subsection{EventSource}
\label{subsec:eventsource}
% ----------------------------------------------------------------------------

The EventSource is the ingress point where external events enter the Kubernetes-native event pipeline. It runs as an HTTP server that listens for incoming webhook payloads on a configurable port (default: 12000). The webhook model is chosen over polling because quality gate triggers are inherently event-driven---a promotion PR is opened, a deployment completes---and webhook delivery provides near-real-time notification without the latency overhead and API rate-limit pressure of periodic polling.

Each quality gate generates a named webhook endpoint following a deterministic naming convention: \texttt{/<appName>-<envName>-gate-pr-trigger}. This naming convention is the same mechanism that drives the Ingress and GitHub webhook configuration (Section~\ref{subsec:generated-github}): the composition derives all three resources---EventSource endpoint, Ingress route, and GitHub webhook URL---from the same two identity fields (application name and environment name), guaranteeing that they agree without manual coordination. For the staging gate of the reference \texttt{perfect-api} deployment, this produces the endpoint \texttt{/perfect-api-staging-gate-pr-trigger}.

The EventSource receives the raw webhook payload, validates its structure, and publishes it to the EventBus (Section~\ref{subsec:eventbus}). This decouples event reception from event processing: the EventSource's only responsibility is to accept and forward events. Filtering (which events are relevant) and action-triggering (submitting workflows) are delegated entirely to the Sensor, maintaining a clean separation of concerns within the event pipeline.

% ----------------------------------------------------------------------------
\subsection{Sensor and Parameter Extraction}
\label{subsec:sensor}
% ----------------------------------------------------------------------------

The Sensor subscribes to events from the EventBus, applies filtering logic, and triggers workflow submissions when filter conditions are met. For pull request validation, the Sensor filters on:

\begin{itemize}
    \item Event type: \texttt{pull\_request}
    \item Action: \texttt{opened}, \texttt{reopened}, or \texttt{synchronize}
\end{itemize}

This filtering ensures that workflows are triggered only for meaningful PR events---new PRs, reopened PRs, or new commits pushed to existing PRs---and not for label changes, review requests, or other non-code events.

When a matching event arrives, the Sensor extracts parameters from the webhook payload using JSONPath expressions and passes them to the workflow submission. Table~\ref{tab:sensor-params} lists the extracted parameters.

\section{Argo Workflows Validation DAG}
\label{sec:argo-workflows-dag}
% ============================================================================

The validation pipeline is implemented as an Argo Workflows WorkflowTemplate containing a directed acyclic graph (DAG). Unlike fixed pipelines, the DAG is \textit{dynamically generated} by the Crossplane composition based on the gate's \texttt{checks[]} array (Section~\ref{subsec:multi-check-gates}). The Sensor submits workflow runs from this template, passing the extracted parameters.

% ----------------------------------------------------------------------------
\subsection{Pipeline Steps}
\label{subsec:pipeline-steps}
% ----------------------------------------------------------------------------

The DAG follows a fixed preamble, a dynamic checks section, and a fixed postamble:

\textbf{Preamble (fixed steps):}

\begin{enumerate}
    \item \textbf{set-pending-status}: Posts a ``pending'' commit status to the PR's head SHA via the GitHub API. A parallel step (\textbf{update-commitstatus-pending}) creates a CommitStatus custom resource with phase \texttt{pending} for the GitOps Promoter.

    \item \textbf{wait-for-source-ready}: Polls the source environment (e.g., \texttt{perfect-api-dev}) to verify that the API deployment is healthy. The step performs up to 60 health checks at 5-second intervals (5 minutes maximum), using \texttt{curl} to probe the API's OpenAPI endpoint. This wait ensures that validation does not run against a partially deployed or restarting instance.
\end{enumerate}

\textbf{Dynamic checks (from \texttt{checks[]} array):}

For each check in the gate's ordered \texttt{checks[]} array, the composition generates a DAG step named \texttt{check-<index>-<type>}. Each step depends on the previous step, forming a sequential chain. The step template is selected by check type:

\begin{itemize}
    \item \texttt{validate-only} $\rightarrow$ \texttt{driveby-validate}: Runs the DriveBy CLI with the configured validation mode. The container image \texttt{ghcr.io/meter-peter/driveby:latest} executes with flags derived from the check's \texttt{validationConfig}. The validation report is stored on a shared PVC at \texttt{/tmp/reports}.
    \item \texttt{functional-test} $\rightarrow$ \texttt{driveby-functional}: Runs the DriveBy CLI in \texttt{function-only} mode against the live API. Authentication credentials are injected from Kubernetes secrets.
    \item \texttt{load-test} $\rightarrow$ \texttt{driveby-loadtest}: Runs the DriveBy CLI in \texttt{load-only} mode with vegeta-based load testing, parameterized from the check's \texttt{loadTestConfig} (concurrent users, duration, P95 threshold, success rate).
\end{itemize}

\textbf{Postamble (fixed steps, parallel after last check):}

\begin{enumerate}
    \item \textbf{report-success}: Posts a ``success'' commit status to the PR's head SHA.
    \item \textbf{comment-pr}: Posts the validation report as a comment on the pull request, reading saved reports from the shared PVC via DriveBy's \texttt{github-comment} command.
    \item \textbf{update-commitstatus-success}: Updates the CommitStatus custom resource to phase \texttt{success}, signaling that the promotion gate has passed.
\end{enumerate}

For example, a staging gate with two checks (\texttt{validate-only}, \texttt{functional-test}) produces the DAG:

\begin{verbatim}
set-pending → health-check → check-0-validate-only →
  check-1-functional-test → report-success / comment-pr /
  update-commitstatus-success
\end{verbatim}

% ----------------------------------------------------------------------------
\subsection{Composition Rendering Mechanics}
\label{subsec:rendering-mechanics}
% ----------------------------------------------------------------------------

The WorkflowTemplate is the most technically demanding resource in the composition because it operates across \textit{four nested template layers}, each with its own escaping rules and evaluation timing:

\begin{enumerate}
    \item \textbf{Helm layer} (evaluated at \texttt{helm template} time). Resolves Helm values: image references, secret names, ingress domains, default ports. These are baked into the composition at chart installation and cannot change per CR.
    \item \textbf{Crossplane go-template layer} (evaluated at composition reconciliation). Resolves XRD spec fields: application name, environment names, check types, validation modes. The composition uses \texttt{function-go-templating} to iterate over the \texttt{environments[]} and \texttt{checks[]} arrays, generating one WorkflowTemplate per gated environment.
    \item \textbf{Argo Workflows layer} (evaluated at workflow submission). Resolves workflow parameters: PR number, head SHA, GitHub owner/repo, service name, source namespace. These are injected by the Sensor at runtime from the webhook payload.
    \item \textbf{Container layer} (evaluated at step execution). Resolves environment variables from Kubernetes secrets: GitHub App credentials, API authentication keys.
\end{enumerate}

This nesting creates an escaping challenge. An Argo Workflows parameter reference like \texttt{\{\{workflow.parameters.head-sha\}\}} uses the same double-brace syntax as Go templates. Inside a Crossplane go-template, this would be interpreted as a go-template expression and fail. The composition solves this with \textit{triple escaping}: each Argo reference is wrapped as \texttt{\{\{ ``\{\{'' \}\}workflow.parameters.head-sha\{\{ ``\}\}'' \}\}}, which the go-template engine evaluates to the literal string \texttt{\{\{workflow.parameters.head-sha\}\}}, which Argo then evaluates at workflow submission.

The DAG's dynamic section uses a stateful rendering pattern. The composition maintains a \texttt{\$state} dictionary with a single key (\texttt{prevStep}) that tracks the last generated step name. As the \texttt{range} loop iterates over \texttt{\$checks[]}, each step's \texttt{dependencies} field references the value of \texttt{prevStep}, and then updates it:

\begin{lstlisting}[language=Go,basicstyle=\ttfamily\footnotesize]
{{- $state := dict "prevStep" "wait-for-source-ready" -}}
{{- range $checkIdx, $check := $checks }}
{{- $stepName := printf "check-
  - name: {{ $stepName }}
    template: {{ $templateName }}
    dependencies: [{{ get $state "prevStep" }}]
{{- $_ := set $state "prevStep" $stepName -}}
{{- end }}
\end{lstlisting}

This pattern produces a sequential dependency chain of arbitrary length: the first check depends on \texttt{wait-for-source-ready}, the second depends on the first, and so on. The postamble steps (report-success, comment-pr, update-commitstatus-success) all depend on the final value of \texttt{prevStep}, which is the last check regardless of how many checks exist.

Step templates are conditionally included. The composition scans the \texttt{checks[]} array to determine which template types are needed (\texttt{\$needsFunctional}, \texttt{\$needsLoadtest}), and only emits the corresponding step template definitions when they are referenced. A gate with only \texttt{validate-only} checks does not include the \texttt{driveby-loadtest} or \texttt{driveby-functional} templates. This prevents Argo from reporting undefined template errors and keeps the rendered WorkflowTemplate minimal.

Per-check configuration is resolved at DAG generation time. A \texttt{validate-only} check passes its \texttt{validationConfig.validationMode} (defaulting to the CR's \texttt{validationDefaults.validationMode}) as a step argument. A \texttt{load-test} check passes four parameters (\texttt{concurrent-users}, \texttt{test-duration}, \texttt{max-latency-p95}, \texttt{min-success-rate}), each with a default from the check's \texttt{loadTestConfig} or a system default (10 users, 5~minutes, 500\,ms P95, 99\% success rate). This allows each check in the same gate to use different thresholds without duplicating the step template.

The result is that a single composition template produces WorkflowTemplates of varying structure: a gate with one \texttt{validate-only} check produces a 5-step DAG; a gate with \texttt{validate-only} + \texttt{functional-test} + \texttt{load-test} produces a 7-step DAG with three different step template definitions and per-check parameters. The composition handles all variants without conditionals on the DAG structure---the \texttt{range} loop and \texttt{\$state} dictionary are sufficient.

% ----------------------------------------------------------------------------
\subsection{Exit Handler}
\label{subsec:exit-handler}
% ----------------------------------------------------------------------------

The workflow defines an exit handler that triggers on any step failure. The exit handler posts a ``failure'' commit status to the PR's head SHA, ensuring that the quality gate is explicitly closed even when validation fails. When the GitOps Promoter is enabled, the exit handler also updates the CommitStatus custom resource to phase \texttt{failure}, blocking automatic promotion.

The exit handler is critical for the quality gate pattern. Without it, a failed workflow would leave the commit status in ``pending'' state indefinitely, neither blocking nor approving promotion. The exit handler guarantees that every workflow run terminates with an explicit quality signal: success or failure, never ambiguous.

\section{Helm Chart Packaging}
\label{sec:helm-chart}
% ============================================================================

The entire Kubernetes infrastructure is packaged as a Helm chart (\texttt{driveby}, version~3.0.0) that installs all Crossplane resources, XRDs, compositions, and provider configuration in a single \texttt{helm install} command.

% ----------------------------------------------------------------------------
\subsection{Chart Structure and Install Order}
\label{subsec:chart-structure}
% ----------------------------------------------------------------------------

The chart contains Crossplane provider references (\texttt{provider-kubernetes}~v0.14.1), Crossplane functions (go-templating, auto-ready), the \texttt{XSDLC} XRD definition, the \texttt{XSDLC} composition, a ProviderConfig for the Kubernetes provider, and optional secret templates.

Installation follows a four-step order designed to handle Crossplane's CRD chicken-and-egg problem: the Crossplane provider must be installed and healthy before ProviderConfig resources that reference it, and the XRD must be installed before the composition that implements it. The recommended sequence is:

\begin{enumerate}
    \item Pre-install: Crossplane provider and functions (wait for CRDs)
    \item Secrets: GitHub PAT, API auth, image pull credentials
    \item Helm install: XRD, composition, ProviderConfig
    \item Apply \texttt{XSDLC} CR: A single custom resource generates all quality gate infrastructure---RBAC, WorkflowTemplates, EventSources, Sensors, Ingresses, ScmProvider, GitRepository, PromotionStrategy, and ArgoCDCommitStatus resources
\end{enumerate}

Step~4 is handled by Crossplane once the XRD and composition are installed. The operator creates a single \texttt{XSDLC} custom resource per application, and Crossplane provisions all child resources automatically.

% ----------------------------------------------------------------------------
\subsection{OCI Distribution}
\label{subsec:oci-distribution}
% ----------------------------------------------------------------------------

The chart is distributed as an OCI (Open Container Initiative) artifact~\cite{helm-oci}, stored in the same container registry that hosts the DriveBy container images. This unified distribution model provides three properties. First, a \textit{single authentication boundary}: one registry credential grants access to both container images and Helm charts, eliminating the need for separate chart repository authentication. Second, \textit{version-aligned storage}: the chart artifact sits alongside the container image artifact for the same release, making it straightforward to verify that chart and image versions correspond. Third, \textit{immutability}: OCI tags, once pushed, are treated as immutable artifacts, providing tamper resistance and reproducible installations.

OCI distribution replaces the traditional model of maintaining a separate Helm chart repository (ChartMuseum, GitHub Pages, or a dedicated object storage bucket). The chart is published to \texttt{oci://ghcr.io/meter-peter/charts/driveby} and installed via standard Helm OCI syntax. Versioned chart releases are produced automatically by the release pipeline (Chapter~\ref{ch:workflow}), using the same Git tag that versions the container image and CLI binary, ensuring that all three artifact types are version-aligned from a single source of truth.

\section{Summary}
\label{sec:k8s-summary}
% ============================================================================

This chapter described the Kubernetes infrastructure that transforms DriveBy from a standalone CLI tool into a declarative, event-driven quality gate system, tracing the evolution from shell script through Go CLI, container image, and workflow step to Crossplane custom resource (Section~\ref{sec:cli-to-cr-evolution}).

The Kubernetes controller pattern (Section~\ref{sec:controller-pattern}) provides the operational model: level-triggered reconciliation loops that guarantee eventual consistency and self-healing. Crossplane extends this model as a universal control plane, managing resources across both the Kubernetes cluster and the GitHub API through a dual-provider architecture (Section~\ref{subsec:provider-architecture}). The declarative lifecycle (Section~\ref{sec:lifecycle-management}) shows how these mechanisms operate across the full lifecycle: platform installation (Day~0), pipeline creation (Day~1), continuous reconciliation (Day~2), and updates or deletion (Day~N).

The single-CR \texttt{XSDLC} model (Section~\ref{sec:xrd-design}) defines an entire SDLC pipeline---environments, multi-check quality gates, and promotion strategy---in one custom resource with only two required fields. The composition pipeline (Section~\ref{sec:composition-pipeline}) uses Crossplane's pipeline-mode functions to generate all required resources from this minimal input, including a dedicated GitOps repository, environment branches, branch protection rules, and ArgoCD Applications (Sections~\ref{subsec:generated-github} and~\ref{subsec:argocd-generation}). The two-tier configuration model (Section~\ref{sec:two-tier-config}) balances simplicity with flexibility across chart-wide defaults and per-resource overrides.

The Argo Events layer (Section~\ref{sec:argo-events-arch}) provides reliable, filtered event delivery from GitHub webhooks to workflow submissions. The Argo Workflows DAG (Section~\ref{sec:argo-workflows-dag}) orchestrates the full validation pipeline---from health checking through multi-check validation steps to commit status reporting---with an exit handler that guarantees explicit quality signals on every run.

Chapter~\ref{ch:workflow} describes how this infrastructure operates within the broader GitOps pipeline: the two-repo architecture and BYOCI design principle, the promotion-driven quality gate flow, human-in-the-loop patterns, and the quality gate as a closed-loop control system.
