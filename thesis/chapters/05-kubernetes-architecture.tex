\chapter{Kubernetes Architecture}
\label{ch:kubernetes}

Chapter~\ref{ch:architecture} described the DriveBy CLI as a standalone validation binary. This chapter describes the execution and provisioning layer of the three-layer model (Section~\ref{sec:three-layer-model}): how that binary is embedded in a Kubernetes-native infrastructure that provisions quality gates declaratively, triggers validation from external events, and orchestrates multi-step validation pipelines as container-native workflows. The result is a system where creating a new API quality gate requires writing a single custom resource---the Kubernetes control plane handles the rest. The architectural evolution that led to this design was traced in Section~\ref{sec:cli-to-cr-evolution}.

The architecture draws on four technologies: Crossplane~\cite{crossplane} for declarative resource provisioning, Argo Events~\cite{argo-events} for event-driven triggering, Argo Workflows~\cite{argo-workflows} for container-native pipeline orchestration, and the GitOps Promoter~\cite{gitops-promoter} for automated environment promotion. Each technology addresses a distinct concern in the quality gate lifecycle, and together they realize the ontological state reconciliation pattern introduced in Section~\ref{subsec:ontological-reconciliation} of Chapter~\ref{ch:related-work}.

\section{Architecture Overview}
\label{sec:k8s-overview}
% ============================================================================

% ----------------------------------------------------------------------------
\subsection{Design Goals}
\label{subsec:k8s-design-goals}
% ----------------------------------------------------------------------------

The Kubernetes architecture is shaped by five design goals:

\begin{enumerate}
    \item \textbf{Declarative provisioning.} An operator declares what quality gates should exist; the system provisions all required infrastructure (event sources, sensors, workflows, ingress routes, RBAC) automatically.

    \item \textbf{Separation of shared and per-API concerns.} Validation logic (the workflow template, RBAC, service accounts) is defined once and shared across all APIs; event routing (webhooks, sensors, ingress) is defined per API. Changes to the shared validation pipeline propagate to all APIs without per-API updates.

    \item \textbf{Multi-environment awareness.} The system validates against a source environment (typically development) and gates promotion to a target environment. This inversion---validating the source, not the target---ensures that quality is assessed before deployment, not after.

    \item \textbf{Progressive configurability.} Sensible defaults enable a minimal-configuration deployment, overridable chart-wide (Helm values) and per-resource (XRD spec fields).

    \item \textbf{Platform inheritance.} The system assumes shared platform capabilities---ArgoCD, Crossplane, Argo Events, Argo Workflows, Traefik, cert-manager---and references them rather than installing them; they are managed by the platform team and inherited by every \texttt{XSDLC} resource.
\end{enumerate}

The figure's legend distinguishes components built in this thesis from platform infrastructure that pre-existed on the target cluster (\texttt{private.novelcore.org}).

\section{The Kubernetes Controller Pattern}
\label{sec:controller-pattern}
% ============================================================================

Every resource described in this chapter---from the \texttt{XSDLC} custom resource to individual Sensors and WorkflowTemplates---is managed by a Kubernetes controller that continuously reconciles declared state against observed reality. This section describes the controller pattern, its consistency guarantees, and how Crossplane extends it into a universal control plane.

% ----------------------------------------------------------------------------
\subsection{The Reconciliation Loop}
\label{subsec:reconciliation-loop}
% ----------------------------------------------------------------------------

A Kubernetes controller implements a three-phase cycle: \textit{observe}, \textit{diff}, and \textit{act}~\cite{k8s-controllers}. It reads the desired state declared in a resource's \texttt{spec} and the actual state observed from the cluster, computes their difference, and takes corrective action---creating missing resources, updating drifted configurations, or deleting obsolete objects.

This cycle is \textit{level-triggered}, not \textit{edge-triggered}~\cite{k8s-up-and-running}: the controller reacts to observed state rather than to individual events, so a controller that crashes, restarts, or is scaled horizontally simply re-reads the current state and reconciles from scratch---no missed event can be lost, because the state itself is the complete input. This robustness is fundamental to the self-healing guarantees described in Section~\ref{subsec:self-healing}.

% ----------------------------------------------------------------------------
\subsection{Eventual Consistency and Self-Healing}
\label{subsec:self-healing}
% ----------------------------------------------------------------------------

Kubernetes does not guarantee immediate consistency. Creating an \texttt{XSDLC} resource returns immediately; the composition controller picks it up on its next reconciliation cycle, and the system \textit{converges} toward the declared state over successive cycles, each child resource subject to its own controller's loop. This eventual-consistency model yields self-healing: a deleted child is re-created and a drifted configuration is overwritten on the next reconciliation pass, with no human intervention (concrete scenarios in Section~\ref{subsec:day2}). The model concretely instantiates the ontological state reconciliation pattern of Section~\ref{subsec:ontological-reconciliation} in Chapter~\ref{ch:related-work}: the \texttt{XSDLC} spec is the ontological artifact, the composition controller the reconciliation agent, and drift correction the correction mechanism.

% ----------------------------------------------------------------------------
\subsection{Crossplane as Universal Control Plane}
\label{subsec:crossplane-control-plane}
% ----------------------------------------------------------------------------

Crossplane~\cite{crossplane} extends the Kubernetes controller pattern by allowing custom resources to declare not just in-cluster objects but any resource reachable through a provider API---cloud databases, DNS records, GitHub branches, and any other resource for which a Crossplane provider exists~\cite{crossplane-compositions}.

The \texttt{XSDLC} composition leverages this extension to manage resources across two control planes simultaneously. In-cluster resources (ServiceAccount, EventBus, WorkflowTemplate, ArgoCD Application, secrets) are provisioned through \texttt{provider-kubernetes}. GitHub resources (Repository, RepositoryFile, Branch, BranchProtection) are provisioned through \texttt{provider-upjet-github}. From the operator's perspective, this distinction is invisible: one \texttt{XSDLC} custom resource declares the entire pipeline, and the composition delegates each child resource to the appropriate provider.

Crossplane compositions function as \textit{meta-controllers}: a composition watches a composite resource (the XRD) and generates \textit{desired state for other controllers}---\texttt{function-go-templating} renders the desired children, \texttt{function-auto-ready} aggregates their readiness, and each child is reconciled by its own provider controller. This two-level reconciliation is what enables a single 25-line YAML declaration to produce and maintain a pipeline of approximately 45--50 managed resources (the exact decomposition is derived in Section~\ref{subsec:day1}).

% ----------------------------------------------------------------------------
\subsection{Provider Architecture}
\label{subsec:provider-architecture}
% ----------------------------------------------------------------------------

The \texttt{XSDLC} composition delegates resource management to two Crossplane providers:

\textbf{\texttt{provider-kubernetes}} (v0.14.1) manages all in-cluster resources. It uses \texttt{InjectedIdentity} for authentication, inheriting the permissions of the Crossplane pod's service account. Every in-cluster resource generated by the composition (the full inventory is given in Section~\ref{subsec:xrd-xsdlc}) is wrapped in a \texttt{provider-kubernetes} \texttt{Object} resource, which the provider reconciles by applying the embedded manifest to the cluster.

\textbf{\texttt{provider-upjet-github}} (v0.18.0) manages GitHub API resources. It authenticates via a GitHub personal access token stored in a Kubernetes secret. The provider exposes GitHub resources as Kubernetes custom resources: \texttt{Repository}, \texttt{Branch}, \texttt{BranchProtection}, and \texttt{RepositoryFile}. The composition generates these resources to auto-create a dedicated GitOps repository, seed it with boilerplate dry manifests, provision environment branches within it, and enforce branch protection rules.

The single-composition, dual-provider model (Figure~\ref{fig:provider-architecture}) means that the operator interacts with one Kubernetes API (\texttt{driveby.io/v1alpha1 XSDLC}) while the system manages resources across two distinct control planes---the Kubernetes cluster and the GitHub API.

\section{Crossplane XRD Design}
\label{sec:xrd-design}
% ============================================================================

The quality gate infrastructure is provisioned through a single Crossplane Composite Resource Definition (XRD): \texttt{XSDLC} (API group \texttt{driveby.io/v1alpha1}). This single-CR model replaces an earlier two-XRD design, reducing the operator's cognitive load and deployment surface: one custom resource defines the entire software development lifecycle (SDLC) pipeline for an application.

% ----------------------------------------------------------------------------
\subsection{XSDLC: Single-CR Pipeline Definition}
\label{subsec:xrd-xsdlc}
% ----------------------------------------------------------------------------

The \texttt{XSDLC} XRD requires only two fields: \texttt{gitopsRepository} (the GitHub owner and gitops repository name) and \texttt{environments} (the ordered list of environments in the promotion chain). The \textit{software repository}---the repository holding the application's actual source code---is never referenced; this exclusion is deliberate: XSDLC manages only the gitops repo, leaving build and CI concerns entirely to the developer's own tooling (the BYOCI boundary, Chapter~\ref{ch:workflow}). From these two inputs, the composition generates all resources needed for the full software delivery lifecycle pipeline.

A single \texttt{XSDLC} custom resource generates three categories of resources. \textit{App-level shared resources} are created once per CR:

\begin{enumerate}
    \item A \textbf{ServiceAccount} with image pull credentials for accessing the DriveBy container image from the GitHub Container Registry.
    \item An \textbf{EventBus} backed by NATS JetStream~\cite{nats-jetstream} for reliable event delivery between EventSources and Sensors.
    \item A \textbf{ScmProvider} authenticating to GitHub via a GitHub App.
    \item A \textbf{GitRepository} pointing to the GitOps repository.
    \item A \textbf{GitHub Repository} auto-creating a dedicated gitops repository.
    \item \textbf{RepositoryFiles} seeding the gitops repository with boilerplate dry manifests (base deployment, service, and kustomization).
    \item An \textbf{ArgoCD push secret} granting the Source Hydrator write access to the gitops repository.\footnote{The ArgoCD Source Hydrator (Section~\ref{subsec:argocd-generation}) renders each environment's Kustomize overlay and \textit{pushes} the hydrated manifests to the corresponding \texttt{-next} branch. Unlike ordinary ArgoCD operation, which only reads from Git, this push requires repository-write credentials; the push secret supplies them to the hydrator in the \texttt{argocd} namespace.}
    \item A \textbf{BranchProtection} rule protecting all \texttt{*-next} branches in the gitops repository.
\end{enumerate}

\textit{Per-environment resources} are created for each environment in the promotion chain:

\begin{enumerate}
    \item A \textbf{PromotionStrategy} defining the environment's auto-merge policy and commit status gates.
    \item Two \textbf{Branches} in the gitops repository (the environment branch and its \texttt{-next} counterpart).
    \item A \textbf{RepositoryFile} seeding the per-environment Kustomize overlay.
    \item A \textbf{ghcr-creds} secret copied into the environment namespace for image pull authentication.
    \item An \textbf{ArgoCD Application} using Source Hydrator to render the environment's overlay.
\end{enumerate}

\textit{Per-gate resources} are created for each environment that defines a \texttt{gate}:

\begin{enumerate}
    \item A \textbf{Role} granting permissions to create and manage Argo Workflows, read secrets and configmaps, manage persistent volume claims, and create and update CommitStatus custom resources.
    \item A \textbf{RoleBinding} associating the service account with the role.
    \item A \textbf{WorkflowTemplate} containing the validation DAG described in Section~\ref{sec:argo-workflows-dag}.
    \item An \textbf{EventSource} configured as a webhook listener on a configurable port (default: 12000).
    \item A \textbf{Sensor} that filters events (e.g., only \texttt{pull\_request} events with actions \texttt{opened}, \texttt{reopened}, or \texttt{synchronize}) and submits workflow runs with extracted parameters.
    \item A \textbf{Service} exposing the EventSource webhook.
    \item An \textbf{Ingress} with TLS termination (via cert-manager) routing external webhook traffic to the EventSource service.
    \item A \textbf{BranchProtection} rule requiring the gate's commit status check before merging into the environment branch.
\end{enumerate}

% ----------------------------------------------------------------------------
\subsection{Multi-Check Gate Model}
\label{subsec:multi-check-gates}
\label{subsec:gate-types}
% ----------------------------------------------------------------------------

Quality gates in the \texttt{XSDLC} model are composed from an ordered \texttt{checks[]} array. Each check becomes a sequential step in the Argo Workflows DAG, enabling gates that combine multiple validation concerns in a single promotion decision. Three check types are supported, each mapping to a distinct SDT concern:

\begin{itemize}
    \item \textbf{\texttt{validate-only}} --- exploits the DriveBy CLI's static validation facilities, evaluating the specification-level principles, which are applied fully or partially depending on the validation mode: full application in strict mode (P001--P005, P008, P009), partial application in minimal mode (a subset). Accepts an optional \texttt{validationConfig.\allowbreak validationMode} override.
    \item \textbf{\texttt{functional-test}} --- runs the DriveBy CLI in \texttt{function-only} mode, executing P006 functional tests against the live API in the source environment. Validates runtime behavioral conformance: correct response schemas, proper error codes, authenticated endpoint behavior.
    \item \textbf{\texttt{load-test}} --- runs the DriveBy CLI in \texttt{load-only} mode, executing vegeta-based load testing (P007) with four configurable parameters and defaults: \texttt{concurrentUsers} (10 simulated parallel clients), \texttt{testDuration} (\texttt{5m}), \texttt{maxLatencyP95} (\texttt{500ms} 95th-percentile latency ceiling), and \texttt{minSuccessRate} (0.99). The defaults are pragmatic baselines: 10 concurrent users over five minutes exercise sustained concurrency without overloading development-grade environments, while the 500\,ms P95 and 99\% success-rate thresholds reflect common targets for internal HTTP APIs; they were tuned empirically during the PoC deployment and are deliberately conservative, since stricter values can be set per check.
\end{itemize}

The composition generates DAG steps with deterministic naming (\texttt{check-0-\allowbreak validate-only}, \texttt{check-1-\allowbreak functional-test}, \ldots), each depending on the previous, so cheaper checks (static validation) run before expensive checks (load testing), failing fast when possible.

Different environment transitions compose different subsets: the staging gate in Listing~\ref{lst:xsdlc-cr} pairs \texttt{validate-only} with \texttt{functional-test}, while the production gate pairs \texttt{validate-only} with \texttt{load-test} (optionally tightened, e.g.\ \texttt{concurrentUsers: 50}, \texttt{testDuration: "10m"}, \texttt{maxLatencyP95: "200ms"}). This distribution is \textit{indicative}; the actual assignment is chosen by the operator according to the application's requirements.

% ----------------------------------------------------------------------------
\subsection{Minimal Configuration}
\label{subsec:minimal-config}
% ----------------------------------------------------------------------------

Listing~\ref{lst:xsdlc-cr} shows a representative \texttt{XSDLC} instance. The entire SDLC pipeline for the \texttt{perfect-api} application\footnote{Source-code identifiers (namespaces, container images, repository names, the example application) retain the historical name \texttt{perfect-api}; the thesis-level rename to \texttt{non-critical-api} (see Section~\ref{sec:controlled-eval} in Chapter~\ref{ch:evaluation} for the rationale) is a naming decision that will be propagated to source in a follow-up release. Wherever this chapter writes \texttt{perfect-api}, the same artefact is meant.}---three environments, a validation gate for staging promotion, and a load test gate for production promotion---is defined in approximately 25 lines of YAML.

\begin{lstlisting}[caption={XSDLC custom resource defining a three-environment pipeline with quality gates.},label={lst:xsdlc-cr}]
apiVersion: driveby.io/v1alpha1
kind: XSDLC
metadata:
  name: perfect-api
  namespace: driveby
spec:
  gitopsRepository:
    owner: novelcore
    name: perfect-api-gitops
  environments:
    - name: dev
    - name: staging
      gate:
        checks:
          - type: validate-only
          - type: functional-test
    - name: prod
      autoMerge: false
      gate:
        checks:
          - type: validate-only
          - type: load-test
\end{lstlisting}

Note that \texttt{validate-only} appears in both gates. Re-running static validation at every promotion gate is intentional and idiomatic: the check is cheap (seconds, no load on the running API), and each gate independently certifies the artifact it promotes---guarding against the specification changing between the staging and production promotions rather than trusting an earlier gate's result.

From this declaration, Crossplane generates all three resource categories of Section~\ref{subsec:xrd-xsdlc}; Figure~\ref{fig:xrd-resource-hierarchy} visualizes the resulting hierarchy. The operator writes approximately 15 lines of meaningful configuration; the composition generates several hundred lines of Kubernetes manifests. All cluster-specific configuration---domain, image references, secret names, ingress class, certificate issuer---is inherited from Helm values, following the two-tier configuration model described in Section~\ref{sec:two-tier-config}.

\section{Declarative Lifecycle Management}
\label{sec:lifecycle-management}
% ============================================================================

This section describes how the controller pattern and provider architecture manifest in the operational lifecycle of the quality gate system---from platform installation through pipeline creation, continuous operation, and eventual decommissioning.

% ----------------------------------------------------------------------------
\subsection{Day 0: Platform Installation}
\label{subsec:day0}
% ----------------------------------------------------------------------------

DriveBy's own Helm chart (\texttt{driveby}, version~3.0.0, published at \texttt{oci://ghcr.io/\allowbreak meter-peter/\allowbreak charts/\allowbreak driveby}; Section~\ref{sec:helm-chart}) installs the \textit{platform layer}: the XRD definition, the composition template, the ProviderConfig for \texttt{provider-kubernetes}, the ProviderConfig for \texttt{provider-upjet-github}, and the Crossplane functions (\texttt{function-\allowbreak go-templating}, \texttt{function-\allowbreak auto-ready}). At this point, no \texttt{XSDLC} instances exist. The platform is ready to accept declarations but has not yet provisioned any quality gate infrastructure.

This separation is deliberate: the platform team installs the Helm chart once per cluster, and application teams create \texttt{XSDLC} custom resources independently, without platform-team involvement for each new API. The platform provides the \textit{capability}; individual CRs exercise it.

% ----------------------------------------------------------------------------
\subsection{Day 1: Pipeline Creation}
\label{subsec:day1}
% ----------------------------------------------------------------------------

When an operator applies an \texttt{XSDLC} custom resource, the Crossplane composition controller detects the new resource on its next reconciliation cycle and begins generating child resources. The resource count decomposes along the three categories of Section~\ref{subsec:xrd-xsdlc}. \textit{Once per CR}: the GitHub Repository, ServiceAccount, EventBus, ScmProvider, GitRepository, ArgoCD push secret, ArgoCDCommitStatus, three seed RepositoryFiles, and the \texttt{*-next} BranchProtection rule---11 resources. \textit{Per environment}: a PromotionStrategy, two Branches, an overlay RepositoryFile, a ghcr-creds secret, and an ArgoCD Application---6 resources each. \textit{Per gated environment}: Role, RoleBinding, WorkflowTemplate, EventSource, Sensor, Service, Ingress, and BranchProtection---8 resources each. For the reference deployment (\texttt{perfect-api} with three environments and two quality gates) this yields $11 + 3 \times 6 + 2 \times 8 = 45$ child resources; across typical configurations (varying environment and gate counts) the total is approximately 45--50, the figure used throughout this thesis. The GitHub-provider resources (Repository, Branches, RepositoryFiles, BranchProtection rules) are generated only when the GitHub provider is enabled; disabling it reduces the count accordingly.

Each child resource is itself subject to its provider's reconciliation loop. The \texttt{provider-kubernetes} controller applies each in-cluster manifest; the \texttt{provider-upjet-github} controller creates the gitops repository and its branches. The \texttt{function-auto-ready} function monitors all children and marks the \texttt{XSDLC} composite as \texttt{READY=True} only when every child has reached its own ready state.

% ----------------------------------------------------------------------------
\subsection{Day 2: Continuous Reconciliation}
\label{subsec:day2}
% ----------------------------------------------------------------------------

Once the pipeline is created, two scenarios illustrate continuous reconciliation.

\textbf{Drift detection.} If an operator or automated process modifies a Crossplane-managed resource---for example, changing the Sensor's filter configuration---the composition controller detects the discrepancy on its next reconciliation pass and overwrites the change: the \texttt{XSDLC} spec is the single source of truth.

\textbf{Self-healing.} If a managed resource is deleted---for example, \texttt{kubectl delete sensor perfect-api-staging-gate-sensor}---the composition controller detects the missing child and re-creates it, returning the pipeline to its declared state without human intervention.

The composition uses two deletion policies to distinguish shared and per-pipeline resources. \textit{Shared resources} (ServiceAccount, EventBus) use \texttt{deletionPolicy: Orphan}. If the \texttt{XSDLC} CR is deleted, these resources are left in place because other \texttt{XSDLC} instances in the same namespace may depend on them. \textit{Per-pipeline resources} (ScmProvider, GitRepository, PromotionStrategy, WorkflowTemplate, EventSource, Sensor, ghcr-creds secrets, ArgoCD push secret, and all per-gate resources) use \texttt{deletionPolicy: Delete}. When the \texttt{XSDLC} CR is deleted, these resources are cascade-deleted because they are specific to the pipeline being decommissioned. Similarly, GitHub \texttt{Branch} and \texttt{RepositoryFile} resources use \texttt{deletionPolicy: Orphan} to preserve branch history and manifest content even when the pipeline is removed.

% ----------------------------------------------------------------------------
\subsection{Day N: Updates and Deletion}
\label{subsec:day-n}
% ----------------------------------------------------------------------------

\textbf{Updates.} Modifying an \texttt{XSDLC} CR's \texttt{spec} field triggers a reconciliation delta: adding an environment generates its ArgoCD Application, branches, and (if gated) per-gate resources; removing one deletes the corresponding children; changing a gate's check types regenerates the WorkflowTemplate. The composition is \textit{idempotent}: the same spec produces no changes, a modified spec exactly the changes needed.

\textbf{Deletion.} Deleting the \texttt{XSDLC} CR cascade-deletes all children with \texttt{deletionPolicy: Delete}; resources with \texttt{deletionPolicy: Orphan} (ServiceAccount, EventBus, Branches, RepositoryFiles) remain, so shared infrastructure survives individual pipeline removal.

% ----------------------------------------------------------------------------
\subsection{Status Reporting}
\label{subsec:status-reporting}
% ----------------------------------------------------------------------------

The \texttt{XSDLC} XRD defines a structured \texttt{status} section that reports the pipeline's operational state. The status fields include:

\begin{itemize}
    \item \texttt{ready} (boolean): overall readiness, set by \texttt{function-auto-ready} when all children are healthy.
    \item \texttt{environmentCount} (integer): number of environments in the promotion chain.
    \item \texttt{gateCount} (integer): number of environments with quality gates.
    \item \texttt{gates[]} (array): one entry per gated environment, reporting environment name, gate type, commit status key, webhook URL, and readiness.
    \item \texttt{promotionStrategy} (object): name and readiness of the generated PromotionStrategy.
    \item \texttt{conditions[]} (array): standard Kubernetes conditions (Ready, Synced) with timestamps and messages.
\end{itemize}

The XRD defines \texttt{additionalPrinterColumns} so that \texttt{kubectl get xsdlcs} displays a summary view:

\begin{verbatim}
NAME          APP          ENVIRONMENTS   GATES   READY   AGE
perfect-api   perfect-api  3              2       True    4d
\end{verbatim}

This status reporting applies the Observability axiom to the infrastructure itself: just as SDT's validation report makes API quality observable, the \texttt{XSDLC} status makes pipeline health observable at a glance, without inspecting individual children.

\section{Composition Pipeline}
\label{sec:composition-pipeline}
% ============================================================================

% ----------------------------------------------------------------------------
\subsection{Pipeline-Mode Compositions}
\label{subsec:pipeline-mode}
% ----------------------------------------------------------------------------

The \texttt{XSDLC} XRD uses Crossplane's pipeline-mode composition, which processes the composite resource through a sequence of functions rather than relying on the legacy patch-and-transform approach. The composition pipeline follows a two-step pattern:

\begin{enumerate}
    \item \textbf{function-go-templating}: Renders Kubernetes manifests from Go templates, with access to the XRD spec and Helm-injected defaults. It performs the bulk of the work: iterating over the environments list and each gate's \texttt{checks[]} array, generating shared resources once and per-gate resources (including the step templates \texttt{driveby-validate}, \texttt{driveby-functional}, \texttt{driveby-loadtest}) per gated environment, resolving the two-tier configuration precedence, and handling the template escaping required when generating Argo Workflows templates that themselves contain Go template syntax.
    \item \textbf{function-auto-ready}: Automatically marks the composite resource as ready when all composed resources reach their ready state.
\end{enumerate}

% ----------------------------------------------------------------------------
\subsection{Template Escaping}
\label{subsec:template-escaping}
% ----------------------------------------------------------------------------

A notable engineering challenge arises from the nested templating layers. The Crossplane composition uses Go templates to generate Argo Workflows manifests, which themselves use Go template syntax for parameter substitution (e.g., \texttt{\{\{workflow.parameters.app-name\}\}}). Without escaping, the Crossplane go-templating function would attempt to evaluate the Argo template expressions during composition rendering, causing failures.

The solution uses a double-escaping convention. Argo template expressions within the composition are written as:

\begin{verbatim}
{{ "{{" }}workflow.parameters.app-name{{ "}}" }}
\end{verbatim}

The outer Go template evaluates \verb|{{"{{" }}| to produce the literal string \verb|{{|, and similarly for the closing braces. The resulting manifest contains the intended Argo expression \verb|{{workflow.parameters.app-name}}| verbatim. This escaping is applied consistently across all workflow step definitions in the template composition.

% ----------------------------------------------------------------------------
\subsection{Generated GitHub Resources}
\label{subsec:generated-github}
% ----------------------------------------------------------------------------

When the GitHub provider is enabled, the \texttt{XSDLC} composition generates three categories of GitHub resources, all managed through \texttt{provider-upjet-github}.

\textbf{Branches.} For each environment in the promotion chain, the composition generates two branches in the gitops repository, sourced from \texttt{main}: \texttt{environment/<name>} (the active branch that ArgoCD watches) and \texttt{environment/<name>-next} (the proposed branch). Both use \texttt{deletionPolicy: Orphan} to preserve Git history when the pipeline is removed. For a three-environment pipeline, this produces six branches.

\textbf{Repository.} The composition auto-creates a dedicated, private GitOps repository under the same GitHub owner (e.g., \texttt{novelcore/perfect-api-gitops}), with \texttt{deletionPolicy: Orphan}: deleting it would destroy the manifest history and audit trail of environments that may still be running, so decommissioning the pipeline deliberately leaves the Git record intact. The software repository is never modified by XSDLC.

\textbf{Branch protection.} When enabled, the composition generates \texttt{BranchProtection} rules for gated environments. Each gated environment's active branch requires the corresponding commit status check to pass before merging. The \texttt{-next} branches receive protection to prevent accidental overwrites.

The key insight is that the GitOps repository and its branch topology are \textit{generated infrastructure}, not hand-authored configuration: the composition maintains them in the same reconciliation loop as in-cluster resources, eliminating manual repository setup.

% ----------------------------------------------------------------------------
\subsection{ArgoCD Application Generation}
\label{subsec:argocd-generation}
% ----------------------------------------------------------------------------

The composition generates an ArgoCD Application for every environment in the promotion chain, not just gated environments. Every Application uses the ArgoCD Source Hydrator~\cite{argocd-hydrator} rather than a traditional \texttt{source} block. Each Application's \texttt{sourceHydrator} configuration points to the environment's Kustomize overlay on the \texttt{main} branch:

\begin{itemize}
    \item \texttt{drySource}: the gitops repository, path \texttt{dry/overlays/<envName>}, revision \texttt{main}
    \item \texttt{syncSource}: the environment's active branch (\texttt{environment/<name>}), path \texttt{manifests}
    \item \texttt{hydrateTo}: the environment's proposed branch (\texttt{environment/\allowbreak <name>-next})
\end{itemize}

When a developer updates dry manifests on the \texttt{main} branch, the hydrator renders the Kustomize overlay for each environment and writes the hydrated output---along with a \texttt{hydrator.metadata} file containing the dry commit SHA, satisfying the GitOps Promoter's provenance contract---to the corresponding \texttt{-next} branch. The promotion flow that follows (Promoter PR, gate execution, merge, sync from the active branch) is described in Chapter~\ref{ch:workflow}.

This per-environment overlay model lets each environment customize its deployment independently (replicas, resource limits, environment variables, image tags), and deploying to a specific environment requires only updating its overlay on \texttt{main}---there is no linear propagation chain through earlier environments.

All generated Applications are configured with \texttt{automated.selfHeal: true} and \texttt{automated.prune: true}. ArgoCD automatically synchronizes changes and self-heals drifted resources regardless of the \texttt{autoMerge} setting. The \texttt{autoMerge} field exclusively controls the GitOps Promoter's behavior: when \texttt{true} (default), the Promoter automatically merges promotion PRs after gates pass; when \texttt{false}, the PR remains open for human review. This decoupling is deliberate---ArgoCD should always reflect the state of the environment branch, while the promotion decision (whether to update that branch) is where human judgment applies.

All generated Applications include \texttt{CreateNamespace=true} in their sync options, ensuring that the target namespace is created automatically if it does not exist. Each Application carries labels (\texttt{driveby.io/app}, \texttt{driveby.io/environment}) that enable the ArgoCDCommitStatus resource to aggregate health signals across all environments.

\section{Argo Events Architecture}
\label{sec:argo-events-arch}
% ============================================================================

Argo Events provides the event-driven layer that connects external triggers (GitHub webhooks) to internal actions (workflow submissions). The architecture uses three Argo Events resources, each generated by the \texttt{XSDLC} composition for every environment that defines a quality gate.

% ----------------------------------------------------------------------------
\subsection{EventBus}
\label{subsec:eventbus}
% ----------------------------------------------------------------------------

The EventBus is the message transport layer between EventSources and Sensors, backed by NATS JetStream~\cite{nats-jetstream} with persistent, at-least-once delivery: events are persisted and replayed if a Sensor is temporarily unavailable, without external message queue infrastructure. The EventBus must be named \texttt{default} within each namespace (an Argo Events convention) and runs a single replica in the development deployment; production deployments would scale to three replicas for high availability.

% ----------------------------------------------------------------------------
\subsection{EventSource}
\label{subsec:eventsource}
% ----------------------------------------------------------------------------

The EventSource is the ingress point where external events enter the Kubernetes-native event pipeline: an HTTP server listening for webhook payloads on a configurable port (default: 12000). Webhooks are chosen over polling because quality gate triggers are inherently event-driven, and webhook delivery provides near-real-time notification without polling's latency and API rate-limit pressure.

Each quality gate generates a named webhook endpoint following a deterministic naming convention: \texttt{/<appName>-<envName>-gate-pr-trigger} (e.g., \texttt{/perfect-api-staging-gate-pr-trigger} for the reference deployment's staging gate). The composition derives the EventSource endpoint, Ingress route, and GitHub webhook URL from the same two identity fields, guaranteeing that they agree without manual coordination.

The EventSource receives the raw webhook payload, validates its structure, and publishes it to the EventBus, decoupling event reception from event processing: filtering and action-triggering are delegated entirely to the Sensor.

% ----------------------------------------------------------------------------
\subsection{Sensor and Parameter Extraction}
\label{subsec:sensor}
% ----------------------------------------------------------------------------

The Sensor subscribes to events from the EventBus, applies filtering logic, and triggers workflow submissions when filter conditions are met. For pull request validation, the Sensor filters on:

\begin{itemize}
    \item Event type: \texttt{pull\_request}
    \item Action: \texttt{opened}, \texttt{reopened}, or \texttt{synchronize}
\end{itemize}

This filtering ensures that workflows are triggered only for meaningful PR events---not for label changes, review requests, or other non-code events.

When a matching event arrives, the Sensor extracts parameters from the webhook payload using JSONPath expressions and passes them to the workflow submission; Table~\ref{tab:sensor-params} lists them.

\section{Argo Workflows Validation DAG}
\label{sec:argo-workflows-dag}
% ============================================================================

The validation pipeline is implemented as an Argo Workflows WorkflowTemplate containing a directed acyclic graph (DAG), \textit{dynamically generated} by the Crossplane composition from the gate's \texttt{checks[]} array (Section~\ref{subsec:multi-check-gates}); the Sensor submits workflow runs from this template with the extracted parameters.

% ----------------------------------------------------------------------------
\subsection{Pipeline Steps}
\label{subsec:pipeline-steps}
% ----------------------------------------------------------------------------

The DAG follows a fixed preamble, a dynamic checks section, and a fixed postamble:

\textbf{Preamble (fixed steps):}

\begin{enumerate}
    \item \textbf{set-pending-status}: Posts a ``pending'' commit status to the PR's head SHA via the GitHub API. A parallel step (\textbf{update-commitstatus-pending}) creates a CommitStatus custom resource with phase \texttt{pending} for the GitOps Promoter.

    \item \textbf{wait-for-source-ready}: Polls the source environment (e.g., \texttt{perfect-api-dev}) with up to 60 \texttt{curl} probes of the OpenAPI endpoint at 5-second intervals (5 minutes maximum), ensuring validation does not run against a partially deployed or restarting instance.
\end{enumerate}

\textbf{Dynamic checks (from \texttt{checks[]} array):}

For each check in the gate's ordered \texttt{checks[]} array, the composition generates a DAG step named \texttt{check-<index>-<type>}. Each step depends on the previous step, forming a sequential chain. The step template is selected by check type:

\begin{itemize}
    \item \texttt{validate-only} $\rightarrow$ \texttt{driveby-validate}: Runs the DriveBy container (\texttt{ghcr.io/\allowbreak meter-peter/\allowbreak driveby:latest}) with flags derived from the check's \texttt{validationConfig}; the validation report is stored on a shared PersistentVolumeClaim (PVC) at \texttt{/tmp/reports}.
    \item \texttt{functional-test} $\rightarrow$ \texttt{driveby-functional}: Runs the CLI in \texttt{function-only} mode against the live API, with authentication credentials injected from Kubernetes secrets.
    \item \texttt{load-test} $\rightarrow$ \texttt{driveby-loadtest}: Runs the CLI in \texttt{load-only} mode, parameterized from the check's \texttt{loadTestConfig}; credentials are injected from the same secret, so the generated load exercises authenticated endpoints.
\end{itemize}

\textbf{Postamble (fixed steps, parallel after last check):}

\begin{enumerate}
    \item \textbf{report-success}: Posts a ``success'' commit status to the PR's head SHA.
    \item \textbf{comment-pr}: Posts the validation report as a comment on the pull request, reading saved reports from the shared PVC via DriveBy's \texttt{github-comment} command.
    \item \textbf{update-commitstatus-success}: Updates the CommitStatus custom resource to phase \texttt{success}, signaling that the promotion gate has passed.
\end{enumerate}

For example, a staging gate with two checks (\texttt{validate-only}, \texttt{functional-test}) produces the DAG:

\begin{verbatim}
set-pending-status → wait-for-source-ready →
  check-0-validate-only → check-1-functional-test →
  report-success / comment-pr / update-commitstatus-success
\end{verbatim}

\noindent
Here $\rightarrow$ denotes sequential dependency and \texttt{/} separates parallel steps; the \texttt{update-commitstatus-pending} step, parallel to \texttt{set-pending-status}, is omitted for readability.

% ----------------------------------------------------------------------------
\subsection{Composition Rendering Mechanics}
\label{subsec:rendering-mechanics}
% ----------------------------------------------------------------------------

The WorkflowTemplate is the most technically demanding resource in the composition because it operates across \textit{four nested template layers}, each with its own escaping rules and evaluation timing:

\begin{enumerate}
    \item \textbf{Helm layer} (evaluated at \texttt{helm template} time). Resolves Helm values: image references, secret names, ingress domains, default ports. Global parameters (e.g., the webhook port, Table~\ref{tab:config-tiers}) are baked into the composition at chart installation and cannot change per CR; parameters exposed in the XRD spec merely receive their defaults here and can still be overridden at the next layer.
    \item \textbf{Crossplane go-template layer} (evaluated at composition reconciliation). Resolves XRD spec fields: application name, environment names, check types, validation modes. The composition uses \texttt{function-\allowbreak go-templating} to iterate over the \texttt{environments[]} and \texttt{checks[]} arrays, generating one WorkflowTemplate per gated environment.
    \item \textbf{Argo Workflows layer} (evaluated at workflow submission). Resolves workflow parameters: PR number, head SHA, GitHub owner/repo, service name, source namespace. These are injected by the Sensor at runtime from the webhook payload.
    \item \textbf{Container layer} (evaluated at step execution). Resolves environment variables from Kubernetes secrets: GitHub App credentials, API authentication keys.
\end{enumerate}

Because Argo parameter references share the Go-template double-brace syntax, the composition applies the escaping convention of Section~\ref{subsec:template-escaping} so that they survive composition rendering verbatim and are evaluated only at workflow submission.

The DAG's dynamic section uses a stateful rendering pattern. The composition maintains a \texttt{\$state} dictionary with a single key (\texttt{prevStep}) that tracks the last generated step name. As the \texttt{range} loop iterates over \texttt{\$checks[]}, each step's \texttt{dependencies} field references the value of \texttt{prevStep}, and then updates it:

\begin{lstlisting}[language=Go,basicstyle=\ttfamily\footnotesize]
{{- $state := dict "prevStep" "wait-for-source-ready" -}}
{{- range $checkIdx, $check := $checks }}
{{- $stepName := printf "check-
  - name: {{ $stepName }}
    template: {{ $templateName }}
    dependencies: [{{ get $state "prevStep" }}]
{{- $_ := set $state "prevStep" $stepName -}}
{{- end }}
\end{lstlisting}

This pattern produces a sequential dependency chain of arbitrary length; the postamble steps all depend on the final value of \texttt{prevStep}, the last check regardless of how many exist.

Step templates are conditionally included: the composition scans the \texttt{checks[]} array (\texttt{\$needsFunctional}, \texttt{\$needsLoadtest}) and only emits the step template definitions that are actually referenced, preventing undefined-template errors and keeping the rendered WorkflowTemplate minimal.

Per-check configuration is resolved at DAG generation time: a \texttt{validate-only} check passes its \texttt{validationConfig.validationMode} (defaulting to the CR's \texttt{validationDefaults.validationMode}); a \texttt{load-test} check passes \texttt{concurrent-users}, \texttt{test-duration}, \texttt{max-latency-p95}, and \texttt{min-success-rate}, each resolved from the check's \texttt{loadTestConfig} or, failing that, from the XRD-schema defaults of Section~\ref{subsec:multi-check-gates} (10 users, 5~minutes, 500\,ms P95, 99\% success rate)---defaults, not measurements. Each check in the same gate can thus use different thresholds without duplicating the step template.

A single composition template thus produces WorkflowTemplates of varying structure. Counting every DAG task---the three fixed preamble tasks plus the three fixed postamble tasks---a gate with one \texttt{validate-only} check produces a 7-step DAG; a gate with \texttt{validate-only} + \texttt{functional-test} + \texttt{load-test} produces a 9-step DAG with three step template definitions and per-check parameters. The composition handles all variants without conditionals on the DAG structure---the \texttt{range} loop and \texttt{\$state} dictionary suffice.

% ----------------------------------------------------------------------------
\subsection{Exit Handler}
\label{subsec:exit-handler}
% ----------------------------------------------------------------------------

The workflow defines an exit handler that triggers on any step failure. It posts a ``failure'' commit status to the PR's head SHA and, when the GitOps Promoter is enabled, updates the CommitStatus custom resource to phase \texttt{failure}, blocking automatic promotion. The exit handler is critical for the quality gate pattern: without it, a failed workflow would leave the commit status ``pending'' indefinitely, neither blocking nor approving promotion. It guarantees that every workflow run terminates with an explicit quality signal---success or failure, never ambiguous.

\section{Helm Chart Packaging}
\label{sec:helm-chart}
% ============================================================================

The entire Kubernetes infrastructure is packaged as a Helm chart (\texttt{driveby}, version~3.0.0) that installs all Crossplane resources, XRDs, compositions, and provider configuration in a single \texttt{helm install} command.

% ----------------------------------------------------------------------------
\subsection{Chart Structure and Install Order}
\label{subsec:chart-structure}
% ----------------------------------------------------------------------------

The chart contains Crossplane provider references (\texttt{provider-kubernetes} v0.14.1), Crossplane functions (go-templating, auto-ready), the \texttt{XSDLC} XRD definition, the \texttt{XSDLC} composition, a ProviderConfig for the Kubernetes provider, and optional secret templates.

Installation follows a four-step order designed to handle Crossplane's CRD chicken-and-egg problem: the Crossplane provider must be installed and healthy before ProviderConfig resources that reference it, and the XRD must be installed before the composition that implements it. The recommended sequence is:

\begin{enumerate}
    \item Pre-install: Crossplane provider and functions (wait for CRDs)
    \item Secrets: GitHub PAT, API auth, image pull credentials
    \item Helm install: XRD, composition, ProviderConfig
    \item Apply \texttt{XSDLC} CR: A single custom resource generates all quality gate infrastructure---Roles, RoleBindings, WorkflowTemplates, EventSources, Sensors, Ingresses, ScmProvider, GitRepository, PromotionStrategy, and ArgoCDCommitStatus resources
\end{enumerate}

The ordering of steps~1--3 is not enforced by the chart itself---Helm cannot wait for a provider's CRDs mid-install---so steps~1 and~2 are applied before \texttt{helm install}; Listing~\ref{lst:install-commands} gives the concrete commands.

\begin{lstlisting}[caption={Installation commands per phase.},label={lst:install-commands},basicstyle=\ttfamily\footnotesize]
# 1. Pre-install: Crossplane provider (repeat for functions)
kubectl apply -f providers/provider-kubernetes.yaml
kubectl wait --for=condition=Healthy \
  provider/provider-kubernetes --timeout=120s

# 2. Secrets: GitHub App, API auth, image pull credentials
kubectl create secret generic github-app-credentials \
  --namespace driveby \
  --from-literal=githubAppID=<APP_ID> \
  --from-literal=githubInstallationID=<INSTALLATION_ID> \
  --from-file=githubAppPrivateKey=<private-key.pem>
kubectl create secret generic driveby-api-auth \
  --namespace driveby --from-literal=api-key=<API_KEY> \
  --from-literal=api-key-header=X-API-Key
kubectl create secret docker-registry ghcr-creds \
  --namespace driveby --docker-server=ghcr.io \
  --docker-username=<USER> --docker-password=<TOKEN>

# 3. Helm install: XRD, composition, ProviderConfig
helm install driveby \
  oci://ghcr.io/meter-peter/charts/driveby \
  --version 3.0.0 --namespace driveby

# 4. Per application (later, by the application team)
kubectl apply -f xsdlc-<app>.yaml
\end{lstlisting}

A distinction in scope applies to step~4: steps~1--3 install the \textit{system} once per cluster by the platform team, whereas step~4 is the per-application pipeline declaration (Section~\ref{subsec:day1}), applied later and independently by each application team; Crossplane then provisions all child resources without further operator involvement.

% ----------------------------------------------------------------------------
\subsection{OCI Distribution}
\label{subsec:oci-distribution}
% ----------------------------------------------------------------------------

The chart is distributed as an OCI (Open Container Initiative) artifact~\cite{helm-oci}, stored in the same container registry that hosts the DriveBy container images. This unified model provides a \textit{single authentication boundary} (one registry credential covers images and charts), \textit{version-aligned storage} (chart and image artifacts sit side by side per release), and \textit{immutability} (OCI tags are treated as immutable, giving tamper resistance and reproducible installations), replacing the traditional separate Helm chart repository. The chart is published to \texttt{oci://ghcr.io/meter-peter/charts/driveby}; versioned releases are produced automatically by the release pipeline (Chapter~\ref{ch:workflow}) from the same Git tag that versions the container image and CLI binary, keeping all three artifact types version-aligned.

\section{Summary}
\label{sec:k8s-summary}
% ============================================================================

This chapter described the Kubernetes infrastructure that transforms DriveBy from a standalone CLI tool into a declarative, event-driven quality gate system, realizing the final stage of the architectural evolution traced in Section~\ref{sec:cli-to-cr-evolution}. A single \texttt{XSDLC} custom resource, reconciled by Crossplane's dual-provider composition under the level-triggered controller pattern, generates and self-heals the full pipeline---GitOps repository, environment branches, ArgoCD Applications, and the Argo Events/Workflows gate machinery with its dynamically rendered validation DAG. Chapter~\ref{ch:workflow} describes how this infrastructure operates within the broader GitOps pipeline: the two-repo architecture, the BYOCI design principle, and the promotion-driven quality gate flow.
