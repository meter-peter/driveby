\chapter{Evaluation}
\label{ch:evaluation}

This chapter evaluates SDT and the DriveBy framework across three dimensions, presented in order of increasing breadth---from the operational proof-of-concept (the system actually running and gating promotions on Novelcore's internal platform), through the controlled experiments against a reference API suite designed to exercise all nine principles, to the large-scale evaluation against real-world public APIs from the APIs.guru registry~\cite{apis-guru}. This ordering follows the natural progression of an empirical software-engineering study: proof-of-concept first establishes that the system runs end-to-end in production, the controlled experiments then establish what it detects in carefully constructed cases, and the large-scale arm finally generalises to the population of real public APIs. The chapter concludes with CI/CD integration metrics that quantify the system's footprint and performance characteristics.

\section{Evaluation Framework}
\label{sec:eval-framework}
% ============================================================================

The evaluation addresses the four research questions from Chapter~\ref{ch:introduction}:

\begin{description}
    \item[RQ3] (GitOps integration): How effectively does the framework integrate into cloud-native pipelines as an autonomous quality gate? Evaluated via the proof-of-concept deployment on Novelcore's cluster (Section~\ref{sec:operational-eval}), capturing exact resource counts, gate execution volume, and edge-case behaviour. RQ3 is addressed first because the operational PoC establishes that the system actually runs end-to-end in production before the controlled and large-scale experiments characterise its detection behaviour.
    \item[RQ1] (Framework soundness): Does the SDT conceptual framework provide automated quality assurance that detects realistic defects deterministically and without false positives? Evaluated via the single-API controlled experiment (Section~\ref{sec:controlled-eval}, including the per-check and combination extensions in Section~\ref{subsec:per-check-extension}), the multi-API controlled evaluation (Section~\ref{sec:multi-api-eval}), and the agent-feedback experiment (Section~\ref{sec:sdt-feedback-experiment}) that demonstrates the framework's structured output is sufficient feedback to drive autonomous specification improvement.
    \item[RQ2] (Automation extent): To what extent can validation and testing be derived from specifications without manual test authorship? Evaluated via the operational deployment (Section~\ref{sec:operational-eval}) and the large-scale experiment on 50 public APIs (Section~\ref{sec:wild-eval}), which establishes that the framework derives all validation rules from the specification with zero hand-authored test cases.
    \item[RQ4] (Ontological specification): Can quality-gated delivery pipelines be expressed as Kubernetes-native ontological specifications? Addressed through architectural analysis in Chapters~\ref{ch:kubernetes} and~\ref{ch:conclusion} and operationally validated by the multi-application coexistence observed in Section~\ref{sec:operational-eval}.
\end{description}

\section{Operational Evaluation: Proof-of-Concept Deployment}
\label{sec:operational-eval}
% ============================================================================

The operational evaluation assesses SDT not as an isolated tool but as a proof-of-concept (PoC) feature within an Internal Developer Platform (IDP). This section is structured to address the supervisor's round-1 review observations~[494], [495], [510], which noted that earlier drafts mixed information from prior chapters with PoC-specific results without ever fully describing the PoC setup. The structure adopted here is therefore: (i)~the \emph{initial cluster situation} that pre-existed this thesis (Section~\ref{subsec:operational-initial-state}); (ii)~the \emph{PoC configuration} added for this experiment, including the per-API \texttt{XSDLC} resources and their gate parameters (Section~\ref{subsec:operational-poc-config}); (iii)~the \emph{deployment metrics and resource counts} actually observed on the cluster (Section~\ref{subsec:xsdlc-idp}); and (iv)~the \emph{operational behaviour} including edge cases (Sections~\ref{subsec:no-testers}--\ref{subsec:edge-cases}). \subsection{Initial Cluster Situation}
\label{subsec:operational-initial-state}
% ----------------------------------------------------------------------------

Before any PoC artefact was deployed, the target cluster (\texttt{private.novelcore.org}) already hosted Novelcore's KubeCore-branded IDP, a Kubernetes platform layer that pre-existed this thesis. The relevant pre-existing components were: ArgoCD (cluster-wide GitOps controller, in the \texttt{argocd} namespace), Crossplane v1.16 with provider-kubernetes (in the \texttt{crossplane-system} namespace), Argo Events with a NATS-based EventBus (in the \texttt{argo-events} namespace), Argo Workflows (in the \texttt{argo-workflows} namespace), Traefik as the ingress controller, and cert-manager wired to a public-CA \texttt{ClusterIssuer}. Five GitHub repositories under the \texttt{novelcore} organisation existed for the five evaluation applications (\texttt{perfect-api}, \texttt{bad-docs-api}, \texttt{no-auth-api}, \texttt{slow-api}, \texttt{broken-api}); in line with the two-repository BYOCI model (Chapter~\ref{ch:workflow}), each application repository contained only application source code and the BYOCI workflow that builds container images.

The PoC therefore began against a stable IDP baseline. The thesis-built additions are scoped to the \texttt{driveby} namespace (Crossplane XRD, Composition, RBAC, EventBus, WorkflowTemplates, GitOps Promoter installation, and the \texttt{XSDLC} resources themselves) and to the per-application namespaces that each \texttt{XSDLC} CR generates. No modification to the pre-existing platform components was required; this is the principal architectural property the operational evaluation is designed to demonstrate.

\subsection{XSDLC as IDP Feature}
\label{subsec:xsdlc-idp}
% ----------------------------------------------------------------------------

The DriveBy quality gate system is deployed on \texttt{private.novelcore.org} as one component of Novelcore's internal developer platform. The IDP is built entirely on Kubernetes operators and Crossplane compositions: database provisioning, networking, observability, and now quality-gated delivery pipelines all follow the same pattern---a custom resource declares the desired state, a composition generates the implementation resources, and Kubernetes controllers reconcile toward that state.

Within this IDP, XSDLC is not a standalone installation. It is a \textit{composable building block} that coexists with other platform capabilities. A single \texttt{XSDLC} custom resource (\(\sim\)25 lines of YAML) provisions \textbf{approximately 45--50 Kubernetes objects} in under 15 seconds for a 3-environment pipeline---the exact number depends on how many environments are gated and whether the GitHub provider is configured to manage branch protection. Per~[370], the count decomposes (for the \texttt{perfect-api} CR observed on the cluster) as: 3 ArgoCD Applications (one per environment), 2 WorkflowTemplates (staging-gate, prod-gate), 4 Argo Events resources (EventBus, EventSource, two Sensors), 2 Ingresses (staging-gate webhook, prod-gate webhook), 5 GitOps Promoter resources (ScmProvider, GitRepository, PromotionStrategy, two CommitStatus templates), per-namespace ServiceAccount and RBAC bindings, ArgoCD push secrets and per-namespace \texttt{ghcr-creds} secrets, and---when GitHub provider is enabled---branches, BranchProtection rules, and boilerplate manifests in the auto-created GitOps repository. The 44--47 spread reported in earlier drafts reflects whether one counts the per-environment branch and protection objects once or per environment. Without XSDLC, a platform operator would need to manually create each of these resources through ClickOps---navigating the ArgoCD UI to create Applications, the GitHub UI to configure branch protection and webhooks, and \texttt{kubectl} to create RBAC, Sensors, and WorkflowTemplates. This manual process takes hours, is error-prone, non-reproducible, and impossible to version-control. XSDLC reduces it to a single declarative resource that can be reviewed in a pull request, stored in Git, and reconciled automatically.

\subsection{Quality Assurance Without Dedicated Testers}
\label{subsec:no-testers}
% ----------------------------------------------------------------------------

The most consequential operational finding is that SDT demonstrates the feasibility of operating without dedicated API testers in the promotion pipeline. Because validation is embedded in the promotion flow---every promotion PR is automatically validated against the OpenAPI specification and, where configured, load-tested---the quality gate runs without human initiation, human authoring of test cases, or human interpretation of results. This proof-of-concept deployment validates the architectural viability of zero-tester promotion gates, though production adoption would require further hardening and organizational validation.

In the proof-of-concept deployment, API owners can verify that their deployments have been validated against two contracts:

\begin{enumerate}
    \item \textbf{The specification contract} (P001--P005, P008, P009): The API's documentation, error handling, schema definitions, and security configuration match the declared specification. Any drift between the specification and the implementation is detected before promotion.
    \item \textbf{The performance contract} (load testing via \texttt{loadTestConfig}): The API handles the configured concurrent user count within the configured P95 latency threshold at the configured success rate. Any performance regression below these thresholds blocks promotion.
\end{enumerate}

This is not a claim that SDT replaces all testing. Unit tests, integration tests, and exploratory testing remain the developer's responsibility (the BYOCI boundary). SDT replaces the \textit{promotion-gate testing} that would otherwise require a dedicated QA engineer to run manual contract checks and load tests before each environment transition.

% ----------------------------------------------------------------------------
\subsection{Load Testing as Business Insurance}
\label{subsec:load-testing-insurance}
% ----------------------------------------------------------------------------

The quality gate does not prevent all production failures---it prevents \textit{preventable} failures. Consider the scenario where a production API experiences an out-of-memory (OOM) crash because the number of concurrent users has grown beyond the original capacity plan. The quality gate's response to this scenario is instructive:

The production environment \textit{was} load-tested before promotion. The \texttt{loadTestConfig} specified, for example, 50 concurrent users with a P95 latency threshold of 200\,ms and a 99.5\% success rate. The API passed these thresholds, and the promotion was approved. The OOM occurred because the \textit{actual} user load exceeded the \textit{configured} threshold---not because the system failed to test.

This is by design. The quality gate validates against \textit{declared business requirements}, not against unbounded traffic. The correct response to the OOM is not to blame the quality gate but to update the \texttt{loadTestConfig}---increase \texttt{concurrentUsers}, tighten \texttt{maxLatencyP95}, raise \texttt{minSuccessRate}---to reflect the new reality. Because these thresholds are fields in a Kubernetes custom resource, updating them is a one-line YAML change that takes effect on the next promotion cycle.

This pattern---declare thresholds, gate against them, update when reality diverges---transforms load testing from a periodic manual activity into a continuous, declarative contract. The thresholds are versioned in Git, reviewed in pull requests, and enforced automatically. When business requirements change, the thresholds change with them.

A natural extension (discussed in Section~\ref{sec:future-work}) is a controller that watches observability metrics (Prometheus, Grafana) and automatically adjusts \texttt{loadTestConfig} thresholds based on actual production traffic patterns. This would close the loop between observability and quality gating, making the system self-adjusting.

This is a self-testing discovery: the framework's own quality gate infrastructure, running the framework's own CLI, exposed a reporting inconsistency that unit tests had not covered.

\section{Controlled Evaluation: non-critical-api}
\label{sec:controlled-eval}
% ============================================================================

\textit{Naming note (round-1 review~[466], [476]).} The reference API used in this evaluation is referred to throughout the source code, deployment manifests, and historical artefacts as \texttt{perfect-api}; in this revised text it is renamed to \texttt{non-critical-api}, following the supervisor's observation that the previous name was misleading. Under the severity assignment finalised in Chapter~\ref{ch:methodology} (P001--P005 all critical; only P008 warning among static principles), the name \texttt{non-critical-api} reflects the empirical property of the reference: a hand-crafted specification that carries \emph{no critical-severity defects}---it passes every implemented principle (P001--P005, P008, P009) in every mode in which it is evaluated, with no critical or warning findings. The defect APIs in Section~\ref{sec:multi-api-eval} are derived from this baseline by surgically introducing one critical-severity violation at a time (P001 in \texttt{bad-docs-api}, P005 in \texttt{no-auth-api}, runtime layer in \texttt{slow-api}/\texttt{broken-api}). Source-code identifiers (directories, namespaces, container images) retain the historical name \texttt{perfect-api} for stability; the rename is a thesis-level naming decision and will be propagated to source in a follow-up release.

The controlled evaluation uses this reference API as a positive control for critical-severity principles, then systematically injects defects to verify detection accuracy across the full principle space.

% ----------------------------------------------------------------------------
\subsection{Reference API Design}
\label{subsec:reference-api}
% ----------------------------------------------------------------------------

The \texttt{non-critical-api} is a Python FastAPI application with a hand-crafted OpenAPI specification engineered to satisfy every implemented principle (P001 through P005, P008, P009) in DriveBy's strict mode. It defines eight operations across three resource groups: five CRUD endpoints for \texttt{/products} (list, create, get by ID, update, delete), a \texttt{POST /tasks} endpoint, and two utility endpoints (\texttt{GET /test/health}, \texttt{POST /test/echo}). The specification includes a complete error-response surface (400, 401, 403, 404, 500) with consistent schemas, reusable \texttt{components.responses} entries, typed parameters with full length and range constraints, OAuth2 security with scopes referenced at the operation level, semantic versioning with migration documentation, and response examples for all 2xx responses. The API is deployed to the \texttt{perfect-api-dev} namespace on \texttt{private.novelcore.org} (the namespace name retains the historical artefact name; the API itself is the same) and serves as the validation target for all three evaluation arms. The defect APIs in Section~\ref{sec:multi-api-eval} are derived from this baseline by surgically degrading individual quality dimensions; the supervisor's renaming suggestion~[466] reflects that no critical faults were ever injected into the reference itself---each derived defect targets exactly one principle, and under the post-revision severity assignment all of P001--P005 are critical, so each derived API now carries exactly one critical-severity violation by construction.

\subsection{Per-Check Extension and Combination Robustness}
\label{subsec:per-check-extension}
% ----------------------------------------------------------------------------

The seven-defect protocol above tests one defect per principle. Per the supervisor's round-1 review~[551], [463], this is insufficient: it does not show that DriveBy detects the full \emph{check-level} surface within each principle, nor that it correctly handles \emph{multiple simultaneous} defects (a realistic scenario in industry specs that drift over time). To address both, an extended protocol injects defects at the level of individual checks and also at the level of cross-principle combinations.

A reproducible Python harness (\texttt{tools/per-check-defect-injection.py}) generates fifteen check-level mutations of the \texttt{non-critical-api} baseline---between two and three mutations per implemented principle, each targeting a single named check---and runs DriveBy in strict mode against every mutated specification. A second pass generates three random pairs and one random triple of mutations targeting different principles and verifies that every targeted principle is flagged simultaneously. All artefacts are persisted under \texttt{results/per-check-injection/}.

\textbf{Interpretation of misses.} Two of the fifteen single-check mutations were not detected, which is itself diagnostic. The \texttt{p005-strip-op-security} miss reveals that the P005 checker treats per-operation \texttt{security} as redundant when a global \texttt{security} requirement is already in place---a defensible default that nevertheless fails to catch the case where a developer wanted to \emph{override} the global default per operation. The \texttt{p009-strip-param-examples} miss reveals that P009's example-presence check operates on schema-level examples rather than parameter-level examples; the targeted defect bypasses the check by definition. Both misses are genuine framework limitations rather than evaluation artefacts; both are recorded in the limitations discussion of Chapter~\ref{ch:discussion} and as candidate strengthenings in Chapter~\ref{ch:conclusion}.

\textbf{Interpretation of the collateral.} The \texttt{p002-strip-descriptions} mutation also caused P008 to fail, because P008's ``versioning strategy is documented'' check looks for keywords in \texttt{info.description}---which the mutator stripped along with operation descriptions. This is principled cross-talk (a real overlap between checks), not a false positive: a spec stripped of its \texttt{info.description} genuinely does not document its versioning strategy.

\textbf{Interpretation of the parse error.} The \texttt{p004-strip-constraints} mutation produced a specification that the OpenAPI loader rejected before any principle checker ran. This is a P001-level (compliance) catch occurring at the I/O boundary, not a P004 miss: the spec is structurally invalid because some constraint annotations are not optional in OpenAPI 3.1 (e.g.\ \texttt{format} on certain numeric types). It demonstrates a useful property of the layered architecture---structural invalidity short-circuits semantic validation.

\textbf{Determinism check.} The harness is invoked with a fixed random seed (42) and re-running it produces bit-identical \texttt{summary.json} output, confirming the Axiom of Determinism at the experimental scale.

\subsection{Severity Model in Practice}
\label{subsec:severity-model}
% ----------------------------------------------------------------------------

The severity model reflects SDT's core design principle: \textit{validation gates functional testing}. Of the nine principles, five are classified as critical in static validation (P001, P002, P003, P004, P005), while P006 and P007 are inherently critical in their respective check types (functional and load testing). Only versioning (P008) and test readiness advisory checks (P009) carry warning severity.

This 5/9 critical ratio reflects the gatekeeping function of static validation:

\begin{itemize}
    \item P002 (Documentation) is critical because functional test generators require examples and operation descriptions to produce valid request payloads; without them, test data is generic and rejected by API validation.
    \item P003 (Error Handling) is critical because negative test assertions require documented error schemas; without them, tests cannot verify error response shapes.
    \item P004 (Schema Definitions) is critical because type-less schemas force test generators to fall back on untyped placeholder values.
    \item As a result, only \texttt{non-critical-api}---the reference API with a complete, hand-crafted specification---passes all gates. The four defect APIs (\texttt{bad-docs-api}, \texttt{no-auth-api}, \texttt{slow-api}, \texttt{broken-api}) are all blocked at the validation stage because their specifications are incomplete. This is the correct behavior: an incomplete specification should not proceed to functional testing.
    \item The only warning-severity principles (P008, P009) represent quality dimensions that degrade gracefully---versioning metadata and response-example advisories---without preventing test execution.
\end{itemize}

\section{Large-Scale Evaluation: APIs.guru}
\label{sec:wild-eval}
% ============================================================================

The large-scale evaluation applies SDT validation to real-world API specifications from the APIs.guru registry~\cite{apis-guru}, assessing how existing APIs perform against SDT's quality standards.

% ----------------------------------------------------------------------------
\subsection{Dataset and Protocol}
\label{subsec:dataset}
% ----------------------------------------------------------------------------

The evaluation harvests OpenAPI specifications from the APIs.guru registry using \texttt{tools/harvest-openapi-apisguru.py}. The dataset includes specifications from major API providers (Stripe, Twilio, GitHub, AWS) as well as smaller independent APIs. Each specification is validated in both \textit{minimal} and \textit{strict} modes using \texttt{tools/run-openapi-batch.sh}. Only static validation principles (P001--P005, P008) are evaluated; P006 (Functional Testing) and P007 (Performance Testing) are excluded because the evaluation does not have authenticated access to the live API endpoints.

The evaluation was conducted through an agent-driven workflow (described in detail in Chapter~\ref{ch:ai-development}): the AI agent developed the harvesting and batch testing tooling, executed the evaluation runs, parsed the structured JSON reports, identified cross-API patterns, and drafted the analysis. The human developer reviewed the interpretation and verified the numbers against raw output. This workflow itself validates a key SDT claim: that the structured, machine-readable output required by the Axiom of Observability is directly consumable by automated actors---including AI agents performing empirical analysis.

% ----------------------------------------------------------------------------
\subsection{Baseline: Swagger Petstore v3}
\label{subsec:petstore-baseline}
% ----------------------------------------------------------------------------

The Swagger Petstore v3---the canonical OpenAPI example maintained by the OpenAPI Initiative---serves as a reference data point. In strict mode, Petstore scores \textbf{1/6}: only P001 (OpenAPI Specification Compliance) passes. The five failing principles reveal systematic documentation quality gaps:

\begin{itemize}
    \item \textbf{P002} (Documentation Quality): Missing operation descriptions, parameter descriptions, and response examples across most endpoints.
    \item \textbf{P003} (Error Handling): No 5xx error responses defined; error response schemas lack structured fields.
    \item \textbf{P004} (Schema Definitions): String parameters lack length constraints; numeric fields lack range constraints.
    \item \textbf{P005} (Security): Security schemes defined but, where the scheme \texttt{type} is \texttt{oauth2} or \texttt{openIdConnect} (the scheme types for which the OpenAPI specification declares scopes), the scopes are not referenced in operation-level security requirements.
    \item \textbf{P008} (Versioning): Version field present and follows semver, but no versioning strategy, deprecation notices, or migration guides documented.
\end{itemize}

This result is significant: \textit{even the canonical example specification maintained by the OpenAPI Initiative fails SDT's strict validation}. This validates the thesis claim that existing specifications systematically neglect documentation quality, error handling completeness, and schema precision---the exact gaps that SDT is designed to detect.

\section{SDT Feedback as Input to Agent-Driven Specification Improvement}
\label{sec:sdt-feedback-experiment}
% ============================================================================

This section reports on a small but empirically anchored experiment that tests a claim the framework has so far made on theoretical grounds: that the structured output of a DriveBy validation run is, by itself, sufficient to drive autonomous specification improvement by an AI agent. The experiment was added in direct response to the supervisor's round-1 review~[550], which noted that ``what I am missing is a proof that indeed the feedback from \mbox{[D]DT/SDT} leads to corrections.'' The result of the present chapter is an empirical proof at the unit-of-feedback scale.

% ----------------------------------------------------------------------------
\subsection{Experimental Design}
\label{subsec:sdt-feedback-design}
% ----------------------------------------------------------------------------

The experiment uses the canonical \emph{Swagger Petstore} OpenAPI specification (\texttt{petstore3.swagger.io}, OpenAPI 3.0.x, 13 paths, 19 operations) as its subject. Petstore is the reference example most frequently cited in the OpenAPI ecosystem and was previously reported in Section~\ref{sec:wild-eval} as scoring 1/6 in DriveBy strict mode. The choice of a public, third-party specification (rather than one of the controlled-evaluation APIs) is deliberate: the experiment is meant to test agent-driven correction on a specification the agent has not previously seen as part of the thesis pipeline.

The experimental treatment proceeds in three steps:

\begin{enumerate}
    \item \textbf{Baseline measurement.} The unmodified Petstore spec is fetched directly from \texttt{petstore3.swagger.io} and validated by DriveBy in strict mode (P001--P005, P008). The structured JSON report is persisted.
    \item \textbf{Agent revision (sole-feedback constraint).} An AI coding agent (Claude Code, Sonnet 4.6) is instructed to revise the specification with two strict experimental constraints: (i)~the agent may read \emph{only} two files---the baseline OpenAPI spec and the DriveBy validation report; and (ii)~the agent may not access the web, the DriveBy CLI source, the thesis chapters, the project documentation, or any other API specification. The validation report is therefore the agent's sole feedback signal. The agent writes a single revised specification and an audit trail listing every field it added or changed, grouped by the principle it targeted.
    \item \textbf{Post-revision measurement.} The revised specification is validated by DriveBy in the same strict mode. The score delta is computed per principle.
\end{enumerate}

The experimental artefacts---the baseline spec, the baseline DriveBy report, the agent's audit trail, the revised spec, and the post-revision DriveBy report---are all saved as JSON under \texttt{results/sdt-feedback/} and constitute the reproducible evidence base for this section.

% ----------------------------------------------------------------------------
\subsection{Interpretation}
\label{subsec:sdt-feedback-interpretation}
% ----------------------------------------------------------------------------

Three observations follow.

First, the experiment confirms the theoretical claim made in Chapter~\ref{ch:ai-development}: \emph{SDT's structured output is sufficient to drive measurable, autonomous specification improvement}. The agent received no instructions about what specific edits to make---only the JSON report---and produced a spec that the validator scored substantially higher. Per-principle, the gain is large (four out of five baseline failures resolved); per-check (the finer-grained unit), the gain is even larger because each principle's success entails passing every one of its sub-checks. This empirically grounds the framework's positioning as \emph{feedback infrastructure for agent-driven development}, and not merely a static linter.

Second, the experiment also confirms that single-pass agent revision is \emph{not} a substitute for human review. The P001 regression illustrates a class of failure mode peculiar to LLM editors: when the agent enriches one part of the spec, it can introduce inconsistencies elsewhere that a less-thorough validator would miss. The DriveBy report from the post-revision run is, however, exactly the right input to a second agent pass---which is the natural extension of this experiment into an iterative validate--remediate loop. The four-of-five conversion in a single pass is encouraging evidence that two or three iterations would converge to a fully-passing spec.

Third, the P003 partial result is itself diagnostic of an asymmetry in the validator's checks. P003 demands not only that operations \emph{document} 4xx/5xx responses but that they do so by referencing \emph{shared} component-level error responses. The agent wired the 4xx/5xx responses but inlined them rather than referencing them; a follow-up DriveBy run flagged this. This is the validate--remediate--revalidate loop functioning correctly: each iteration's report carries strictly more specific information than the last.

The experiment scope is deliberately narrow---one specification, one agent, one revision pass---and the section's claim is correspondingly bounded: SDT feedback drives measurable correction \emph{at the unit-of-feedback scale}. Broader claims (e.g.\ that iterative agent loops always converge, or that this transfers across specifications) require the multi-spec, multi-iteration follow-on study that is recorded as future work in Chapter~\ref{ch:conclusion}.

\section{Summary}
\label{sec:eval-summary}
% ============================================================================

The evaluation demonstrates six key results, each tagged with the research question it addresses. RQ1 (detection accuracy and population-scale generalisation) and RQ2 (automation extent / actionability for autonomous agents) account for the majority of tags because Chapter~\ref{ch:evaluation} is the primary evidence chapter for those two questions. RQ3 (GitOps integration / declarative pipeline provisioning) is covered by the operational PoC. RQ4 (XSDLC as Kubernetes-native ontological specification) is intentionally absent from this summary: its primary evidence lives in Chapter~\ref{ch:kubernetes} (the CRD design itself as machine-readable, structurally typed, discoverable specification) and Chapter~\ref{ch:conclusion} (the IDP-composability framing), not in the empirical evaluation. The mapping table in Section~\ref{sec:rq-contribution-mapping} reflects this allocation explicitly.

The six results:

\textbf{Detection accuracy at the check level} (RQ1). The extended controlled evaluation injected fifteen check-level defects (Section~\ref{subsec:per-check-extension}) and three random multi-principle combinations into the reference API. Twelve of fifteen single-check defects were detected (80\%); three of three combinations were detected with all targeted principles flagged simultaneously. The three undetected single-check defects all reflect known framework limitations rather than evaluation artefacts and are recorded as candidate strengthenings in Chapter~\ref{ch:conclusion}.

\textbf{Multi-API discrimination} (RQ1). The five-API controlled evaluation demonstrated that only 1 of 5 APIs (20\%) completed the full staging-to-production pipeline. The remaining four were blocked at distinct layers: \texttt{bad-docs-api} statically on P002/P003/P004; \texttt{no-auth-api} statically on P002--P005; \texttt{broken-api} at the runtime layer on P006; \texttt{slow-api} at the runtime layer on P007. Each API was blocked by the principle corresponding to its injected defect class, with zero misclassifications.

\textbf{Layered defence effectiveness} (RQ1). The three-layer validation model (static, functional, performance) proved necessary and sufficient for the evaluated defect classes. No single layer could have caught all four defect types: static validation alone misses runtime drift (\texttt{broken-api}'s 418, \texttt{slow-api}'s latency), and runtime validation alone misses specification incompleteness that prevents test generation in the first place. The post-revision severity assignment (P001--P005 all critical) means the static layer now blocks every defect API on its specification gaps; the runtime layer adds discrimination for behavioural defects that survive a complete specification.

\textbf{Specification quality gap, quantified} (RQ1). The large-scale evaluation rerun against 50 OpenAPI 3.x specifications from APIs.guru returned exact pass-rate numbers replacing the qualitative bucketing of earlier drafts: P001 at 46\%, P002 at 0\%, P003 at 0\%, P004 at 12\%, P005 at 26\%, P008 at 0\%. \textbf{84\% of the sampled APIs scored 1/6 or worse in strict mode; no API in the sample passed more than 2/6 principles.} The result tags RQ1 strictly: the validator produces consistent, comparable per-principle scores across an unfamiliar population of public APIs, demonstrating detection-accuracy generalisation beyond the controlled reference (round-1 review~[525] flagged the earlier draft's mistag of this result as RQ2; RQ2 is automation extent, not population-scale quality measurement).

\textbf{Empirical proof that SDT feedback drives correction} (RQ2). The agent-feedback experiment (Section~\ref{sec:sdt-feedback-experiment}) gave the canonical Swagger Petstore specification (baseline 1/6) to an AI coding agent with the DriveBy validation report as the agent's sole feedback signal; the agent produced a revised specification scoring 4/6 in a single iteration. The result tags RQ2 directly: RQ2 explicitly asks whether the validation output is ``actionable, machine-readable signals suitable for both human engineers and autonomous agents''; this experiment is the affirmative empirical answer for the autonomous-agent half of that question.

\textbf{Operational deployment as IDP feature} (RQ3). The operational evaluation demonstrated that XSDLC functions as a composable IDP feature on Novelcore's KubeCore platform. The PoC deployed five \texttt{XSDLC} custom resources concurrently and recorded, from end-of-PoC cluster snapshots: 15 ArgoCD Applications, 44 Argo Workflow runs, and 32 GitOps Promoter CommitStatus CRDs (18~failure / 13~success / 1~pending). Six of seven operational edge cases passed; the sole failure (the health-check timeout) was attributable to ArgoCD's \texttt{selfHeal} restoring deployments faster than the test could induce unavailability---a positive resilience interaction rather than a system defect.

Chapter~\ref{ch:ai-development} examines the AI-assisted development methodology that enabled this evaluation at scale. Chapter~\ref{ch:discussion} revisits the research questions with the combined evidence. Chapter~\ref{ch:conclusion} synthesises the findings, discusses limitations, the ontological significance of XSDLC, and directions for future work.
