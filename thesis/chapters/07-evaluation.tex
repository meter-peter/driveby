\chapter{Evaluation}
\label{ch:evaluation}

This chapter evaluates SDT and the DriveBy framework across four arms, the first three ordered by increasing breadth: the operational proof-of-concept (the system actually running and gating promotions on Novelcore's internal platform, concluding with the CI/CD integration metrics that quantify its footprint), the controlled experiments against a reference API suite designed to exercise all nine principles, and the large-scale evaluation against real-world public APIs from the APIs.guru registry~\cite{apis-guru}. The fourth arm---the agent-feedback experiment (Section~\ref{sec:sdt-feedback-experiment})---closes the loop by testing whether the framework's structured validation output is, by itself, sufficient feedback for an autonomous agent to improve a defective specification, demonstrating that the signals the system produces are actionable.

% ============================================================================
\section{Evaluation Framework}
\label{sec:eval-framework}
% ============================================================================

The evaluation addresses the four research questions stated in full in Chapter~\ref{ch:introduction}:

\begin{description}
    \item[RQ3] (GitOps integration; declarative gate provisioning) Evaluated via the proof-of-concept deployment on Novelcore's cluster (Section~\ref{sec:operational-eval}), capturing exact resource counts, gate execution volume, edge-case behaviour, and the CI/CD integration metrics (Section~\ref{sec:cicd-metrics}). RQ3 is addressed first: the PoC establishes that the system runs end-to-end before the other arms characterise its detection behaviour.
    \item[RQ1] (feasibility of automated, tester-free promotion-gate quality assurance) Evaluated via the single-API controlled experiment (Section~\ref{sec:controlled-eval}, including the per-check and combination extensions of Section~\ref{subsec:per-check-extension}), the multi-API controlled evaluation (Section~\ref{sec:multi-api-eval}), the large-scale evaluation (Section~\ref{sec:wild-eval}), which generalises the detection results to a population of public APIs, and the agent-feedback experiment (Section~\ref{sec:sdt-feedback-experiment}).
    \item[RQ2] (automatic derivation of validation rules; actionable machine-readable signals) The derivation half is evidenced by the operational deployment (Section~\ref{sec:operational-eval}) and the large-scale experiment on 50 public APIs (Section~\ref{sec:wild-eval}), which derive all validation rules from the specification with zero hand-authored test cases. The actionability half is evidenced primarily by the agent-feedback experiment (Section~\ref{sec:sdt-feedback-experiment}), in which the validation report alone drives autonomous specification correction, and secondarily by the agent-driven analysis workflow of Section~\ref{subsec:dataset}.
    \item[RQ4] (pipelines as Kubernetes-native ontological specifications) Addressed through architectural analysis in Chapter~\ref{ch:kubernetes} and operationally validated by the multi-application coexistence observed in Section~\ref{sec:operational-eval}.
\end{description}

\section{Operational Evaluation: Proof-of-Concept Deployment}
\label{sec:operational-eval}
% ============================================================================

The operational evaluation assesses SDT not as an isolated tool but as a proof-of-concept (PoC) feature within an Internal Developer Platform (IDP), proceeding from the pre-existing platform state (Section~\ref{subsec:operational-initial-state}) through the PoC configuration, observed deployment metrics, and operational behaviour to the CI/CD integration metrics (Section~\ref{sec:cicd-metrics}).

% ----------------------------------------------------------------------------
\subsection{Initial Situation}
\label{subsec:operational-initial-state}
% ----------------------------------------------------------------------------

Before any PoC artefact was deployed, the target cluster (\texttt{private.\allowbreak novelcore.\allowbreak org}) already hosted Novelcore's KubeCore-branded IDP, a Kubernetes platform layer that pre-existed this thesis. The relevant pre-existing components were: ArgoCD (cluster-wide GitOps controller), Crossplane v1.16 with provider-kubernetes, Argo Events with a NATS-based EventBus, Argo Workflows, Traefik as the ingress controller, and cert-manager wired to a public-CA \texttt{ClusterIssuer}.

Outside the cluster, five GitHub repositories under the \texttt{novelcore} organisation existed for the five evaluation applications (\texttt{perfect-api}, \texttt{bad-docs-api}, \texttt{no-auth-api}, \texttt{slow-api}, \texttt{broken-api}); in line with the two-repository BYOCI model (Chapter~\ref{ch:workflow}), each application repository contained only application source code and the BYOCI workflow that builds container images.

The PoC therefore began against a stable IDP baseline. The thesis-built additions are scoped to the \texttt{driveby} namespace (Crossplane XRD, Composition, RBAC, EventBus, WorkflowTemplates, GitOps Promoter installation, and the \texttt{XSDLC} resources themselves) and to the per-application namespaces that each \texttt{XSDLC} CR generates. No modification to the pre-existing platform components was required; this is the principal architectural property the operational evaluation is designed to demonstrate.

\subsection{XSDLC as IDP Feature}
\label{subsec:xsdlc-idp}
% ----------------------------------------------------------------------------

The DriveBy quality gate system is deployed on \texttt{private.\allowbreak novelcore.\allowbreak org} as one composable building block of Novelcore's Crossplane-based IDP, following the same declarative pattern as the platform's other capabilities (Chapter~\ref{ch:kubernetes}). A single \texttt{XSDLC} custom resource (\(\sim\)25 lines of YAML) provisions \textbf{approximately 44 Kubernetes objects} (up to 47, depending on counting convention) in under 15 seconds for a 3-environment pipeline. For the \texttt{perfect-api} CR observed on the cluster, the count decomposes as: 3 ArgoCD Applications, 2 WorkflowTemplates, 4 Argo Events resources, 2 Ingresses, 5 GitOps Promoter resources, per-namespace ServiceAccount/RBAC and secrets, and---when the GitHub provider is enabled---branches, BranchProtection rules, and boilerplate manifests in the auto-created GitOps repository (the full generated-resource catalogue is given in Chapter~\ref{ch:kubernetes}). The 44--47 spread reflects whether the per-environment branch and protection objects are counted once or per environment.

Without XSDLC, a platform operator would create each of these resources manually through ClickOps across the ArgoCD UI, GitHub settings, and \texttt{kubectl}---a process taking hours, error-prone, and impossible to version-control. XSDLC reduces it to a single declarative resource reviewed in a pull request and reconciled automatically.

% ----------------------------------------------------------------------------
\subsection{Quality Assurance Without Dedicated Testers}
\label{subsec:no-testers}
% ----------------------------------------------------------------------------

The most consequential operational finding is that SDT demonstrates the feasibility of operating without dedicated API testers in the promotion pipeline. Because validation is embedded in the promotion flow---every promotion PR is automatically validated against the specification and, where configured, load-tested---the gate runs without human initiation, test authoring, or result interpretation. One qualification applies: where \texttt{autoMerge:false} is configured (as on all five production gates in this PoC), a human must still merge the promotion PR---the validation \emph{verdict} is produced without human involvement, but the final promotion \emph{decision} remains a deliberate human act. This proof-of-concept deployment validates the architectural viability of zero-tester promotion gates, though production adoption would require further hardening and organizational validation.

In the proof-of-concept deployment, API owners can verify that their deployments have been validated against two contracts:

\begin{enumerate}
    \item \textbf{The specification contract} (P001--P005, P008, P009): The API's documentation, error handling, schema definitions, and security configuration match the declared specification. Any \emph{structural} drift is detected before promotion; \emph{semantic} drift---structurally valid but substantively wrong response content---lies beyond the static contract and is caught only to the extent that functional testing (P006) exercises the affected paths.
    \item \textbf{The performance contract} (\texttt{loadTestConfig}): the API meets the configured concurrency, P95 latency, and success-rate thresholds; any regression below them blocks promotion.
\end{enumerate}

This is not a claim that SDT replaces all testing. Unit tests, integration tests, and exploratory testing remain the developer's responsibility (the BYOCI boundary). SDT replaces the \textit{promotion-gate testing} that would otherwise require a dedicated QA engineer before each environment transition.

% ----------------------------------------------------------------------------
\subsection{Load Testing as Business Insurance}
\label{subsec:load-testing-insurance}
% ----------------------------------------------------------------------------

The quality gate prevents \textit{preventable} failures, not all failures. Consider a production out-of-memory crash caused by concurrent users growing beyond the original capacity plan: the environment \textit{was} load-tested before promotion against its declared \texttt{loadTestConfig} thresholds (for example, 50 concurrent users, P95 $\leq$ 200\,ms, 99.5\% success) and passed; the crash occurred because \textit{actual} load exceeded the \textit{configured} threshold. This is by design---the gate validates against declared business requirements, not unbounded traffic---and the correct response is to update the thresholds to reflect the new reality, a one-line YAML change in the custom resource that takes effect on the next promotion cycle.

This pattern---declare thresholds, gate against them, update when reality diverges---transforms load testing from a periodic manual activity into a continuous, declarative contract versioned in Git. A natural extension (Section~\ref{sec:future-work}) is a controller that watches observability metrics and adjusts \texttt{loadTestConfig} thresholds from actual production traffic, closing the loop between observability and quality gating.

\section{Controlled Evaluation: non-critical-api}
\label{sec:controlled-eval}
% ============================================================================

\textit{Naming note.} The reference API is referred to throughout the source code, deployment manifests, and historical artefacts as \texttt{perfect-api}; it is renamed here to \texttt{non-critical-api} because the previous name was misleading. Under the severity assignment of Chapter~\ref{ch:methodology}, the new name reflects the empirical property of the reference: it carries \emph{no critical-severity defects}, passing every implemented principle (P001--P005, P008, P009) in every mode in which it is evaluated, with no critical or warning findings. Source-code identifiers retain the historical name for stability; the rename is a thesis-level naming decision to be propagated to source in a follow-up release.

The controlled evaluation uses this reference API as a positive control for critical-severity principles, then systematically injects defects to verify detection accuracy across the full principle space.

% ----------------------------------------------------------------------------
\subsection{Reference API Design}
\label{subsec:reference-api}
% ----------------------------------------------------------------------------

The \texttt{non-critical-api} is a small \emph{product management} API: a Python FastAPI application with a hand-crafted OpenAPI specification engineered to satisfy every implemented principle in DriveBy's strict mode. It defines eight operations across three resource groups: five CRUD endpoints for \texttt{/products}, a \texttt{POST /tasks} endpoint, and two utility endpoints (health, echo). The specification includes a complete error-response surface (400, 401, 403, 404, 500) with consistent schemas, reusable \texttt{components.responses} entries, typed parameters with full length and range constraints, OAuth2 security with scopes referenced at the operation level, semantic versioning with migration documentation, and response examples for all 2xx responses. The reference is clean at the runtime layer as well as the static layer: it passes P006 functional testing and clears its P007 load-test thresholds in the operational pipeline (Section~\ref{subsec:prod-results}), qualifying it as the base from which behavioural faults can be injected. The API is deployed to the \texttt{perfect-api-dev} namespace (the historical artefact name) on the target cluster and serves as the validation target for the controlled and operational arms.

\subsection{Per-Check Extension and Combination Robustness}
\label{subsec:per-check-extension}
% ----------------------------------------------------------------------------

The seven-defect protocol above tests one defect per principle; it shows neither full \emph{check-level} coverage within each principle nor behaviour under \emph{multiple simultaneous} defects (a realistic scenario in specs that drift over time). An extended protocol therefore injects defects at the level of individual checks and of cross-principle combinations.

A reproducible Python harness (\texttt{tools/per-check-defect-injection.py}) generates fifteen check-level mutations of the \texttt{non-critical-api} baseline---two to three per implemented principle, each targeting a single named check---and runs DriveBy in strict mode against each. A second pass generates four randomised mutation combinations (three pairs and one triple spanning different principles) and verifies that every targeted principle is flagged simultaneously. One pair could not be evaluated: its mutated specification triggers a nil-pointer panic inside the upstream \texttt{kin-openapi} parser, aborting the validator before any principle runs---an upstream library defect, recorded as such rather than as a detection miss. All artefacts are persisted under \texttt{results/per-check-injection/}. The protocol samples the check space rather than exhausting it; complete coverage is recorded as future evaluation work.

\textbf{Interpretation of misses.} The two undetected single-check mutations have different natures. The \texttt{p005-strip-op-security} miss is an injection artefact rather than a framework limitation: the removed per-operation \texttt{security} entries are redundant under the intact global \texttt{security} requirement, so the mutated specification is still fully protected and there is no real defect to report. The \texttt{p009-strip-param-examples} miss, by contrast, is a genuine framework limitation: P009's example-presence check operates on schema-level rather than parameter-level examples, so the targeted defect bypasses the check by definition. The genuine miss is recorded in the limitations discussion of Chapter~\ref{ch:discussion} and as a candidate strengthening in Chapter~\ref{ch:conclusion}; the injection artefact is recorded as a defect-generator refinement for future rounds.

\textbf{Interpretation of the collateral.} The \texttt{p002-strip-descriptions} mutation also caused P008 to fail, because P008's ``versioning strategy is documented'' check looks for keywords in \texttt{info.description}---which the mutator stripped along with operation descriptions. This is principled cross-talk (a real overlap between checks), not a false positive: a spec stripped of its \texttt{info.description} genuinely does not document its versioning strategy.

\textbf{Interpretation of the parse error.} The \texttt{p004-strip-constraints} mutation produced a specification the OpenAPI loader rejected before any principle checker ran---a P001-level catch at the I/O boundary, not a P004 miss, since some constraint annotations are not optional in OpenAPI 3.1. It demonstrates a useful property of the layered architecture: structural invalidity short-circuits semantic validation.

\textbf{Determinism check.} The harness is invoked with a fixed random seed (42) and re-running it produces bit-identical \texttt{summary.json} output, confirming the Axiom of Determinism at the experimental scale.

\textbf{Conclusions from the per-check extension.} Fourteen of the fifteen single-check mutations are accounted for (twelve detected, one neutralised by the loader's structural validation, one an injection artefact with no real defect), every evaluable multi-defect combination was fully detected, and repeated runs are bit-identical. The remaining limitations---P009's parameter-level blind spot, the sampled rather than exhaustive check space, and the combination unevaluable due to an upstream parser defect---are carried into Chapters~\ref{ch:discussion} and~\ref{ch:conclusion}.

\subsection{Severity Model in Practice}
\label{subsec:severity-model}
% ----------------------------------------------------------------------------

The severity assignment (defined in Chapter~\ref{ch:methodology}) reflects SDT's core design principle: \textit{validation gates functional testing}. Seven of the nine principles are Critical---the static P001--P005 plus the runtime P006 and P007, whose failures block within their respective gate types; a declared performance threshold is a contract, so a P007 breach always blocks promotion exactly as a static critical failure does---there is no advisory mode for a violated SLA. The 5/7 static-critical ratio reflects the gatekeeping function of static validation:

\begin{itemize}
    \item P002 (Documentation) is critical because functional test generators require examples and operation descriptions to produce valid request payloads; without them, test data is generic and rejected by API validation.
    \item P003 (Error Handling) is critical because negative test assertions require documented error schemas; without them, tests cannot verify error response shapes.
    \item P004 (Schema Definitions) is critical because type-less schemas force test generators to fall back on untyped placeholder values.
    \item As a result, the specification-defect APIs are blocked at static validation and the behavioural-defect APIs at the runtime stage---the correct behaviour: an incomplete specification should not proceed to functional testing, while a complete specification with a defective implementation should fail exactly there.
    \item The only warning-severity principles (P008, P009) represent quality dimensions that degrade gracefully---versioning metadata and response-example advisories---without preventing test execution.
\end{itemize}

\section{Large-Scale Evaluation: APIs.guru}
\label{sec:wild-eval}
% ============================================================================

The large-scale evaluation applies SDT validation to real-world API specifications from the APIs.guru registry~\cite{apis-guru}, assessing how existing APIs perform against SDT's quality standards.

% ----------------------------------------------------------------------------
\subsection{Dataset and Protocol}
\label{subsec:dataset}
% ----------------------------------------------------------------------------

The evaluation harvested API specifications from the APIs.guru registry using \texttt{tools/harvest-openapi-apisguru.py}. The dataset comprises \textbf{70 specifications in total}: 50 OpenAPI 3.x (26 at 3.0.x, 24 at 3.1.0) and 20 Swagger~2.0, drawn from major API providers (Stripe, Twilio, GitHub, AWS) as well as smaller independent APIs. Results are reported per version family (Sections~\ref{subsec:pass-rates} and~\ref{subsec:swagger2-eval}) because the two arms exercise different specification adapters and the version-agnosticity claim requires per-adapter evidence; the 2.0 arm reproduces the 3.x pattern, so the split changes no conclusion. Each specification is validated in both \textit{minimal} and \textit{strict} modes using \texttt{tools/run-openapi-batch.sh}. Only the static principles of strict mode (P001--P005, P008) are evaluated: P006 (Functional Testing) and P007 (Performance Testing) are excluded because the evaluation lacks authenticated access to the live API endpoints, and P009 (Test Readiness)---although static---is excluded because it belongs to the test-ready mode set, not the strict mode applied uniformly across the sample (Table~\ref{tab:baseline-results}), and its advisory checks presuppose the downstream functional testing this protocol does not perform.

The evaluation was conducted through an agent-driven workflow (Chapter~\ref{ch:ai-development}): the AI agent developed the harvesting and batch-testing tooling, executed the runs, parsed the structured JSON reports, and drafted the analysis; the human developer reviewed the interpretation and verified the numbers against raw output. The workflow itself validates a key SDT claim: the machine-readable output required by the Axiom of Observability is directly consumable by automated actors, including AI agents performing empirical analysis.

% ----------------------------------------------------------------------------
\subsection{Baseline: Swagger Petstore v3}
\label{subsec:petstore-baseline}
% ----------------------------------------------------------------------------

The Swagger Petstore v3---the canonical OpenAPI example maintained by the OpenAPI Initiative---serves as a reference data point. In strict mode, Petstore scores \textbf{1/6}: only P001 (OpenAPI Specification Compliance) passes. The five failing principles reveal systematic documentation quality gaps:

\begin{itemize}
    \item \textbf{P002} (Documentation Quality): Missing operation descriptions, parameter descriptions, and response examples across most endpoints.
    \item \textbf{P003} (Error Handling): No 5xx error responses defined; error response schemas lack structured fields.
    \item \textbf{P004} (Schema Definitions): String parameters lack length constraints; numeric fields lack range constraints.
    \item \textbf{P005} (Security): Security schemes defined, but their scopes (for \texttt{oauth2}/\texttt{openIdConnect} schemes) are not referenced in operation-level security requirements.
    \item \textbf{P008} (Versioning): Version field present and follows semver, but no versioning strategy, deprecation notices, or migration guides documented.
\end{itemize}

This result is significant: \textit{even the canonical example specification maintained by the OpenAPI Initiative fails SDT's strict validation}, supporting the thesis claim that existing specifications systematically neglect exactly the gaps SDT is designed to detect.

A plausible explanation is toolchain maturity: specifications still published in 2.0 form have survived a decade of strict parser ecosystems, whereas the 3.x sample includes newer 3.1.0 documents whose structural conventions are less uniformly enforced. P002, P003, and P008, by contrast, fail across the entire sample in both arms.

\paragraph{Summary.} DriveBy validates real-world 2.0 specifications end-to-end with the same per-principle output structure as 3.x---so downstream consumers such as the agent-feedback loop (Section~\ref{sec:sdt-feedback-experiment}) work without modification---and the 3.x empirical pattern reproduces in 2.0; raw artefacts are version-controlled under \texttt{results/swagger2-evaluation/}.

% ============================================================================
\section{SDT Feedback as Input to Agent-Driven Specification Improvement}
\label{sec:sdt-feedback-experiment}
% ============================================================================

This section reports a small but empirically anchored experiment testing a claim the framework has so far made on theoretical grounds: that the structured output of a DriveBy validation run is, by itself, sufficient to drive autonomous specification improvement by an AI agent. The result is an empirical proof at the unit-of-feedback scale.

% ----------------------------------------------------------------------------
\subsection{Experimental Design}
\label{subsec:sdt-feedback-design}
% ----------------------------------------------------------------------------

The experiment uses the canonical \emph{Swagger Petstore} OpenAPI specification (\texttt{petstore3.swagger.io}, OpenAPI 3.0.x, 13 paths, 19 operations), previously reported in Section~\ref{sec:wild-eval} as scoring 1/6 in strict mode. The choice of a public, third-party specification (rather than one of the controlled-evaluation APIs) is deliberate: the experiment tests agent-driven correction on a specification the agent has not previously seen as part of the thesis pipeline.

The experimental treatment proceeds in three steps:

\begin{enumerate}
    \item \textbf{Baseline measurement.} The unmodified Petstore spec is fetched directly from \texttt{petstore3.swagger.io} and validated by DriveBy in strict mode (P001--P005, P008). The structured JSON report is persisted.
    \item \textbf{Agent revision (sole-feedback constraint).} An AI coding agent (Claude Code, Sonnet 4.6) is instructed to revise the specification with two strict experimental constraints: (i)~the agent may read \emph{only} two files---the baseline OpenAPI spec and the DriveBy validation report; and (ii)~the agent may not access the web, the DriveBy CLI source, the thesis chapters, the project documentation, or any other API specification. The validation report is therefore the agent's sole feedback signal. The agent writes a single revised specification and an audit trail listing every field it added or changed, grouped by the principle it targeted.\footnote{The full instruction and the audit trail are archived at \texttt{results/sdt-feedback/petstore-revised/agent-changes.md}, alongside the baseline and revised specifications and all validation reports.}
    \item \textbf{Post-revision measurement.} The revised specification is validated by DriveBy in the same strict mode. The score delta is computed per principle.
\end{enumerate}

All experimental artefacts---baseline spec and report, audit trail, revised spec, post-revision report---are saved under \texttt{results/sdt-feedback/} as the reproducible evidence base for this section.

% ----------------------------------------------------------------------------
\subsection{Interpretation}
\label{subsec:sdt-feedback-interpretation}
% ----------------------------------------------------------------------------

Three observations follow.

First, the experiment confirms the theoretical claim made in Chapter~\ref{ch:ai-development}: \emph{SDT's structured output is sufficient to drive measurable, autonomous specification improvement}. The agent received no instructions about what specific edits to make---only the JSON report---and produced a spec the validator scored substantially higher, empirically grounding the framework's positioning as \emph{feedback infrastructure for agent-driven development}, not merely a static linter.

Second, the experiment also confirms that single-pass agent revision is \emph{not} a substitute for human review. The P001 regression illustrates a class of failure mode peculiar to LLM editors: when the agent enriches one part of the spec, it can introduce inconsistencies elsewhere that a less-thorough validator would miss. The post-revision DriveBy report is, however, exactly the right input to a second agent pass, and the four-of-five conversion in a single pass is encouraging evidence that two or three iterations would converge to a fully-passing spec.

Third, the P003 partial result is itself diagnostic: the agent wired the 4xx/5xx responses but inlined them rather than referencing the \emph{shared} component-level error responses P003 demands, and the follow-up DriveBy run flagged exactly this---the validate--remediate--revalidate loop functioning correctly, each iteration's report carrying strictly more specific information than the last.

A further design limit deserves explicit statement: revising from the report alone, the agent cannot know which operations \emph{should} be protected or which errors the implementation \emph{actually} produces, so report-only revision risks a specification that diverges from the implementation; P006 functional testing catches such divergence only to the extent its coverage exercises the affected paths. Source-aware revision---giving the agent read access to the implementation alongside the report---is future work, as is the variant of supplying the agent with the principle \emph{definitions} in addition to the report, which might converge in fewer rounds.

The experiment scope is deliberately narrow---one specification, one agent, one revision pass---and the section's claim is correspondingly bounded: SDT feedback drives measurable correction \emph{at the unit-of-feedback scale}. Broader claims (e.g.\ that iterative agent loops always converge, or that this transfers across specifications) require the multi-spec, multi-iteration follow-on study that is recorded as future work in Chapter~\ref{ch:conclusion}.

\section{Summary}
\label{sec:eval-summary}
% ============================================================================

Across its four arms the evaluation establishes: check-level detection accuracy with deterministic re-runs and exactly one genuine framework miss (Section~\ref{subsec:per-check-extension}); clean per-layer discrimination of all four injected defect classes in the five-API pipeline, with zero misclassifications and only the reference reaching production (Section~\ref{sec:multi-api-eval}); a quantified, population-wide specification-quality gap that reproduces across the OpenAPI 3.x and Swagger 2.0 arms (Section~\ref{sec:wild-eval}); single-pass agent-driven improvement of Petstore from 1/6 to 4/6 with the validation report as sole feedback (Section~\ref{sec:sdt-feedback-experiment}); and an operational PoC running five concurrent \texttt{XSDLC} pipelines with sub-minute typical gate latency (Sections~\ref{sec:operational-eval} and~\ref{sec:cicd-metrics}). These results evidence RQ1 (detection accuracy and generalisation), RQ2 (derivation and agent-actionability), and RQ3 (GitOps integration), while RQ4 receives its primary evidence in Chapter~\ref{ch:kubernetes} with partial empirical support from the multi-application PoC; the mapping table in Section~\ref{sec:rq-contribution-mapping} reflects this allocation. Chapter~\ref{ch:ai-development} examines the AI-assisted development approach that enabled this evaluation at scale, Chapter~\ref{ch:discussion} revisits the research questions with the combined evidence, and Chapter~\ref{ch:conclusion} synthesises findings, limitations, and future work.
