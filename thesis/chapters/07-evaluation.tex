\chapter{Evaluation}
\label{ch:evaluation}

This chapter evaluates DDT and the DriveBy framework across three dimensions: a controlled experiment against a reference API designed to exercise all nine principles, a large-scale evaluation against real-world public APIs from the APIs.guru registry~\cite{apis-guru}, and a proof-of-concept operational evaluation of the XSDLC quality gate system deployed on Novelcore's internal development platform. The chapter concludes with CI/CD integration metrics that quantify the system's footprint and performance characteristics.

% ============================================================================
\section{Evaluation Framework}
\label{sec:eval-framework}
% ============================================================================

The evaluation addresses the three research questions from Chapter~\ref{ch:introduction}:

\begin{description}
    \item[RQ1] (Methodology soundness): Does DDT provide automated quality assurance comparable to manual approaches? Evaluated via the controlled experiment (Section~\ref{sec:controlled-eval}).
    \item[RQ2] (Automation extent): To what extent can validation and testing be derived from specifications without manual test authorship? Evaluated via the large-scale experiment (Section~\ref{sec:wild-eval}) and operational deployment (Section~\ref{sec:operational-eval}).
    \item[RQ3] (GitOps integration): How effectively does DDT integrate into cloud-native pipelines as an autonomous quality gate? Evaluated via the proof-of-concept deployment on Novelcore's cluster (Section~\ref{sec:operational-eval}).
    \item[RQ4] (Ontological specification): Can quality-gated delivery pipelines be expressed as Kubernetes-native ontological specifications? Addressed through architectural analysis in Chapters~\ref{ch:kubernetes} and~\ref{ch:conclusion} rather than empirical evaluation.
\end{description}

\section{Controlled Evaluation: perfect-api}
\label{sec:controlled-eval}
% ============================================================================

The controlled evaluation uses a reference API (\texttt{perfect-api}) designed to satisfy all nine DDT principles at baseline, then systematically injects defects to verify detection accuracy.

% ----------------------------------------------------------------------------
\subsection{Reference API Design}
\label{subsec:reference-api}
% ----------------------------------------------------------------------------

The \texttt{perfect-api} is a Python FastAPI application with a hand-crafted OpenAPI specification that satisfies every check of every principle. It defines eight operations across three resource groups: five CRUD endpoints for \texttt{/products} (list, create, get by ID, update, delete), a \texttt{POST /tasks} endpoint, and two utility endpoints (\texttt{GET /test/health}, \texttt{POST /test/echo}). The specification includes comprehensive error responses (400, 401, 403, 404, 500) with consistent schemas, typed parameters with constraints, OAuth2 security with scopes, semantic versioning with migration documentation, and response examples for all 2xx responses. The API is deployed to the \texttt{perfect-api-dev} namespace on \texttt{private.novelcore.org} and serves as the validation target for all three evaluation arms.

The five-API evaluation revealed a three-layer defence model, where each layer caught a distinct class of defect that the preceding layers could not detect:

\centering

\begin{tabular}{@{}clll@{}}

Each layer was necessary. Static validation alone would have passed \texttt{slow-api} and \texttt{broken-api}---both had valid specifications with only warning-level issues. \subsection{Severity Model in Practice}
\label{subsec:severity-model}
% ----------------------------------------------------------------------------

The severity model reflects DDT's core design principle: \textit{validation gates functional testing}. Of the nine principles, five are classified as critical in static validation (P001, P002, P003, P004, P005), while P006 and P007 are inherently critical in their respective check types (functional and load testing). Only versioning (P008) and test readiness advisory checks (P009) carry warning severity.

This 5/9 critical ratio reflects the gatekeeping function of static validation:

\begin{itemize}
    \item P002 (Documentation) is critical because functional test generators require examples and operation descriptions to produce valid request payloads; without them, test data is generic and rejected by API validation.
    \item P003 (Error Handling) is critical because negative test assertions require documented error schemas; without them, tests cannot verify error response shapes.
    \item P004 (Schema Definitions) is critical because type-less schemas force test generators to fall back on untyped placeholder values.
    \item As a result, only \texttt{perfect-api}---the reference API with a complete, hand-crafted specification---passes all gates. The four defect APIs (\texttt{bad-docs-api}, \texttt{no-auth-api}, \texttt{slow-api}, \texttt{broken-api}) are all blocked at the validation stage because their specifications are incomplete. This is the correct behavior: an incomplete specification should not proceed to functional testing.
    \item The only warning-severity principles (P008, P009) represent quality dimensions that degrade gracefully---versioning metadata and response-example advisories---without preventing test execution.
\end{itemize}

\section{Large-Scale Evaluation: APIs.guru}
\label{sec:wild-eval}
% ============================================================================

The large-scale evaluation applies DDT validation to real-world API specifications from the APIs.guru registry~\cite{apis-guru}, assessing how existing APIs perform against DDT's quality standards.

% ----------------------------------------------------------------------------
\subsection{Dataset and Protocol}
\label{subsec:dataset}
% ----------------------------------------------------------------------------

The evaluation harvests OpenAPI specifications from the APIs.guru registry using \texttt{tools/harvest-openapi-apisguru.py}. The dataset includes specifications from major API providers (Stripe, Twilio, GitHub, AWS) as well as smaller independent APIs. Each specification is validated in both \textit{minimal} and \textit{strict} modes using \texttt{tools/run-openapi-batch.sh}. Only static validation principles (P001--P005, P008) are evaluated; P006 (Functional Testing) and P007 (Performance Testing) are excluded because the evaluation does not have authenticated access to the live API endpoints.

The evaluation was conducted through an agent-driven workflow (described in detail in Chapter~\ref{ch:ai-development}): the AI agent developed the harvesting and batch testing tooling, executed the evaluation runs, parsed the structured JSON reports, identified cross-API patterns, and drafted the analysis. The human developer reviewed the interpretation and verified the numbers against raw output. This workflow itself validates a key DDT claim: that the structured, machine-readable output required by the Axiom of Observability is directly consumable by automated actors---including AI agents performing empirical analysis.

% ----------------------------------------------------------------------------
\subsection{Baseline: Swagger Petstore v3}
\label{subsec:petstore-baseline}
% ----------------------------------------------------------------------------

The Swagger Petstore v3---the canonical OpenAPI example maintained by the OpenAPI Initiative---serves as a reference data point. In strict mode, Petstore scores \textbf{1/6}: only P001 (OpenAPI Specification Compliance) passes. The five failing principles reveal systematic documentation quality gaps:

\begin{itemize}
    \item \textbf{P002} (Documentation Quality): Missing operation descriptions, parameter descriptions, and response examples across most endpoints.
    \item \textbf{P003} (Error Handling): No 5xx error responses defined; error response schemas lack structured fields.
    \item \textbf{P004} (Schema Definitions): String parameters lack length constraints; numeric fields lack range constraints.
    \item \textbf{P005} (Security): Security schemes defined but OAuth2 scopes not referenced in security requirements.
    \item \textbf{P008} (Versioning): Version field present and follows semver, but no versioning strategy, deprecation notices, or migration guides documented.
\end{itemize}

This result is significant: \textit{even the canonical example specification maintained by the OpenAPI Initiative fails DDT's strict validation}. This validates the thesis claim that existing specifications systematically neglect documentation quality, error handling completeness, and schema precision---the exact gaps that DDT is designed to detect.

\section{Operational Evaluation: Proof-of-Concept Deployment}
\label{sec:operational-eval}
% ============================================================================

The operational evaluation assesses DDT not as an isolated tool but as a proof-of-concept feature within an internal developer platform (IDP). This section evaluates the system's deployment characteristics, its impact on quality assurance workflow, and its behavior under operational conditions on a live cluster.

% ----------------------------------------------------------------------------
\subsection{XSDLC as IDP Feature}
\label{subsec:xsdlc-idp}
% ----------------------------------------------------------------------------

The DriveBy quality gate system is deployed on \texttt{private.novelcore.org} as one component of Novelcore's internal developer platform. The IDP is built entirely on Kubernetes operators and Crossplane compositions: database provisioning, networking, observability, and now quality-gated delivery pipelines all follow the same pattern---a custom resource declares the desired state, a composition generates the implementation resources, and Kubernetes controllers reconcile toward that state.

Within this IDP, XSDLC is not a standalone installation. It is a \textit{composable building block} that coexists with other platform capabilities. A single \texttt{XSDLC} custom resource (\(\sim\)25 lines of YAML) provisions approximately 44 Kubernetes resources in under 15 seconds: ArgoCD Applications, WorkflowTemplates, EventSources, Sensors, Ingresses, RBAC roles and bindings, PromotionStrategies, BranchProtection rules, environment branches, boilerplate manifests, ArgoCD push secrets, and per-namespace image pull secrets. Without XSDLC, a platform operator would need to manually create each of these resources through ClickOps---navigating the ArgoCD UI to create Applications, the GitHub UI to configure branch protection and webhooks, and \texttt{kubectl} to create RBAC, Sensors, and WorkflowTemplates. This manual process takes hours, is error-prone, non-reproducible, and impossible to version-control. XSDLC reduces it to a single declarative resource that can be reviewed in a pull request, stored in Git, and reconciled automatically.

% ----------------------------------------------------------------------------
\subsection{Quality Assurance Without Dedicated Testers}
\label{subsec:no-testers}
% ----------------------------------------------------------------------------

The most consequential operational finding is that DDT demonstrates the feasibility of operating without dedicated API testers in the promotion pipeline. Because validation is embedded in the promotion flow---every promotion PR is automatically validated against the OpenAPI specification and, where configured, load-tested---the quality gate runs without human initiation, human authoring of test cases, or human interpretation of results. This proof-of-concept deployment validates the architectural viability of zero-tester promotion gates, though production adoption would require further hardening and organizational validation.

In the proof-of-concept deployment, API owners can verify that their deployments have been validated against two contracts:

\begin{enumerate}
    \item \textbf{The specification contract} (P001--P005, P008, P009): The API's documentation, error handling, schema definitions, and security configuration match the declared specification. Any drift between the specification and the implementation is detected before promotion.
    \item \textbf{The performance contract} (load testing via \texttt{loadTestConfig}): The API handles the configured concurrent user count within the configured P95 latency threshold at the configured success rate. Any performance regression below these thresholds blocks promotion.
\end{enumerate}

This is not a claim that DDT replaces all testing. Unit tests, integration tests, and exploratory testing remain the developer's responsibility (the BYOCI boundary). DDT replaces the \textit{promotion-gate testing} that would otherwise require a dedicated QA engineer to run manual contract checks and load tests before each environment transition.

% ----------------------------------------------------------------------------
\subsection{Load Testing as Business Insurance}
\label{subsec:load-testing-insurance}
% ----------------------------------------------------------------------------

The quality gate does not prevent all production failures---it prevents \textit{preventable} failures. Consider the scenario where a production API experiences an out-of-memory (OOM) crash because the number of concurrent users has grown beyond the original capacity plan. The quality gate's response to this scenario is instructive:

The production environment \textit{was} load-tested before promotion. The \texttt{loadTestConfig} specified, for example, 50 concurrent users with a P95 latency threshold of 200\,ms and a 99.5\% success rate. The API passed these thresholds, and the promotion was approved. The OOM occurred because the \textit{actual} user load exceeded the \textit{configured} threshold---not because the system failed to test.

This is by design. The quality gate validates against \textit{declared business requirements}, not against unbounded traffic. The correct response to the OOM is not to blame the quality gate but to update the \texttt{loadTestConfig}---increase \texttt{concurrentUsers}, tighten \texttt{maxLatencyP95}, raise \texttt{minSuccessRate}---to reflect the new reality. Because these thresholds are fields in a Kubernetes custom resource, updating them is a one-line YAML change that takes effect on the next promotion cycle.

This pattern---declare thresholds, gate against them, update when reality diverges---transforms load testing from a periodic manual activity into a continuous, declarative contract. The thresholds are versioned in Git, reviewed in pull requests, and enforced automatically. When business requirements change, the thresholds change with them.

A natural extension (discussed in Section~\ref{sec:future-work}) is a controller that watches observability metrics (Prometheus, Grafana) and automatically adjusts \texttt{loadTestConfig} thresholds based on actual production traffic patterns. This would close the loop between observability and quality gating, making the system self-adjusting.

This is a positive finding for operational resilience---\texttt{selfHeal} and the quality gate reinforce each other---but it means the 5-minute timeout path was only observed when the staging gate genuinely failed and no deployment existed in the target namespace.

The multi-API evaluation also exposed a reporting inconsistency in the \texttt{load-only} CLI command. The \texttt{slow-api} production load test produced a JSON report with \texttt{"exit\_code": 0} despite the test having failed (\texttt{"status": "failed"}). The actual process exit code was correct (exit code~1, raised by the Cobra command handler's \texttt{ExitError} return), and the workflow correctly detected the failure via the process exit code rather than the JSON field. The bug was fixed by computing \texttt{result.Status} from the \texttt{FailedChecks} count before serializing the report. This is a self-testing discovery: the framework's own quality gate infrastructure, running the framework's own CLI, exposed a reporting inconsistency that unit tests had not covered.

\section{Summary}
\label{sec:eval-summary}
% ============================================================================

The evaluation demonstrates five key results:

\textbf{Detection accuracy} (RQ1). The controlled single-API evaluation showed 100\% detection rate for injected defects with zero false positives. The defect injection protocol confirmed that each principle checker detects its targeted defect class independently and deterministically.

\textbf{Multi-API discrimination} (RQ1). The five-API controlled evaluation demonstrated that only 1 of 5 APIs (20\%) completed the full staging-to-production pipeline. The remaining four were blocked at distinct layers: two by static validation (P005), one by functional testing (P006), and one by load testing (P007). Each API was blocked by the principle corresponding to its injected defect class, with zero misclassifications.

\textbf{Layered defence effectiveness} (RQ1, RQ2). The three-layer validation model (static, functional, performance) proved necessary and sufficient for the evaluated defect classes. No single layer could have caught all four defect types. The severity model correctly distinguished blocking failures (2 of 9 principles critical in static validation) from quality signals, allowing \texttt{slow-api} to pass staging with 3/6 warning-only failures before being caught by the performance layer at the production gate.

\textbf{Specification quality gap} (RQ2). The large-scale evaluation against APIs.guru revealed that real-world APIs systematically fail DDT's quality standards---even canonical examples like the Swagger Petstore score 1/6 in strict mode. This validated DDT's thesis that specification quality is systematically neglected and that automated enforcement is necessary. The zero-test-authorship property was confirmed: all validation rules were derived from the specification without any manual test case writing. The agent-driven evaluation workflow further validated this property: the structured JSON reports were consumed directly by an AI agent for cross-API pattern analysis without human interpretation of individual results (Chapter~\ref{ch:ai-development}).

\textbf{Operational deployment} (RQ3). The operational evaluation demonstrated that XSDLC functions as a composable IDP feature, provisioning a complete quality-gated delivery pipeline from a single custom resource in 15 seconds. The system ran in production on Novelcore's cluster across five APIs simultaneously, with 32 CommitStatus CRDs, 15 BranchProtection rules, and 10 gate workflow executions observed. Six of seven operational edge cases passed, with the sole failure attributable to ArgoCD's \texttt{selfHeal} restoring deployments faster than the test could induce unavailability---a positive resilience interaction rather than a system defect.

Chapter~\ref{ch:ai-development} examines the AI-assisted development methodology that enabled this evaluation at scale. Chapter~\ref{ch:discussion} revisits the research questions with the combined evidence. Chapter~\ref{ch:conclusion} synthesises the findings, discusses limitations, the ontological significance of XSDLC, and directions for future work.
