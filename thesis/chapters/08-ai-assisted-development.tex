\chapter{AI-Assisted Development}
\label{ch:ai-development}

This thesis was not only \textit{about} documentation-driven quality assurance---it was \textit{built} using a documentation-driven development methodology in which AI agents served as primary implementors, guided by structured knowledge protocols. This chapter examines that process: how the DriveBy framework, the XSDLC composition, the evaluation experiments, and this thesis document itself were developed through agentic workflows. The chapter makes three claims. First, that the CLAUDE.md knowledge protocol---a hierarchical system of machine-first documentation files---is the enabling infrastructure for effective agent-driven development. Second, that DDT's structured, machine-readable output positions it as a natural feedback source for autonomous agent loops. Third, that the experience of building this system with AI agents provides empirical evidence for the agent-readiness properties that DDT's axioms guarantee.

% ============================================================================
\section{Agentic Development as Method}
\label{sec:agentic-method}
% ============================================================================

% ----------------------------------------------------------------------------
\subsection{From Code Completion to Autonomous Engineering}
\label{subsec:completion-to-autonomous}
% ----------------------------------------------------------------------------

Chapter~\ref{ch:related-work} distinguished three levels of AI assistance: code completion, autonomous coding agents, and agentic development workflows. The development of DriveBy exercised all three levels, but the dominant mode was the third: multi-session agentic workflows in which an AI agent---Claude Code~\cite{claude-code}---operated as an autonomous engineering collaborator with persistent context, structured task delegation, and iterative feedback.

The distinction matters because it shapes the kind of knowledge infrastructure the project requires. Code completion needs only local context: the current file, the current function, the surrounding lines. Autonomous coding agents need task-level context: a bug report, a feature description, the relevant source files. Agentic development workflows need \textit{project-level} context: the architecture, the invariants, the conventions, the thesis chapter that describes the code being modified, and the memory of what was decided in previous sessions. This project-level context cannot be derived from the codebase alone---it must be authored, maintained, and structured for machine consumption.

% ----------------------------------------------------------------------------
\subsection{Scale of AI Assistance}
\label{subsec:scale}
% ----------------------------------------------------------------------------

The DriveBy project was developed across 57 Claude Code sessions. Of 33 total commits in the repository, 11 (33\%) carry the \texttt{Co-Authored-By: Claude} trailer, indicating substantial AI involvement in the implementation. The co-authored commits span the entire later development phase---from the monorepo restructuring through the XSDLC composition redesign, CLI enhancements, multi-API evaluation, and thesis writing.

The git history reveals a visible phase transition. Early commits are human-only with informal messages (``fix dockerfile'', ``push'', ``lesse''). Later commits are AI-assisted with structured, multi-section messages describing changes across code, documentation, Kubernetes resources, and thesis chapters simultaneously. This transition corresponds to the adoption of the CLAUDE.md knowledge protocol described in Section~\ref{sec:claudemd-protocol}: once the agent had structured context about the project's architecture, conventions, and thesis mapping, it could operate on multiple dimensions of the project simultaneously rather than making isolated, narrow changes.

The AI agent was not a peripheral tool. It was the primary implementor for the Crossplane composition pipeline (Chapter~\ref{ch:kubernetes}), the batch evaluation tooling (Chapter~\ref{ch:evaluation}), the report generation system (Chapter~\ref{ch:architecture}), and substantial portions of this thesis. The human developer provided architectural direction, reviewed outputs, corrected errors, and maintained the knowledge protocol. This division of labor---human as architect and reviewer, agent as implementor and writer---proved effective because the knowledge protocol ensured that the agent's implementation was grounded in documented decisions rather than ad-hoc inference.

\section{The CLAUDE.md Knowledge Protocol}
\label{sec:claudemd-protocol}
% ============================================================================

The central enabling infrastructure for agentic development in this project is a hierarchical system of \texttt{CLAUDE.md} files---machine-first documentation distributed across the monorepo. These files are not READMEs (written for human developers) or configuration files (written for specific tools). They are \textit{agent context files}: structured knowledge artifacts designed to be consumed by AI agents at the start of every working session, providing the persistent context that enables cross-session continuity.

% ----------------------------------------------------------------------------
\subsection{Hierarchical Structure}
\label{subsec:hierarchy}
% ----------------------------------------------------------------------------

The DriveBy project contains eleven CLAUDE.md files organized in a tree that mirrors the monorepo structure:

\begin{table}[htbp]
\centering
\caption{CLAUDE.md hierarchy in the DriveBy monorepo.}
\label{tab:claudemd-hierarchy}
\small
\begin{tabular}{@{}lp{8cm}@{}}
\toprule
\textbf{File} & \textbf{Scope} \\
\midrule
\texttt{CLAUDE.md} (root)                          & Project vision, DDT axioms, monorepo map, build commands, code quality rules, maintenance rules \\
\texttt{driveby-cli/CLAUDE.md}                     & Package map, dependency flow, validation modes, test structure \\
\texttt{driveby-cli/internal/principles/CLAUDE.md}  & PrincipleChecker interface, per-file status, axiom assignments, procedure for adding principles \\
\texttt{driveby-cli/internal/spec/CLAUDE.md}        & APISpec interface, adapter pattern, normalized types, strict rules \\
\texttt{kubernetes/CLAUDE.md}                       & Helm chart structure, XSDLC schema, cluster state, template escaping \\
\texttt{apis/CLAUDE.md}                            & API inventory, evaluation purpose \\
\texttt{apis/perfect-api/CLAUDE.md}                 & Endpoints, security model, expected pass/fail results \\
\texttt{thesis/CLAUDE.md}                          & Chapter specifications, source-to-code feed map, figure checklist, LaTeX conventions \\
\texttt{docs/CLAUDE.md}                            & Documentation index, diagram coverage \\
\texttt{.github/CLAUDE.md}                         & CI/CD workflow descriptions \\
\texttt{tools/CLAUDE.md}                           & Batch testing workflow, CSV formats \\
\bottomrule
\end{tabular}
\end{table}

When an agent begins working in a directory, the CLAUDE.md files in the path from root to that directory are loaded into the agent's context. An agent modifying \texttt{driveby-cli/internal/principles/p004\_schema.go} receives context from three CLAUDE.md files: the root (project-wide conventions), the CLI (package structure), and the principles directory (interface contract, axiom assignments). This layered loading ensures that the agent always has both the global invariants and the local domain knowledge needed for the task at hand.

% ----------------------------------------------------------------------------
\subsection{Content Categories}
\label{subsec:content-categories}
% ----------------------------------------------------------------------------

Each CLAUDE.md file contains four categories of knowledge:

\textbf{Structural knowledge}: what exists, where it lives, and how it connects. The root CLAUDE.md contains the monorepo directory table with status indicators. The CLI CLAUDE.md contains the package dependency graph. The principles CLAUDE.md contains a per-file table with line counts, axiom assignments, and implementation status.

\textbf{Invariants}: rules that must never be violated. The root file specifies five code quality rules, including the mandatory \texttt{spec.APISpec} abstraction and the prohibition on \texttt{os.Exit()} in command handlers. These invariants are repeated in the sub-directory CLAUDE.md files where they are most relevant, ensuring that an agent working in a leaf directory still encounters the project-wide rules.

\textbf{Procedures}: step-by-step instructions for common tasks. The principles CLAUDE.md includes a procedure for adding a new principle (create source file, test file, docs entry, update CLAUDE.md). The root file includes procedures for building, testing, and releasing. These procedures transform tribal knowledge (``ask Peter how to add a new principle'') into structured, machine-executable instructions.

\textbf{Thesis mapping}: bidirectional traceability between code and academic writing. Every sub-directory CLAUDE.md includes a ``Thesis Mapping'' section identifying which thesis chapter describes that code. The thesis CLAUDE.md includes a ``Complete Feed Map'' table mapping every thesis section to the code files and documentation files the agent should read before writing. This bidirectional mapping enables two critical workflows: updating thesis content when code changes, and updating code when thesis analysis reveals inconsistencies.

% ----------------------------------------------------------------------------
\subsection{Maintenance Rules and Self-Enforcement}
\label{subsec:maintenance-rules}
% ----------------------------------------------------------------------------

The CLAUDE.md protocol includes four maintenance rules encoded in the root file:

\begin{enumerate}
    \item When modifying source files, update the corresponding CLAUDE.md in that directory.
    \item When modifying source files, update the corresponding \texttt{docs/} file if documented behavior changes.
    \item When adding a new principle, create: source file, test file, \texttt{docs/principles/PXXX.md}, and update \texttt{principles/CLAUDE.md}.
    \item When adding a new directory, create a CLAUDE.md in it and add it to the root monorepo table.
\end{enumerate}

These rules are not merely advisory. The project's CI pipeline includes a documentation completeness check (\texttt{tools/check-docs.sh}) that mechanically verifies CLAUDE.md coverage. The script performs nine categories of checks: CLAUDE.md existence in required directories, principle documentation completeness, documentation-versus-reality consistency (detecting stale claims like ``Not yet implemented'' when the source file exists), thesis chapter status (flagging stubs under 20 lines), and test coverage gaps. When any check fails, the CI build fails.

This CI enforcement closes the loop. The CLAUDE.md protocol tells agents what to update; the CI check verifies that updates were made. The combination prevents knowledge drift---the same problem that DDT prevents for API specifications. In both cases, the solution is the same: treat documentation as a testable artifact and gate on its completeness.

\section{Persistent Agent Memory}
\label{sec:agent-memory}
% ============================================================================

Beyond the per-directory CLAUDE.md files, the project maintains a persistent memory system that survives across agent sessions. This memory captures information that cannot be derived from the codebase: user preferences, learned corrections, project decisions, and external references.

The memory system contains nine entries organized by type:

\begin{itemize}
    \item \textbf{User profile}: the developer's role (diploma thesis student), expertise (deep Go and Kubernetes, new to LaTeX), and communication preferences.
    \item \textbf{Feedback corrections}: learned behaviors from iterative interaction. Examples include ``documentation agents are critical, not optional'' (after the agent initially treated documentation updates as low-priority), ``don't assume---ask meaningful questions when decisions are ambiguous'' (after incorrect assumptions), and ``always update CLAUDE.md, docs, and thesis drafts after each session'' (after skipped documentation updates).
    \item \textbf{Project decisions}: architectural decisions with rationale, such as the monorepo restructuring plan and the target cluster configuration.
    \item \textbf{External references}: pointers to resources outside the codebase, such as the target cluster URL and the instruction to never reinstall ArgoCD.
\end{itemize}

The feedback corrections are particularly valuable. Each correction encodes a lesson learned from a failed interaction: the agent did something wrong, the user corrected it, and the correction was persisted so that the same mistake would not recur in future sessions. Over 57 sessions, these corrections accumulated into a behavioral profile that shaped the agent's approach to the project. This is analogous to organizational learning in human teams~\cite{nonaka-knowledge}: tacit knowledge (``Peter wants docs updated after every session'') is externalized into explicit, persistent artifacts that new sessions inherit.

\section{Agent-Driven Multi-API Evaluation}
\label{sec:agent-eval}
% ============================================================================

The evaluation described in Chapter~\ref{ch:evaluation} was not conducted manually. The large-scale evaluation against APIs.guru was designed, tooled, and executed through an agentic workflow in which the AI agent served as the primary experimenter.

% ----------------------------------------------------------------------------
\subsection{Tooling Development}
\label{subsec:tooling-dev}
% ----------------------------------------------------------------------------

The three-step batch testing pipeline (\texttt{tools/harvest-openapi-apisguru.py}, \texttt{tools/probe-openapi-endpoints.py}, \texttt{tools/run-openapi-batch.sh}) was developed collaboratively: the human specified the experimental protocol (harvest from APIs.guru, filter for reachable endpoints, validate in both minimal and strict modes), and the agent implemented the tooling. The harvester script queries the APIs.guru registry, filters for OpenAPI 3.x specifications, and produces a CSV of API names, specification URLs, and base hosts. The prober validates reachability by testing simple GET endpoints. The batch runner executes DriveBy against each entry and collects results.

This tooling enabled evaluation at a scale that would have been impractical manually. The batch runner processed APIs from major providers (Stripe, Twilio, GitHub, AWS) alongside smaller independent APIs, producing per-principle pass rates that revealed the systematic documentation quality gaps reported in Section~\ref{sec:wild-eval} of Chapter~\ref{ch:evaluation}.

% ----------------------------------------------------------------------------
\subsection{Agent as Experimenter}
\label{subsec:agent-experimenter}
% ----------------------------------------------------------------------------

The agentic workflow extended beyond tooling development. The agent executed the evaluation runs, analyzed the results, identified patterns (e.g., the universal gap between P001 pass rates and P002--P004 pass rates), and drafted the evaluation narrative. The human reviewed the analysis, verified the numbers against raw output, and refined the interpretation.

This workflow illustrates a key property of DDT's structured output. The validation reports produced by DriveBy are JSON documents with per-principle pass/fail status, specific check results, and suggested remediations. An AI agent can parse these reports, identify patterns across multiple APIs, and generate comparative analysis without human intervention. The same property that makes DDT output suitable for CI/CD quality gates---structured, machine-readable, deterministic---makes it suitable for agent-driven evaluation. The Axiom of Observability, which requires that validation produces measurable, actionable results, is what enables this workflow.

\section{Agent-Driven Thesis Writing}
\label{sec:agent-thesis}
% ============================================================================

This thesis document was itself produced through an agentic workflow. The thesis CLAUDE.md file (171 lines) provides chapter-by-chapter specifications that function as agent task descriptions: for each chapter, it lists the expected sections, the source code files to read, the documentation files to consult, and the key content requirements. The ``Complete Feed Map'' table maps every thesis section to both its code and documentation sources.

When the agent writes a thesis chapter, it follows a structured protocol:

\begin{enumerate}
    \item \textbf{Read the specification}: the thesis CLAUDE.md's chapter entry identifies what the chapter should contain.
    \item \textbf{Read the source}: the feed map identifies which code files and documentation files to read for factual accuracy.
    \item \textbf{Write the content}: the agent produces LaTeX content grounded in the actual implementation, using the code as the authoritative source.
    \item \textbf{Cross-reference}: claims in the thesis are verified against the codebase. Check counts, mode mappings, principle behaviors, CLI flags, and Crossplane resource counts are all derived from reading the implementation, not from memory or assumption.
\end{enumerate}

This protocol makes the thesis a \textit{tested document} in the same spirit that DDT makes the API specification a tested artifact. Just as DDT detects drift between a specification and its implementation, the thesis writing protocol detects drift between the thesis narrative and the code. The CI documentation check (Section~\ref{subsec:maintenance-rules}) extends this verification to the structural level, flagging thesis chapters that are stubs (under 20 lines) and CLAUDE.md entries that are inconsistent with the source tree.

The result is a thesis that is not merely \textit{about} documentation-driven quality---it \textit{practices} documentation-driven quality in its own construction. Every technical claim can be traced to a source code file through the feed map. Every code change triggers a review of the corresponding thesis sections. The same principle that DDT applies to API specifications---treat documentation as a testable, enforceable contract---is applied reflexively to the thesis itself.

\section{DDT as Agent Feedback Infrastructure}
\label{sec:ddt-agent-feedback}
% ============================================================================

The experience of building DriveBy with AI agents validates a claim made throughout this thesis: that DDT's structured output is naturally suited for consumption by autonomous agents. This section formalizes the connection.

% ----------------------------------------------------------------------------
\subsection{The Agent Validation Loop}
\label{subsec:agent-loop}
% ----------------------------------------------------------------------------

Consider an autonomous agent tasked with improving an API specification's DDT compliance. The agent executes the following loop:

\begin{enumerate}
    \item \textbf{Validate}: Run \texttt{driveby validate-only --validation-mode strict} against the specification.
    \item \textbf{Parse}: Read the JSON report. Identify failing principles and specific check failures.
    \item \textbf{Diagnose}: For each failure, read the \texttt{SuggestedFix} field and the \texttt{Details} map to determine what is missing or incorrect.
    \item \textbf{Remediate}: Generate specification changes that address the diagnosed issues---add missing descriptions (P002), document error responses (P003), add schema constraints (P004), define security schemes (P005).
    \item \textbf{Re-validate}: Run DriveBy again to confirm that the remediation resolved the issue without introducing new failures.
\end{enumerate}

This loop is feasible because of three properties guaranteed by DDT's axioms:

\begin{itemize}
    \item \textbf{Completeness} ensures that the validation report identifies \textit{what} is missing. A P002 failure with a details map listing ``44 request/response bodies missing examples'' gives the agent a precise remediation target.
    \item \textbf{Determinism} ensures that the agent can distinguish genuine fixes from noise. If the agent adds examples and re-runs validation, a P002 pass confirms the fix; a continued failure indicates the fix was incomplete. Non-deterministic validation would make this feedback loop unreliable.
    \item \textbf{Observability} ensures that the report is structured and machine-readable. The JSON format with per-principle results, named checks, and suggested fixes is parseable without natural language understanding---the agent reads fields, not prose.
\end{itemize}

% ----------------------------------------------------------------------------
\subsection{From Validation to Remediation}
\label{subsec:validation-remediation}
% ----------------------------------------------------------------------------

The \texttt{SuggestedFix} field in each \texttt{PrincipleResult} is the interface between validation and remediation. For P002 failures, the suggested fix identifies specific operations lacking descriptions and specific schemas lacking examples. For P004 failures, it identifies specific fields lacking type constraints. For P005 failures, it identifies missing security scheme definitions.

These suggested fixes are not aspirational---they are actionable specifications that an agent can translate into concrete specification edits. When DriveBy reports ``string field \texttt{email} lacks length constraints,'' the remediation is unambiguous: add \texttt{maxLength} and \texttt{pattern} properties to the field's schema. The specification change is derivable from the failure report without consulting external documentation, querying a human, or inferring intent from context.

This property---that the validation report contains sufficient information for autonomous remediation---is a direct consequence of the Axiom of Completeness applied to the validation output rather than the specification input. Just as DDT requires the specification to be complete enough for validation, DDT's own output must be complete enough for remediation. The \texttt{SuggestedFix} field ensures this.

\section{Lessons Learned}
\label{sec:lessons}
% ============================================================================

The experience of building DriveBy with AI agents over 57 sessions yields several observations relevant to the practice of agent-assisted software engineering.

\textbf{Structured knowledge protocols are prerequisites, not luxuries.} Without the CLAUDE.md hierarchy, every agent session began with the agent re-discovering the project's architecture, conventions, and invariants---a process that consumed context window capacity and produced inconsistent starting states. With the protocol, sessions began with the agent already knowing the dependency graph, the maintenance rules, and the thesis mapping. The initial investment in authoring CLAUDE.md files was repaid within the first few sessions through faster onboarding and fewer incorrect assumptions.

\textbf{Feedback corrections compound.} Each correction persisted in the memory system prevented the same mistake in all subsequent sessions. The correction ``always update CLAUDE.md after modifying source'' was issued once and obeyed in every subsequent session. Over 57 sessions, the accumulated corrections shaped the agent into a collaborator that anticipated the developer's expectations rather than requiring repeated guidance. This is the agent analog of team formation: initial friction gives way to shared norms.

\textbf{CI enforcement closes the knowledge loop.} The documentation completeness check in CI caught cases where the agent (or the human) modified code without updating CLAUDE.md or docs. Without CI enforcement, the knowledge protocol would have drifted from the codebase---the same documentation drift that DDT is designed to prevent. The parallel is exact: automated enforcement is necessary because voluntary compliance degrades under deadline pressure, whether the author is human or artificial.

\textbf{Bidirectional traceability enables concurrent development.} The thesis feed map---mapping code files to thesis chapters and vice versa---enabled the agent to update both simultaneously. When a principle checker's behavior changed, the agent updated the source code, the test, the CLAUDE.md, the docs entry, and the thesis chapter in a single session. Without bidirectional traceability, these updates would have been sequential and error-prone, with each downstream artifact at risk of falling out of sync.

\textbf{Machine-readable output is agent-ready output.} DDT's structured JSON reports were consumed directly by the agent during evaluation analysis. The same property that makes DriveBy suitable for CI/CD pipelines---structured, deterministic, per-principle results---made it suitable for agent-driven evaluation. This is not a coincidence; it is a consequence of the Axiom of Observability, which requires output that automated actors (whether shell scripts or AI agents) can consume.

\section{Summary}
\label{sec:ai-summary}
% ============================================================================

This chapter examined the AI-assisted development methodology used to build DriveBy, the XSDLC pipeline, and this thesis. The central enabling infrastructure is the CLAUDE.md knowledge protocol---a hierarchical system of eleven machine-first documentation files, enforced by CI, that provides AI agents with the persistent, structured context needed for effective cross-session collaboration. The persistent memory system extends this with user preferences, learned corrections, and project decisions that shape agent behavior over time.

The multi-API evaluation (Chapter~\ref{ch:evaluation}) was conducted through an agentic workflow in which the agent developed the tooling, executed the experiments, and analyzed the results. DDT's structured output---a direct consequence of the Axiom of Observability---enabled the agent to parse validation reports, identify cross-API patterns, and generate comparative analysis without human intervention.

The thesis itself was written through the same protocol: chapter specifications in the thesis CLAUDE.md guided the agent's writing, the feed map ensured that every claim was grounded in the actual codebase, and CI enforcement caught documentation drift.

Three properties of DDT enable this agent integration: Completeness ensures that validation reports identify what is missing, Determinism ensures that agents can distinguish genuine fixes from noise, and Observability ensures that output is structured and machine-readable. Together, these properties position DDT not only as a quality assurance methodology but as a feedback infrastructure for autonomous agent workflows---the validate-diagnose-remediate-revalidate loop that represents the next frontier of specification-driven development.
