\section{Summary of Contributions}
\label{sec:contributions-summary}
% ============================================================================

This thesis presented six principal contributions to the field of automated API quality assurance, summarised below in the same order as Section~\ref{sec:contributions} of Chapter~\ref{ch:introduction}.

\textbf{A conceptual framework for specification-driven API validation.} Specification-Driven Testing formalises specification-driven validation as three axioms (Completeness, Determinism, Observability) operationalised by nine automatable principles (P001--P009), all derived from the OpenAPI specification with zero manual test authorship (Chapter~\ref{ch:methodology}). We claim it as a conceptual framework rather than a complete software-testing methodology in its own right; the elements that would elevate it to one (test derivation procedure, execution and failure semantics, lifecycle governance) are scoped as future work in Section~\ref{sec:future-work}.

\textbf{The DriveBy framework.} A Go CLI tool implementing SDT (Chapter~\ref{ch:architecture}): the \texttt{APISpec} abstraction enables version-agnostic validation across OpenAPI~3.x and Swagger~2.0; seven principle checkers apply each check only in the modes for which it is suitable, across four validation modes (minimal, strict, test-ready, test-only); and structured reports carry per-principle pass/fail status, severity classifications, and suggested remediations.

\textbf{The XSDLC delivery pipeline.} A Crossplane custom resource definition that transforms the DriveBy CLI from a standalone tool into a declarative, Kubernetes-native quality gate system: a single XSDLC custom resource (\(\sim\)25 lines of YAML) generates approximately 45--50 managed Kubernetes objects in under 15 seconds (Chapter~\ref{ch:kubernetes}). The XSDLC follows the BYOCI (Bring Your Own CI) principle: it owns delivery while leaving application CI to the developer's chosen tooling (Chapter~\ref{ch:workflow}).

\textbf{XSDLC as ontological specification.} The XSDLC CRD functions as a Kubernetes-native ontological artifact that operators and autonomous agents can discover, inspect, and manage as a composable building block within an internal developer platform. This contribution reframes quality-gated delivery as a platform capability expressed through structured, machine-readable specifications rather than imperative tooling.

\textbf{Empirical evaluation.} A four-arm evaluation of SDT---a controlled experiment over a five-API suite with deliberate defect injection, an agent-driven large-scale study over public OpenAPI specifications from APIs.guru, a proof-of-concept deployment on the Novelcore IDP, and an agent-feedback experiment in which an AI agent, using the DriveBy report as its sole feedback signal, improved the Swagger Petstore specification from 1/6 to 4/6 passing principles (Section~\ref{sec:sdt-feedback-experiment})---establishes that the framework detects real specification-quality gaps, integrates into a live GitOps pipeline, operates without dedicated testers in the promotion path, and produces feedback actionable by autonomous agents (Chapter~\ref{ch:evaluation}).

\textbf{An agent-driven development framework.} The CLAUDE.md knowledge protocol---a hierarchical system of sixteen machine-first documentation files---provided AI agents with persistent, structured context during the 12-day Phase~B partnership window described in Chapter~\ref{ch:ai-development}, in which the author and the agent jointly produced (under the author's direction and review) the productisation polish, the multi-API evaluation pipeline, and the thesis-writing scaffolding. We claim this as an enabling framework within an existing software development lifecycle, not a standalone methodology. SDT's structured output proved directly consumable by AI agents, validating the Axiom of Observability's practical utility beyond CI/CD gating.

\section{Answers to Research Questions}
\label{sec:rq-answers}
% ============================================================================

\textbf{RQ1:} \textit{Can a conceptual framework grounded in specification completeness, behavioral determinism, and operational observability demonstrate the feasibility of automated API quality assurance that can operate without dedicated testers in the promotion pipeline?}

Yes. The controlled evaluation (Section~\ref{sec:controlled-eval}) detected all seven principle-level injected defects with zero false positives; at the finer-grained check level, the per-check extension (Section~\ref{subsec:per-check-extension}) detected 12 of 15 single-check defects (80\%)---the three misses trace to known framework limitations, not evaluation artefacts---and all three evaluable multi-principle combinations. The large-scale evaluation (Section~\ref{sec:wild-eval}) across real-world APIs from the APIs.guru registry confirmed that SDT detects real quality gaps that even canonical specifications (Swagger Petstore v3) exhibit. The three axioms are not aspirational---they are necessary conditions for the validation loop to function: Completeness ensures the specification is a sufficient test oracle, Determinism ensures reproducible gate decisions, and Observability ensures actionable feedback for CI/CD pipelines and AI agents alike, a sufficiency the agent-feedback experiment (Section~\ref{sec:sdt-feedback-experiment}) demonstrated empirically.

\textbf{RQ2:} \textit{To what extent can validation rules, test cases, and quality gates be derived automatically from OpenAPI specifications without manual test authorship?}

Fully, for the implemented static principles. All seven principle checkers derive their validation logic entirely from the OpenAPI specification. No test cases are authored by hand; no test data is manually curated. The qualification: performance gating (P007) is parameterised by thresholds declared in the XSDLC custom resource rather than derived from the OpenAPI document, so the zero-authorship property holds for the static principles and functional testing, while non-functional thresholds remain a declared deployment-policy artifact (Chapter~\ref{ch:related-work}). The test-ready mode (P009) explicitly validates whether the specification provides sufficient detail for automated test generation. The multi-API controlled evaluation (Section~\ref{sec:multi-api-eval}) showed each defect API blocked by exactly the principle matching its injected defect class, and the large-scale evaluation confirmed meaningful validation results for any valid OpenAPI specification without per-API configuration.

\textbf{RQ3:} \textit{How effectively does specification-driven quality assurance integrate into cloud-native GitOps pipelines, and can a single declarative custom resource replace the manual provisioning of quality gate infrastructure?}

Effectively, as demonstrated by the proof-of-concept deployment on Novelcore's cluster. A single XSDLC custom resource (\(\sim\)25 lines of YAML) generates approximately 45--50 managed Kubernetes objects in under 15 seconds, replacing hours of manual provisioning across the ArgoCD UI, GitHub UI, and \texttt{kubectl}. The CI/CD integration metrics (Section~\ref{sec:cicd-metrics}) point the same way: sub-second CLI startup, 2--5 second strict-mode validation, and under 90 seconds of end-to-end gate latency from webhook to posted commit status keep the gate inside interactive developer feedback loops. The integration also scaled: the multi-API evaluation (Section~\ref{sec:multi-api-eval}) ran five concurrent XSDLC-provisioned pipelines without operational problems, and the surgical coexistence model allowed installation into---and removal from---an existing cluster without modifying its running ArgoCD, Argo Workflows, and Argo Events installations. Every promotion was automatically validated against both the specification contract and configurable performance thresholds, demonstrating the feasibility of operating quality gates without dedicated testers in the promotion pipeline.

\textbf{RQ4:} \textit{Can quality-gated delivery pipelines be expressed as Kubernetes-native ontological specifications that operators and autonomous agents can discover, inspect, and manage?}

Yes. Section~\ref{sec:ontological-spec} demonstrates that the XSDLC CRD functions as a machine-readable, structurally typed ontological artifact: in Novelcore's IDP it is one Crossplane composition among many, discoverable via the Kubernetes API, inspectable, and manageable by higher-level operators as a child resource. Its structural typing means that a team onboarding controller could create XSDLC resources without understanding the composition's internals, and an observability controller could adjust load testing thresholds without human intervention; these controllers are not yet implemented (see Section~\ref{sec:future-work}).

\section{XSDLC as Ontological Specification}
\label{sec:ontological-spec}
% ============================================================================

The most significant architectural insight of this thesis is that XSDLC is not a tool---it is a \textit{specification}. Specifically, it is a Kubernetes Custom Resource Definition that describes a quality-gated delivery pipeline as a machine-readable, structurally typed, discoverable ontological artifact~\cite{gruber-ontology}.

This distinction matters because it determines how the system composes with other systems. A tool must be invoked; a specification can be \textit{discovered}. Any Kubernetes controller, operator, or autonomous agent can:

\begin{itemize}
    \item \textbf{Discover} XSDLC resources via the Kubernetes API (\texttt{kubectl get xsdlcs}).
    \item \textbf{Inspect} their declared delivery pipeline---environments, quality gates, thresholds.
    \item \textbf{Manage} them as child resources, e.g.\ a team onboarding controller creating an XSDLC while provisioning a new microservice.
    \item \textbf{Update} individual fields. An observability controller could adjust \texttt{loadTestConfig.concurrentUsers} to production traffic patterns; a security policy controller could enforce that every XSDLC includes a \texttt{validate-only} check with \texttt{validationMode: strict}, guaranteeing the security principle is always evaluated---though the coverage it enforces is limited to what P005 checks, the presence and operation-level wiring of declared authentication schemes; deeper security testing is future work (Section~\ref{sec:future-work}).
\end{itemize}

In Novelcore's IDP, XSDLC sits alongside database, networking, and observability compositions, all following the same pattern: a custom resource declares intent, a composition generates implementation, and controllers reconcile toward the declared state. The XSDLC's value here is not its validation logic (which the DriveBy CLI provides) but its \textit{structural integration} into the Kubernetes resource model: typed, versioned, discoverable, reconcilable.

This framing connects to the platform engineering movement~\cite{humanitec-platform-engineering, team-topologies}: a CRD is the Kubernetes-native \textit{self-service interface}, exposing a simplified API surface (the XRD schema) that abstracts away implementation complexity (the composition). The XSDLC demonstrates that quality-gated delivery can be delivered through this same interface, making quality assurance a platform capability rather than a per-team responsibility.

The transition from CLI flags to Custom Resource Definition (Section~\ref{sec:cli-to-cr-evolution}) is a change not of tool but of \textit{paradigm}: the operator stops telling the system what to do and declares how the world should \textit{be}, and the control plane converges toward that state continuously. This shift---from imperative instruction to ontological declaration---is the central architectural insight of this thesis, and it applies far beyond API validation.

\section{Limitations}
\label{sec:limitations}
% ============================================================================

The limitations below were identified through three channels: the empirical evaluation (Chapter~\ref{ch:evaluation}), the supervisory review, and deliberate implementation scope decisions.

\textbf{Verdict tier is open-loop.} The controller in the verdict tier (Section~\ref{subsec:controller-stack}) decides \emph{promote} or \emph{block}, but does not itself emit a corrective signal $u$ that reduces the error $e(t)$ on the plant. There is no automated spec re-write, no implementation patch, no autonomous remediation. The error signal is exported as a structured report; the corrective action is performed externally---by a developer or, in Section~\ref{sec:sdt-feedback-experiment}, by an AI coding agent consuming the same report. This is the deliberate, scoped open-loop component of an otherwise self-reconciling system, and closing it autonomously is recorded as future work below. Drift between gate evaluations is \emph{not} a separate limitation: the promotion chain actively blocks any production-bound transition that has not first passed P006, so spec--implementation divergence cannot reach production by construction (Section~\ref{subsec:controller-stack}).

\textbf{Principle coverage.} Two of nine principles (P006: Functional Testing, P007: Performance Testing) are defined theoretically but not yet implemented as \texttt{PrincipleChecker} wrappers. The underlying testing logic exists in the CLI but does not contribute to the structured validation report. Closing this gap must preserve the layered-validation design: strict mode remains \emph{static-only}, so the P006/P007 wrappers would join the dynamic \texttt{test-only} mode (or a composed full-validation mode; Section~\ref{sec:future-work}), never the static modes. P006 itself has a depth limit: it verifies that responses \emph{structurally} comply with the declared schemas (status codes, types, required fields), not that the response \emph{content} is semantically correct for the request.

\textbf{Keyword-based checks.} Several P008 checks (versioning strategy, breaking changes, migration guides) rely on keyword matching in the \texttt{info.description} field. This approach is brittle: a specification that documents its versioning strategy in a separate markdown file rather than in the OpenAPI description would fail P008 despite having adequate documentation. More fundamentally, P008 verifies only that a versioning strategy is \emph{documented}, not how well versioning is \emph{supported} by the API---assessing the latter would require understanding the semantics of the applied strategy (URI versioning, header negotiation, deprecation windows) and testing the API's behaviour against them.

\textbf{Single specification format.} DriveBy currently supports OpenAPI~3.x and Swagger~2.0. APIs documented in other formats (GraphQL schemas, gRPC protobuf definitions, AsyncAPI specifications) are not covered. The \texttt{APISpec} abstraction layer is designed to accommodate additional adapters, but none have been implemented.

\textbf{Load testing scope.} The current load testing implementation validates against static thresholds declared in the XSDLC spec. It does not account for time-varying traffic patterns, seasonal load spikes, or progressive capacity growth. The thresholds represent a point-in-time business requirement, not an adaptive contract. Load testing is also the \emph{only} non-functional testing performed: stress and soak testing, security testing beyond P005's authentication-scheme checks, and reliability/chaos testing are not covered.

\textbf{Evaluation scale.} The large-scale evaluation uses public APIs from APIs.guru, which may not be representative of internal enterprise APIs. Internal APIs often have different documentation practices, security models, and quality standards. The operational evaluation is limited to a single IDP (Novelcore) with a single reference API (perfect-api).

\textbf{Single delivery cluster.} The XSDLC composition is exercised against one ArgoCD/Crossplane cluster (\texttt{private.novelcore.org}); multi-cluster promotion, where environments span distinct Kubernetes clusters, is not exercised. The architectural shape supports it---ArgoCD ApplicationSets and multi-cluster Crossplane providers exist---but the present evaluation does not test the cross-cluster orchestration path.

\section{Future Work}
\label{sec:future-work}
% ============================================================================

Each direction below addresses a specific limitation from Section~\ref{sec:limitations}.

\textbf{Adaptive load testing thresholds.} A Kubernetes controller that watches production observability metrics (Prometheus, Grafana) and adjusts \texttt{loadTestConfig} fields to actual traffic patterns, tightening the gate to the observed operational reality. This would partially close the observability--gating feedback loop---partially, because it improves only the gate thresholds in the XSDLC resource, not the OpenAPI specification itself, which may also need improvement.

\textbf{Risk-based scoring model.} A severity-weighted scoring model in which each failed check contributes a weight proportional to its operational risk---a missing security scheme (P005) outweighs a missing example (P002). The implementation deliberately keeps a binary verdict for gating simplicity; a risk-based score would complement it with a continuous quality signal for trend dashboards, graduated promotion thresholds, and longitudinal comparison. The conceptual work is calibrating the weights: expert judgement, the API-quality literature, or learned remediation effort. This is the natural follow-up to the construct-validity discussion in Chapter~\ref{ch:discussion}.

\textbf{Agent-driven remediation.} Autonomous engineering agents~\cite{swe-agent, devin-cognition} that parse SDT validation reports, identify failing principles, generate fixes, and re-push to trigger re-validation. The scope is deliberately \emph{specification-first}: agents remediate the OpenAPI specification (or, for gate-configuration failures, the XSDLC resource), keeping the implementation as the stable ground truth; extending remediation to application code is explicitly conditional on first establishing a reliable procedure for deciding which artifact---specification or implementation---is authoritative when the two disagree. The structured output required by the Axiom of Observability is precisely the interface agents need, as the agent-feedback experiment (Section~\ref{sec:sdt-feedback-experiment}) demonstrated for a single report-driven pass. The target, however, is a multi-round validate--remediate--revalidate loop converging to complete mitigation of all principle failures; characterising that convergence at scale is the doctoral extension recorded in Section~\ref{subsec:doctoral-continuation}.

\textbf{P006 and P007 as PrincipleCheckers.} Wrapping the existing functional and performance testing logic into the unified principle evaluation pipeline, so runtime results contribute to the structured report in the same per-principle format as static checks. The extension preserves the static/dynamic layering: strict mode remains static-only, permanently, and the wrappers join the \texttt{test-only} mode; a complete nine-principle assessment would come from a composed \emph{full validation} run that executes both layers and merges their reports, never from folding runtime testing into a static mode.

\textbf{Advanced security testing.} Security coverage today is what P005 checks: declared security schemes and their operation-level wiring. A near-term extension is dynamic security-testing scenarios derived from the specification---verifying that protected operations reject unauthenticated and under-scoped requests and that undeclared endpoints are unreachable. Like P006/P007, these would live in the dynamic validation layer, not the static modes.

\textbf{Performance thresholds as an OpenAPI vendor extension.} A vendor extension (e.g.\ \texttt{x-performance}) carrying non-functional thresholds---latency percentiles, throughput, concurrent-user envelopes---inside the OpenAPI document itself. The performance gate would then be derived from the specification rather than parameterised by the XSDLC resource, removing the single qualification on the zero-authorship claim (Chapter~\ref{ch:related-work}); the XSDLC CR would retain only gate \emph{policy}. This is the near-term form of the metamodel-level extension recorded in Section~\ref{subsec:doctoral-continuation}.

\textbf{Scheduled prod-environment gate.} The per-PR gate guarantees that no spec--implementation divergence introduced through the pipeline reaches production (Section~\ref{subsec:controller-stack}). A complementary engineering extension---not a research direction---is a CronWorkflow trigger executing P006 over the deployed prod API on a schedule, reusing the same XSDLC gate machinery. This covers the residual class of changes that bypass the promotion chain: out-of-band operator intervention, infrastructure-level shifts (runtime upgrades, library auto-updates), or data-driven divergences that do not manifest at PR time.

\textbf{Multi-format specification support.} Extending the \texttt{APISpec} abstraction layer with adapters for GraphQL introspection schemas, gRPC protobuf definitions, and AsyncAPI specifications. The extension is more than an interface exercise: those formats lack first-class equivalents for documented error surfaces, security-scheme wiring, examples, and versioning narratives, and must be extended or supplemented before the checkers can produce comparable verdicts.

\textbf{Enterprise multi-cluster patterns.} Extending XSDLC to support multi-cluster delivery pipelines where environments span different Kubernetes clusters (e.g., development on a shared cluster, production on a dedicated cluster). This would require cross-cluster ArgoCD ApplicationSets~\cite{argocd} and multi-cluster Crossplane providers~\cite{crossplane}.

\textbf{XSDLC as operator child resource.} Realising the composition pattern of Section~\ref{sec:ontological-spec} at scale: a microservice provisioning operator declares an XSDLC resource as a child alongside database credentials, networking policies, and observability configurations, making quality assurance a declared attribute of every service rather than a separate concern.

\subsection{Doctoral Continuation}
\label{subsec:doctoral-continuation}
% ----------------------------------------------------------------------------

Several research directions exceed the scope of a diploma thesis but constitute a coherent doctoral programme building directly on the foundations laid here.

\textbf{From conceptual framework to formal methodology.} The most consequential extension is to upgrade SDT from a conceptual framework---three axioms, nine principles, an empirical implementation---to a complete software-testing methodology. This requires three additions: (i)~a formal \emph{test derivation procedure} that maps from the specification to a test suite (controlled by a derivation logic, with completeness and minimality theorems); (ii)~explicit \emph{execution and failure semantics} (a labelled transition system over validation states, with axioms over how partial failures compose into a global verdict); and (iii)~\emph{lifecycle governance} (when a principle is added, deprecated, refined, or split; how methodology versions relate). Together they would make SDT a peer to TDD, BDD, and Domain-Driven Design rather than a candidate for that role.

\textbf{Coverage extension across testing types.} The framework covers contract validation (P001--P005, P008, P009), functional testing (P006), and load testing (P007), but a complete API testing programme also includes unit, integration, end-to-end, security, and reliability/chaos testing. The conceptual question is whether each can be expressed as a principle (or family of principles) over the specification, or requires complementary frameworks; the empirical question is what the principle space looks like at full coverage.

\textbf{Stress testing as a first-class concern.} The load-testing principle (P007) tests the system under \emph{expected} load. A complementary stress-testing principle would test the system under \emph{breaking} load, surfacing the operational envelope rather than the operational baseline. The methodological question is how to derive stress-test parameters from the specification: declared rate-limit annotations, declared SLA fields, observed historical load patterns.

\textbf{Ontological extension to performance and security metrics.} OpenAPI's vocabulary lacks first-class concepts for performance characteristics (expected latency, throughput, percentile guarantees) and for security-testing semantics beyond declared authentication schemes (threat assumptions, enforcement behaviours, scope semantics). Extending the OpenAPI metamodel with these annotation vocabularies, then deriving the corresponding testing principles from them, would let the contract specify both the ideal functional \emph{and} non-functional behaviour of the API, leaving the XSDLC CR to specify mainly gate policies.

\textbf{Conditional gate transitions.} A \emph{conditional} gate would let a build through subject to constraints (e.g.\ ``promote to staging only if observed P95 latency in the last 24h is below 100\,ms''), requiring a formal language for single and composite gate conditions, an evaluator integrated with cluster observability, and an audit trail for promotion decisions. The delta is precise: today's gates evaluate point-in-time load-test results against XSDLC-declared thresholds; conditional gates would evaluate constraints over live, time-windowed production observability data.

\textbf{Outer loop with dynamic setpoint over the existing two-tier stack.} The doctoral extension to the two-tier controller stack (Section~\ref{subsec:controller-stack}) is a \emph{third, outer} loop that adjusts the verdict-tier setpoint based on observed system behaviour: an SLA-based controller that tightens the quality threshold when observed latency creeps up and loosens it when stability is established. This is control-theoretic SDT---the natural research bridge between specification-driven testing and self-adjusting platforms.

\textbf{Empirical proof of agent-driven correction at scale.} The single-spec, single-iteration experiment in Section~\ref{sec:sdt-feedback-experiment} establishes that the SDT report is sufficient feedback for an agent to make measurable corrections. The doctoral extension is the multi-spec, multi-iteration study---dozens of public APIs, multiple agents, multiple revision passes, with statistical analysis of convergence rates, failure modes, and the agent characteristics that predict success---converting ``feedback infrastructure for agent-driven development'' from a substantiated claim into a fully characterised empirical regime.

These directions are not independent: the formal methodology is the substrate on which the others rest, and a doctoral plan would address them roughly in the order listed, with the formalisation programme spanning the first eighteen months.
